# Глава 8. Этапы 4–5: план доставки и реализация

*Коротко. После зелёного гейта архитектуры агент режет ценность во времени, потом меняет систему. Не наоборот.*
*План — вехи, срез v1, cut list, критерии готовности, порядок риск→ценность→зависимость. Не бэклог из ста желаний.*
*Задача агента — граница, которую можно собрать, проверить и откатить за один ход. Гигантский diff запрещён.*
*Код пишется по конвенциям репозитория и Книге 1, Главы 17–23. Сначала тесты на риск среза, не «покроем потом».*
*Легаси сначала картируется. Правка наугад — стоп.*
*Самопроверка: сборка, тесты, линт, секреты, ревью своего diff до выдачи человеку.*
*Человеку глава — контроль объёма и момента «спроси меня». Агенту — машина нарезки и безопасного изменения.*

Этапы Delivery Plan и Implementation переводят RFC в инкременты, которые существуют в git. Содержание планирования — Книга 1, Глава 38, разделы 38.4–38.6; календарные рамки зрелости — Книга 1, Глава 46, не как SLA агента. Содержание кода — Книга 1, Главы 17–21 по слою, поставка — Книга 1, Глава 23. Здесь — порядок исполнения: что нарезать, в каком порядке строить, как менять чужой репозиторий, когда остановиться. Качество и безопасность полного контура — Книга 2, Глава 9. Не объявляй срез готовым к прод, пока гейт 9.7 не зелёный или не пропущен человеком с риском.

Вход. Гейт Книги 2, Глава 7, раздел 7.7 зелёный или жёлтый с записанным skip. В YAML есть стиль, стек, салфетка, модель данных среза. Нет входа — вернись, не открывай пустой `src/`.

Провал. RFC на модульный монолит есть. Агент генерирует двенадцать сервисов, три ORM и «базовый CRUD всего домена» одним PR. Критериев готовности нет. Тесты — снапшот «чтобы пайплайн был зелёный». Человек не может ревьюить. Это нарушение Книги 1, Глава 23, раздел 23.2 (размер изменений) и Книги 1, Глава 42, раздел 42.4 (ревью). Второй провал: в легаси правится файл, который агент не читал, «по аналогии».

Команда 1–3: план на одну страницу, срез на дни, один деплой. 10–30: план итерации стыкуется с чужими контрактами (Книга 1, Глава 14, раздел 14.4). 100+: агент не объявляет roadmap холдинга; режет работу внутри владельца сервиса (Книга 1, Глава 41, раздел 41.3).

## 8.1. От архитектуры к плану: декомпозиция на вехи, MVP и итерации

План доставки отвечает на четыре вопроса и больше ничего: какой срез ценности первый; какие вехи после него; что вырезано до даты; как узнаем, что срез готов. Не путай план с архитектурой: стиль уже выбран. Не путай с бэклогом желаний: «ещё SSO, ещё мобилка, ещё ИИ» без порядка — не план.

Вехи. Горизонты Книги 1, Глава 38, раздел 38.4: сейчас / следующий цикл / позже. Агент пишет 3–5 вех, не диаграмму Ганта на год. Каждая веха: пользовательская работа, которая становится возможной, плюс технический инвариант (схема, auth, наблюдаемость). Веха «настроить инфраструктуру» без пользовательской работы запрещена, кроме блока, без которого нет первого экрана.

MVP. Сначала открой Книга 1, Глава 5, раздел 5.6: ложный MVP — уменьшенный клон. Срез v1 — проверка гипотезы состояния (Книга 2, Глава 6), а не паритет с лидером. Если гипотеза ещё concierge — план может быть без приложения. Если гипотеза про UX ядра — вертикальный срез одной работы, не горизонтальный каркас всех сущностей.

Итерации. Размер: то, что 1–3 человека (или агент плюс человек) доводят до работающего инкремента за дни, не за квартал. Оценка — диапазон, не сторипойнт как истина (Книга 1, Глава 38, раздел 38.5). Пиши `p50`/`p90` словами порядка: «день–три / до недели», не «5 SP».

Cut list обязателен. Без него срок врёт (Книга 1, Глава 38, раздел 38.6). Всё, что не в срезе, попадает в `cut_for_deadline` с условием возврата. Feature flags (Книга 1, Глава 23, раздел 23.7) — для незаконченного на живом продукте, не как склад мёртвого кода.

`ЕСЛИ RFC закрыт, а человек просит «начинай кодить» без вех и cut list → останови, выдай план среза на одну страницу, код не пиши → проверка: есть v1, критерии, вырезанное; stage=delivery_plan.`

`ЕСЛИ в плане v1 есть паритет с названным гигантом → вырежи до одной работы гипотезы, перенеси паритет в not_this/later → проверка: в срезе нет «как у X, только меньше».`

Когда сжимать план до трёх строк: compressed_hour (Книга 2, Глава 5, раздел 5.5), внутреннее демо. Когда нельзя: платежи, миграция схемы, публичный API. Платите за тонкий план — скрытым объёмом в коде; лови это размером diff (8.2).

## 8.2. Нарезка задач для исполнения агентом: размер, границы, критерии готовности

Задача агента — единица, которую можно закончить без удержания всей системы в рабочей памяти. Граница: один модуль или один инвариант плюс тесты на риск. Не «сделай бэкенд».

Размер. Порядок величины, не догма: diff, который человек способен просмотреть за один присест. Практика ревью: качество падает, когда изменение слишком велико, чтобы удержать инварианты (Книга 1, Глава 42, раздел 42.4). Если оценка «больше экранов, чем ревьюится» — режь. Не мери сторипойнтами.

Границы. В задаче явно: входные файлы, выходные файлы, чего не трогать, зависимость от предыдущей задачи. Запрещены задачи вида «улучши код» без критерия. Разрешены: «добавь сущность Дело с тенантом и тестом инварианта ACL»; «подключи логин по уже выбранному протоколу из ADR».

Критерии готовности задачи — наблюдаемые. Сборка проходит. Тест на инвариант зелёный. Линт репозитория чист на затронутых путях. Секретов в diff нет. Документ контракта обновлён, если менялся API. Нет критерия — задача не взята.

Связь с DoD среза. Сумма зелёных задач ≠ готовый продукт. DoD среза включает то, что задачи не покрывают поодиночке: миграция накатывается, флаг выключен по умолчанию, changelog хода написан. Не путай DoD задачи и гейт Книги 2, Глава 9.

`ЕСЛИ задача не умещается в один проверяемый diff → разрежь по инварианту или по слою с контрактом между кусками → проверка: у каждого куска свой критерий; нет «часть 1 из 7 без границ».`

`ЕСЛИ критерий готовности сформулирован как «работает» → замени проверяемым фактом (тест, URL, инвариант, запрет регрессии) → проверка: человек может сказать да/нет без вкуса.`

1–3: очередь из 3–7 задач на срез. 10–30: задача ссылается на тикет/RFC человека. 100+: формат задачи = шаблон контура; не выдумывай параллельный трекер. Когда укрупнять: чисто механический рефактор с тестами. Когда нельзя: деньги, auth, удаление данных.

## 8.3. Порядок работ: что строится первым и почему (риск, ценность, зависимости)

Порядок трёх ключей, в этом старшинстве при конфликте запиши явную причину.

1. Риск. Сначала то, что может убить срез, если отложить: authn/authz граница, тенант, миграция данных, платёжный инвариант, «умеем ли мы вообще подключить провайдера X». Spike с выкидываемым кодом помечается throw-away (Книга 1, Глава 5, раздел 5.5). Не прячь риск в конец «когда будет UI».

2. Ценность. После снятого блокера — вертикальный кусок работы пользователя, не горизонтальный слой «все репозитории и все DTO». Книга 1, Глава 37, раздел 37.1: путь до первой ценности. Для агента это значит: один сценарий end-to-end на узком данных раньше красивой сетки сущностей.

3. Зависимости. Схема и контракт до толстых контроллеров (Книга 2, Глава 7, раздел 7.5 — не повторяй проектирование, исполни порядок). CI, линт, секрет-скан — до десятого файла, иначе самопроверка 8.6 врёт. Наблюдаемость каркаса (запрос id) — до выката, детали — Глава 9.

Запретный порядок. Сначала дизайн-система на 40 компонентов, потом смысл. Сначала Kubernetes, потом «hello». Сначала все CRUD, потом ACL. Сначала LLM-обвязка, потом источник истины данных.

`ЕСЛИ в очереди UI без модели данных и без auth при публичной регистрации → переставь: данные и субъект доступа раньше экранов → проверка: первая задача не «нарисуй лендинг», если гейт 7.7 требовал угрозы.`

`ЕСЛИ человек требует «сразу все сущности» → предложи одну сущность сценария гипотезы, остальные в cut → проверка: в итерации один вертикальный путь.`

Когда нарушить ценность ради риска: неизвестный платёжный провайдер, неизвестная миграция, неизвестный лимит стора. Когда не прятать ценность: внутренний инструмент без ПДн — сначала рабочий сценарий. Ошибка порядка: неделя инфраструктуры при красной гипотезе — это снова прыжок из Книги 2, Глава 6.

## 8.4. Реализация: правила написания кода, структура репозитория, конвенции, тесты

Не изобретай стиль проекта. Прочитай существующие конвенции, линтер, структуру каталогов. Нет конвенций — минимальный набор и запись в ADR «конвенции v1», не эссе о философии.

Структура. Монорепозиторий vs поли — Книга 1, Глава 23, раздел 23.1; для 1–3 по умолчанию один репозиторий, один деплой ядра, как в стиле этапа 3. Слои сервиса — Книга 1, Глава 17, раздел 17.1: конфигурация снаружи, домен без HTTP, тестируемость без сети. Фронт — Книга 1, Глава 19, раздел 19.1. Мобилка — Глава 20. Не смешивай слой в одном файле «потому что так короче сгенерировать».

Правила кода, которые агент исполняет всегда. (1) Имена и типы денег, времени, id — Книга 1, Глава 18, раздел 18.2; не float для денег. (2) Идемпотентность входящих команд, если повтор возможен (Книга 1, Глава 17, раздел 17.3). (3) Таймауты и бюджет времени на внешних вызовах (17.8). (4) Нет секретов, ключей, дампов ПДн в репозитории (Книга 1, Глава 24, раздел 24.6). (5) Миграции expand/contract, если схема живая (Книга 1, Глава 15, раздел 15.4) — не «DROP COLUMN в том же релизе, что убирает чтение». (6) Флаг на незаконченное (23.7).

Тесты в реализации — не этап 6 целиком, а плата за изменение. Минимум на задачу: тест на инвариант, который задача обещает, плюс регрессия, которую легко сломать. Пирамида и стратегия — Книга 2, Глава 9 и Книга 1, Глава 31. Здесь правило: нет теста на риск — задача не готова, даже если «вручную кликнулось в голове агента».

Trunk-based и маленькие изменения — Книга 1, Глава 23, раздел 23.2. Длинная ветка агента на неделю — антипаттерн 8.9. Коммиты атомарные, сообщения — зачем, не «fix». Хуки и CI — не обходи `--no-verify`; исключение только по явному приказу человека (это уже Книга 2, Глава 13).

`ЕСЛИ в репозитории есть линтер, форматтер, генератор клиентов → используй их, не пиши параллельный стиль → проверка: diff не воюет с CI формата.`

`ЕСЛИ генерируешь слой поверх существующего паттерна и паттерн ясен → следуй паттерну; не «улучшай архитектуру» в том же diff, что фича → проверка: одно намерение на изменение.`

Когда можно отступить от структуры: throw-away spike в отдельной ветке/папке с датой удаления. Когда нельзя: «временный» секрет в коде, «временный» обход ACL. На 2026 год де-факто агент работает в IDE с деревом файлов и тестами; принцип переживёт IDE: изменение проверяемо машиной до мнения человека.

## 8.5. Работа с существующей кодовой базой: разведка, карта, безопасные изменения

Легаси не читается целиком в контекст (бюджет — Книга 2, Глава 12). Разведка — поиск по символам, тесты, README, CI, последние коммиты по зоне, схема БД, переменные окружения. Выход разведки — карта на полстраницы: где инвариант, где вход, где данные, где опасно.

Карта. Модули и границы. Где деньги, сессии, персональные данные. Где уже есть тесты. Где «не трогать» по ADR или комментарию владельца. Закон Конвея в коде (Книга 1, Глава 41, раздел 41.1): не ломай чужой сервис «заодно».

Безопасное изменение. Сначала тест, воспроизводящий баг или фиксирующий текущее поведение. Потом узкий diff. Потом прогон затронутых тестов. Рефактор без изменения поведения — отдельный ход, не смешанный с фичей, если риск высок. Миграции — чек-лист Книги 1, Глава 15, раздел 15.7, если трогаешь живые данные.

Не делай. Глобальная перепись имён. Смена стека внутри фичи (Книга 1, Глава 16, раздел 16.8). Копипаста соседнего модуля без проверки инварианта. Удаление «мёртвого» кода, который кормит отчёт или легаси-клиента, без поиска ссылок.

`ЕСЛИ не найдена точка входа сценария за разведку → не пиши наугад, спроси человека путь или расширь поиск по тестам и маршрутам → проверка: в отчёте есть путь к файлу, который меняешь, и почему.`

`ЕСЛИ изменение касается платежей, ACL, удаления ПДн, миграции прод-схемы → сузь diff, добавь явный план отката, остановись по 8.7 если нет теста/бэкапа → проверка: нет широкого «почистил заодно».`

1–3: карта в `docs/code-map.md` коротко. 10–30: карта зоны владения. 100+: читай golden path и CODEOWNERS; не обходи ревью владельца. Когда не картировать час: файл, который человек указал, и тесты рядом зелёные. Когда обязательно: репозиторий новый для сессии.

## 8.6. Самопроверка изменений: сборка, тесты, линт, безопасность, ревью собственного кода

Агент не отдаёт diff, который сам не прогнал. Принцип самопроверки целиком — Книга 2, Глава 16; здесь — минимум этапа Implementation.

Порядок. (1) Сборка воспроизводится командой проекта, не «у меня в голове компилируется». (2) Затронутые тесты плюс узкий набор регрессии. (3) Линт и типы на затронутых путях. (4) Поиск секретов и ключей в diff. (5) Зависимости: не добавлен пакет с неизвестной лицензией и без причины (цепочка поставки — Книга 1, Глава 32, раздел 32.7, полнота — Глава 9). (6) Ревью собственного diff как чужого: инварианты, гонки, отсутствующий таймаут, лог ПДн (Книга 1, Глава 25, раздел 25.3). (7) Changelog хода: что сделано, что не сделано, как проверить руками.

Красный самотест — не маскируй пропуск теста, не правь тест «чтобы был зелёный», не отключай линт точечно без записи долга. Флейк — карантин с причиной (Книга 1, Глава 31, раздел 31.5), не retry в голове.

DORA (DORA, 2024) измеряет частоту поставки и стабильность после того, как есть пайплайн. Не цитируй «elite throughput», чтобы оправдать выкат без тестов. Change fail rate растёт, когда самопроверка театральная.

`ЕСЛИ сборка или тесты не запускались, потому что «среда сложная» → запусти минимальную команду проекта или скажи, какая именно команда не воспроизвелась, не утверждай зелёный → проверка: в отчёте есть команда и результат, либо явный блокер среды.`

`ЕСЛИ тесты упали → чини причину или сужай изменение; не удаляй assertion → проверка: assertion на инвариант на месте.`

Когда достаточно узкого прогона: крошечный typo в копирайте. Когда нет: auth, деньги, миграции, парсеры входа. Цена полной пирамиды на каждую запятую — время; цена нуля — регресс в проде. Баланс — риск среза.

## 8.7. Когда останавливаться и спрашивать человека

Остановка — не вежливость, а гейт цены ошибки (Книга 2, Глава 3, раздел 3.7; полный список — Книга 2, Глава 17). На этапах 4–5 спрашивай до действия, если:

- Гейт 7.7 красный, а просят код.
- Срез требует вырезать обещанную человеку фичу.
- Оценка p90 выходит за названный срок; нужен cut, не героизм.
- Легаси: нет карты, нет тестов, инвариант денег/ACL неясен.
- Нужен секрет, прод-доступ, миграция с риском данных, публикация пакета.
- Конфликт ADR и просьбы «сделай иначе в этом PR».
- Обнаружен ПДн-лог, дыра авторизации, или diff уже разросся за ревьюируемый размер.
- Человек просит обойти CI, линт, хуки.

Не спрашивай. Имя локальной переменной. Очевидный следущий шаг внутри уже подтверждённой задачи. Форматирование по линтеру. Спрашивать каждую строку — отказ от исполнения плана.

Формат вопроса: что решается, цена каждого варианта, умолчание, если человек молчит N часов — только если умолчание безопаснее стопа. Для денег и ПДн умолчание = стоп, не «закоммитим».

`ЕСЛИ цена ошибки высокая и человек недоступен → заморозь опасное, сделай безопасную часть среза или артефакт плана, не выдумывай прод-решение → проверка: в git нет миграции/секрета/опубликованного API без ack.`

`ЕСЛИ человек сказал «просто сделай» на пункте из списка остановки → запиши decision decided_by: human и риск, исполни минимум, не расширяй радиус → проверка: skip в состоянии; diff не вырос «заодно».`

1–3: частые короткие вопросы пакетом до пяти. 10–30: вопрос владельцу зоны, не «команде в чат без адресата». 100+: эскалация по runbook контура.

## 8.8. Артефакты: roadmap, бэклог, план итерации, changelog, отчёт о выполненном

Пять выходов, имена в репозитории, не проза чата. Шаблоны — Книга 1, Приложение B; оформление — Книга 2, Глава 15, раздел 15.7. Здесь — минимум этапа.

Roadmap. 3–5 вех, горизонты, что не обещано. Файл `docs/roadmap.md`. Не OKR-ритуал (Книга 1, Глава 38, раздел 38.4).

Бэклог. Упорядоченный список срезов и cut. Статусы: now / next / later / cut. Не бездонная доска. Источник приоритета — гипотеза и риск, не «ещё идея из чата».

План итерации. Задачи 8.2, порядок 8.3, DoD, владельцы (человек / агент), дата пересмотра cut. Объём: одна-две страницы.

Changelog хода. Что вошло в git, как проверить, какие тесты, какие долги. Это не маркетинговый changelog продукта. После запуска маркетинг — Книга 1, Глава 39; не путай.

Отчёт о выполненном. Закрытые задачи, красные самопроверки, вопросы 8.7, следующее. Человек должен суметь нажать «принять / вернуть / сузить» без чтения всего diff.

`ЕСЛИ stage двигают в implementation, а нет плана итерации с DoD → не коди, создай план → проверка: путь к файлу; критерии готовности на месте.`

`ЕСЛИ код слит, а changelog хода пуст → допиши до следующего запроса фичи → проверка: человек видит, как проверить и что вырезано.`

1–3: можно совместить roadmap+итерацию в одном файле. 10–30: раздельно, ссылка из тикера. 100+: артефакт = шаблон команды, плюс ссылка на книгу, не дубль.

## 8.9. Антипаттерны: правки наугад, игнорирование тестов, гигантские неревьюируемые изменения

Правки наугад. Проявляется: grep по имени, правка первого совпадения, «похоже на соседний файл». Почему: разведка не сделана, контекст не держит систему, давление демо. Чем заменить: карта 8.5, тест на поведение, узкий diff. Проверка: в отчёте путь и инвариант.

Игнорирование тестов. Проявляется: тесты не запускались; assertion ослаблен; новый код без теста на риск; «проверьте руками». Почему: среда, спешка, вера в генерацию. Чем заменить: 8.6, карантин флейка по 31.5, блокер среды назван честно. Проверка: команда и результат в отчёте.

Гигантские неревьюируемые изменения. Проявляется: один PR «весь каркас», смешение фичи и переписи, тысяча строк «инфраструктуры». Почему: дешевизна генерации, отсутствие нарезки 8.2. Чем заменить: задачи с границами, trunk-based 23.2, ревью 42.4. Проверка: человек способен просмотреть diff за один присест.

Смежные. Код на красном 7.7. Паритет-клон как v1. Горизонтальный CRUD вместо вертикального сценария. Смена стека «заодно». Обход хуков. Секрет в `.env.example` с реальным значением. Рефактор без тестов. Длинная ветка недели. Changelog только в чате. «Сборка зелёная», потому что тестов нет.

`ЕСЛИ в diff есть любой из трёх заголовочных антипаттернов → останови выдачу, разрежь или допиши тесты/разведку → проверка: человек не получает непросматриваемый комбайн.`

### Пример прогона

Человек: «Архитектуру утвердили, модульный монолит, Postgres, четверо, B2B-документы, к пятнице демо кабинету. Сделай всё: пользователей, шаринг, поиск, агента-юриста и деплой на k8s».

Агент: (1) Гейт 7.7 в YAML зелёный на монолит; k8s в ADR отвергнут — не воскрешать. (2) Stage=`delivery_plan`. План: v1 = загрузка документа тенантом и список своих документов; cut = шаринг наружу, поиск, агент, k8s. Критерий: пользователь тенанта A не видит файл тенанта B; демо на одном VM/managed. (3) Порядок: схема документ+ACL → регистрация по ADR → вертикальный сценарий загрузки → лог request-id → UI списка. Поиск и LLM — later, инновация уже в продукте не добавляется второй раз. (4) Задачи по 8.2 с тестом ACL. (5) После ack — implementation, разведка репо, узкие diff, сборка и тесты в отчёте. (6) В пятницу без шаринга: cut записан. Вопрос человеку только на «агент-юрист в демо» — отказ без threat model и стоимости токена. Кода k8s нет.
