# Глава 15. Производство артефактов

*Коротко. Артефакт — файл с владельцем и критерием приёмки, не простыня в чате. Без файла состояние не переживает сессию.*
*Каталог ниже: что обязательно на этапе, что можно сжать, что запрещено имитировать.*
*PRD, RFC, ADR, схемы, тест-план, threat model, SLO, runbook, постмортем, roadmap — разные жанры. Не мешай в один «док».*
*Имена, папка, версия, статус. Человек находит за минуту. Агент не плодит `final_v3_really.md`.*
*Перед выдачей — чек-лист 15.9. Красивый текст с выдуманными цифрами — брак.*
*Человеку глава — что требовать с агента на гейте. Агенту — как писать, куда класть, когда остановиться.*

Артефакты — выходы этапов Книги 2, Глав 6–10, в форме, которую читает следующий ход и другой человек. Содержание практик — Книга 1 (38.2 PRD, 10.7 RFC/ADR/C4, 31 тест-план, 32.1 угрозы, 26 SLO/runbook/постмортем, 38.4 roadmap). Эта глава не пересказывает Книгу 1. Она говорит, как агент производит эти документы: объём, поля, типовые дыры, хранение.

Провал. RFC на 40 экранов без салфетки. ADR «выбрали Postgres» без альтернативы. Threat model = список OWASP без субъекта. SLO «99.99» без SLI. Постмортем «больше не повторится». Roadmap = список желаний до 2029.

Команда 1–3: один каталог `docs/`, короткие шаблоны Приложения D. 10–30: те же файлы в git, ревью как код. 100+: шаблоны платформы; агент заполняет, не изобретает жанр.

## 15.1. Каталог артефактов и когда каждый обязателен

Обязательность привязана к гейту, не к желанию «быть взрослыми». Сжатый час (Книга 2, Глава 5, раздел 5.5) сокращает объём, не вычёркивает имя артефакта: пишется `lite`, с риском.

Discovery/Strategy. Обязательны: problem statement, список гипотез, constraints в состоянии. PR-FAQ — если есть спор «что обещаем рынку» (Книга 1, Глава 4, раздел 4.3). Экономическая модель — если платный канал или usage-себестоимость; иначе пометка «не считали». Не обязателен: полный TAM.

Architecture. Обязательны: салфетка 9.6, RFC среза, ADR стиля и стека. Схемы C4 контейнер+контекст на срез. Оценка cost per request порядка (Книга 1, Глава 22, раздел 22.6). Не обязателен: C4 code для каждого класса.

Delivery. Обязательны: roadmap на 3–5 вех, срез v1, cut list, критерии готовности, план итерации. Не обязателен: Jira на 200 тикетов.

Implementation. Changelog хода, карта зоны для легаси. Код — не «артефакт ради артефакта»; документ только если менялся контракт.

Quality & Security. Тест-план на риски среза, threat model, чек-листы 32.11/33.9 по типу, черновик SLO если идёте в прод, наблюдаемость 25.8. Без этого гейт 9.7 красный.

Launch/Growth. Launch plan, rollback, дерево метрик, план экспериментов если рост. Не обязателен: пресс-кит, если нет PR-волны.

Operations. Runbook на 2–3 отказа, incident notes в огне, постмортем после Sev, план масштаба только при данных о потолке.

`ЕСЛИ гейт требует артефакт, а в чате только абзац → сериализуй в файл по шаблону → проверка: путь в ответе; статус draft/review.`

`ЕСЛИ человек просит «все документы как в банке» на гипотезе concierge → откажи полный комплект, выдай problem+гипотезы+lite RFC «не строить» → проверка: нет SOC2-простыни до продукта.`

Trade-off полного каталога: недели бумаги, ноль пользователей. Trade-off нуля: каждая сессия заново выбирает стек. Ошибка: артефакт для галочки без полей 15.9.

## 15.2. PRD: структура, объём, критерии качества, типовые ошибки

PRD читают, чтобы нарезать срез, не чтобы восхититься видением. Якорь: Книга 1, Глава 38, раздел 38.2. Поля агента: проблема и чей JTBD; не-цели; пользовательские сценарии v1; метрика успеха и guardrail; constraints; срез и cut; открытые вопросы; риски. Объём: 1–3 экрана на фичу, до ~6 на продукт v1. Больше — это уже несколько PRD или RFC.

Критерии качества. Сценарий проверяемый. Метрика наблюдаемая. Cut список не пуст. Нет «удобный современный UX» как требования. Есть связь с `product-state.md`.

Типовые ошибки. Фичи вместо проблемы. Паритет с гигантом. Смешение PRD и RFC (экран + шарды в одном). Выдуманный TAM. Отсутствие done_when. Агент пишет PRD языком кода — фаундер не может сказать да/нет.

`ЕСЛИ PRD нельзя отвергнуть (нет cut и не-целей) → допиши not_this и cut → проверка: есть то, чего не делаем.`

`ЕСЛИ в PRD уже выбран Kafka и микросервисы → вынеси в RFC, оставь в PRD работу пользователя → проверка: PRD не содержит стека без NFR-причины.`

Когда PRD вреден: тикет на опечатку. Когда обязателен: новая пользовательская работа, спор о scope. 1–3: PRD = problem + сценарий + cut. 10–30: тот же файл для согласования. 100+: шаблон портфеля, агент не пишет PRD холдинга.

Объём против страха. Если не влезает в три экрана — вы уже смешали несколько срезов или RFC. Разрежь: один PRD на одну работу. Вложения (макеты, таблицы цен) — ссылками, не вставкой. Язык: фаундер должен суметь отвергнуть срез, не зная Kafka. Если отвергнуть нельзя — нет cut, чини 15.2 выше.

## 15.3. Технический дизайн-док (RFC): разделы, обязательные расчёты, альтернативы

RFC отвечает: как срез устроен, почему так, что ломается, сколько стоит порядок величины. Якорь: Книга 1, Глава 10, раздел 10.7; сборка этапа — Книга 2, Глава 7. Разделы агента: контекст и NFR; салфетка нагрузки/данных/денег; стиль и границы; данные и API; угрозы страницей; отказы и деградация; стоимость; альтернативы; план выката/миграции; открытые вопросы.

Обязательные расчёты. Хотя бы порядок: RPS, объём, cost per request или честный отказ считать при отсутствии входа (тогда вопрос человеку). Без салфетки RFC — картинка.

Альтернативы. Минимум две отвергнутых с причиной и `revisit_when`. «Не рассматривали» — дыра критика (Книга 2, Глава 11, раздел 11.5).

Объём. Срез v1: 2–6 экранов. Не энциклопедия всех будущих сервисов. Схемы — текстовые, 15.5.

`ЕСЛИ RFC без чисел 9.6 и без альтернатив → не отдавай на гейт 7.7, допиши → проверка: есть порядок нагрузки и две отвергнутых.`

`ЕСЛИ RFC описывает систему на 100× при 1–3 людях и 50 пользователях → срежь до модульного монолита, 100× в revisit → проверка: стиль стыкуется с 10.5.`

Когда не RFC: переименование. Когда нельзя сжимать в ноль: платежи, мультитеннант, AI-агент в продукте, миграция стораджа.

Critic RFC (11.5) бьёт четыре дыры в первую очередь: нет салфетки; нет альтернатив; стиль не стыкуется с 10.5; деградация = «упадём вместе». Если этих четырёх нет в красном списке и critic написал «ок» — прогон не засчитан. Автор чинит до гейта 7.7, не спорит тоном.

## 15.4. ADR: как фиксировать решения, чтобы к ним возвращались

ADR — одно неотменяемое решение, не дневник. Якорь: Книга 1, Глава 10, раздел 10.7; журнал — Книга 2, Глава 3, раздел 3.4. Шаблон: заголовок; статус `proposed|accepted|superseded`; контекст; решение; альтернативы; последствия; `revisit_when`. Имя файла: `NNNN-slug.md` в `docs/adr/`.

Пиши ADR, когда решение дорого менять: стиль, стек, ключ шарда, провайдер платежей, модель тенанта, «не делаем e2e шифрование». Не пиши на выбор отступа.

Возврат. Новый агент читает accepted, не чат. Смена — новый ADR со ссылкой superseded, не правка истории молча (гигиена Книги 2, Глава 12, раздел 12.8).

`ЕСЛИ в чате выбрали стек, а в docs/adr пусто → запиши ADR до кода против стека → проверка: путь; статус; альтернатива.`

`ЕСЛИ правишь accepted ADR так, что смысл перевернулся → создай новый, старый superseded → проверка: история решения читается.`

1–3: 5–15 ADR за год нормальнее нуля. 10–30: ревью ADR как код. 100+: номер в каталоге платформы. Ошибка: ADR-простыня «вся архитектура».

## 15.5. Архитектурные схемы в текстовом виде: нотация, уровни C4, читаемость

Рисуй текстом: ASCII или списки узлов и рёбер. Человек и агент grep'ают. Якорь C4: Книга 1, Глава 10, раздел 10.7. Уровни: Context (кто с системой), Container (процессы/сторы), Component на спорный кусок. Code-уровень агенту обычно не нужен.

Нотация. Имя узла, ответственность, данные в покое, синхрон/очередь. Стрелка: протокол и что ломается, если её нет (деградация, Книга 1, Глава 12, раздел 12.4). Ключ изоляции подпиши. Секреты и ПДн пометь.

Читаемость. До ~15 узлов на схему. Две схемы лучше одной каши. Запрещены украшения, эмодзи, «микросервис» без процесса.

`ЕСЛИ схема не называет ключ изоляции и единицу стоимости → допиши или признай, что это не архитектура → проверка: можно прочитать shard/tenant key.`

`ЕСЛИ в схеме 40 сервисов у команды 1–3 → это не схема продукта, срежь до исполняемого → проверка: узлы ≤ того, что кто-то дежурит.`

Когда схема обязательна: RFC, публичный API, платежный контур. Когда достаточно списка модулей монолита: внутренний CRUD. Не вставляй диаграмму Netflix.

## 15.6. Тест-план, threat model, SLO-документ, runbook, постмортем

Пять жанров, пять ошибок, если склеить.

Тест-план. Риски среза → уровень теста → что ловит (Книга 1, Глава 31). Не «покрыть 80%». Обязательны инварианты ACL, денег, миграции. Для 1–3 — минимум 31.10.

Threat model. Субъекты, активы, вход, злоупотребления, контроль, что сознательно не закрыто (Книга 1, Глава 32, раздел 32.1). Не копипаст STRIDE без субъекта. AI-вход — ещё 30.6.

SLO. SLI, цель, окно, источник измерения, error budget, что делаем при выгорании (Книга 1, Глава 26, раздел 26.1). Запрещён 99.99 без измерения и без цены. Черновик на первый прод допустим с пометкой `unmeasured`.

Runbook. Симптом → проверка → действие → эскалация. 2–3 отказа: 5xx, зависимость, ошибка выката. Не роман архитектуры.

Постмортем. Без обвинений: что видели, таймлайн, контрибуторы, действия с владельцем и датой (26.5). «Будем внимательнее» — не действие.

`ЕСЛИ threat model не содержит субъекта и актива → не засчитывай гейт 9.7 → проверка: есть «кто» и «что крадут/ломают».`

`ЕСЛИ SLO без SLI и без дашборда/лога → пометь unmeasured, не обещай SLA клиенту → проверка: нет числа из воздуха.`

Когда lite: внутреннее демо. Когда полный: деньги, ПДн, публичный запуск. Шаблоны — Приложение D.

## 15.7. Roadmap, бэклог, план итерации, план экспериментов

Roadmap — горизонты сейчас / цикл / позже плюс обязательства и не-обязательства (Книга 1, Глава 38, раздел 38.4). 3–5 вех. Каждая веха: пользовательская работа + инвариант. Не Гант на 18 месяцев.

Бэклог — очередь срезов с причиной, не склад идей. Идеи без гипотезы — в `later` или удалить.

План итерации — выбранный срез, задачи агента с границами (Книга 2, Глава 8, раздел 8.2), DoD, cut, кто человек на гейте.

План экспериментов — гипотеза, метрика, guardrail, размер/длительность или качественная альтернатива при малом трафике (Книга 1, Глава 28). Нет north_star — сначала дерево метрик, не закупка (Книга 2, Глава 10).

`ЕСЛИ roadmap обещает паритет гиганта в v1 → вырежи в later, оставь гипотезу → проверка: v1 проверяем, не клонируем.`

`ЕСЛИ план эксперимента без guardrail → добавь «что не должны сломать» или не запускай канал → проверка: есть стоп-условие.`

1–3: один файл `docs/plan.md` на все четыре, секциями. 10–30: разнести. 100+: агент не публикует корпоративный roadmap.

Эксперимент без события активации в коде — план в стол. Сначала инструментация 28.3 Книги 1, потом канал. Roadmap без cut врёт срок так же, как PRD без not_this: нельзя отказаться от работы, значит объём бесконечен.

## 15.8. Правила именования, хранения и версионирования артефактов

Корень: `docs/`. Подкаталоги: `adr/`, `rfc/`, `prd/`, `security/`, `sre/`, `plans/`. Имена: `YYYY-MM-DD-slug.md` или `NNNN-slug.md` для ADR. Без `final`, `new`, `copy`. Язык slug — английский ASCII, заголовок внутри — русский.

В шапке каждого файла: тип, статус `draft|review|accepted|deprecated`, дата, `product_id`, ссылки на связанные ADR/PRD. Статус дублируется в `product-state.md` путями, не копией текста.

Версии. Git — единственная история. Не храни `rfc_v2.md` рядом, если можно заменить и сослаться. Существенное изменение accepted RFC — либо новая ревизия с changelog вверху, либо новый файл и deprecated старому.

Секреты и ПДн в артефактах запрещены (Книга 2, Глава 13, раздел 13.7). Примеры — фиктивные.

`ЕСЛИ артефакт живёт только в чате после гейта → запиши в docs/ до конца хода → проверка: git видит файл; путь в резюме.`

`ЕСЛИ два файла претендуют на одну истину (два RFC стиля) → пометь один deprecated, в состоянии один путь → проверка: нет вилки без статуса.`

Когда вынести из репо: юридические заключения, сырые ПДн интервью. Тогда в состоянии — указатель «вне репо, владелец человек», не содержимое.

## 15.9. Чек-лист качества артефакта перед выдачей человеку

Прогони на каждый документ гейта. Критик (11.5) использует этот список.

1. Тип жанра один. Нет PRD+RFC+бюджет в каше без секций.
2. Статус и дата есть.
3. Поля шаблона заполнены или явно `n/a` с причиной.
4. Цифры: источник и год, либо «порядок / не считали». Нет украшенных TAM.
5. Альтернативы на неотменяемом решении.
6. Связь с YAML: сегмент, stage, constraints не противоречат.
7. Якоря Книги 1 на нормах, не на каждом предложении.
8. Нет секретов и живых ПДн.
9. Схема читается без картинки-хостинга.
10. Cut/revisit_when/открытые вопросы не пусты, если жанр их требует.
11. Человек может сказать да/нет за пять минут на резюме сверху.
12. Critic нашёл дыры или записал, какие три искал.

`ЕСЛИ пункт 4 красный → вычисти цифру или пометь допущением до выдачи → проверка: нет голого миллиарда рынка.`

`ЕСЛИ артефакт хвалебный без красных пунктов → прогони критика, не отдавай → проверка: есть конкретные дыры или карта поиска.`

Сжатие: lite помечается в статусе. Нельзя сжать пункт 4 и запрет секретов.

Дополнительно перед выдачей. Имя файла по 15.8. Связанные ADR не противоречат тексту. Человек из другой сессии поймёт статус без чата. Если артефакт для внешней аудитории (питч) — не подменяй им RFC: два файла, питч ссылается на draft, не наоборот. Critic на питче ищет выдуманные цифры в первую очередь.

`ЕСЛИ человек просит «один красивый PDF на всё» → сделай резюме 14.1 сверху и приложи пути канонических файлов, не склеивай жанры в неверсионируемый бинарь → проверка: git видит md; PDF если нужен — производное.`

### Пример прогона

Человек: «Напиши полноценный PRD, RFC, threat model и SLO 99.99, завтра питч, продукта нет».

Агент: (1) Каталог 15.1: обязательны problem, гипотезы, lite RFC; SLO 99.99 без измерения — брак 15.6. (2) PRD: одна работа сегмента, cut «не клон Notion», метрика качественная на 2 недели. (3) RFC lite: модульный монолит, салфетка «неизвестно, порядок <100 RPS», альтернатива serverless отложена. (4) Threat lite: публичный вход, сессия, IDOR. (5) SLO: `unmeasured`, предложить availability после логов, не обещать 99.99 инвестору. (6) Файлы в `docs/` со статусом draft. (7) Critic: нет интервью — assumption в YAML. Питч-обёртка — резюме 14.1, не четвёртый жанр «презентации вместо фактов».

## Чек-лист главы

Каталог и жанр

- [ ] Артефакт этапа назван и лежит в docs/
- [ ] Жанр не смешан без секций
- [ ] Lite помечен, если сжатие
- [ ] Гейт не закрыт чат-абзацем

Качество полей

- [ ] PRD: проблема, cut, done_when
- [ ] RFC: салфетка, альтернативы, деградация
- [ ] ADR: статус, revisit_when, один decision
- [ ] Threat: субъект и актив
- [ ] SLO: SLI и источник или unmeasured
- [ ] Постмортем: действия с датой

Хранение

- [ ] Имя и статус по 15.8
- [ ] Нет секретов
- [ ] 15.9 прогнан, критик не хвалил вхолостую

## Антипаттерны

Простыня в чате — RFC умер после сессии — лень сериализовать — 15.8.

Каша жанров — PRD со шардами — один файл «на всё» — 15.1–15.3.

Цифра-украшение — TAM $12B — питч — 15.9 п.4.
