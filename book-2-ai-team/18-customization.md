# Глава 18. Донастройка: как человек адаптирует книги под себя

*Коротко. Книги — слой по умолчанию. Компания и проект имеют право сказать «у нас иначе», письменно и с причиной.*
*Слои: книга → отрасль → компания → проект. Конфликт разрешает приоритет, не громкость чата.*
*Исключение — фраза «у нас иначе, потому что…» плюс срок пересмотра. Не молчаливый skip навсегда.*
*Локаль: регион, закон, язык, сторы, платежи. Overlay без региона врёт на ПДн.*
*Версии playbook совместимы с принятыми ADR: смена главы не переписывает историю молча.*
*Постмортем → правило → eval. Иначе книга в репо, а агент повторяет ту же дыру.*
*Человеку глава — как внедрить книги без культа. Агенту — какой файл бьёт какой.*

Донастройка — законный способ не притворяться универсальным стартапом из примеров. Книга 1, Глава 1, раздел 1.4 даёт маршруты чтения людям. Книга 2, Глава 12, раздел 12.7 — skills как каркас. Эта глава — приоритеты, исключения, версионирование, как добавить главу так, чтобы агент её подхватил.

Провал. В Notion «у нас запрещён AWS us-east-1», агент всё равно кладёт туда, потому что книга молчит, а overlay не в репо. Второй: юрист запретил определённый трекинг, агент каждый раз спорит по Главе 39. Третий: скопировали 46 глав в rules IDE, они разошлись с `book-1-guidebook/` (антипаттерн 12.7).

Команда 1–3: один `docs/playbook-overlay.md`. 10–30: overlay + ADR процесса. 100+: внутренний стандарт как слой компании, книги — дефолт где стандарт молчит.

## 18.1. Слои знаний: книга → отраслевые дополнения → правила компании → правила проекта

Слой 0. Сообщение человека в этой сессии: задача и явный skip. Не отменяет закон и запреты 17.6.

Слой 1. Книга 1 — как строить продукт. Книга 2 — как агент работает. При конфликте «как строить» vs «порядок работы» — см. промт: Книга 1 на норму продукта, Книга 2 на ритуал агента.

Слой 2. Отрасль: medtech, fintech, игры, госсектор. Отдельные файлы `docs/overlay-industry.md`: PCI, клинические данные, античит, гос-облако. Не вписывать в Книгу 1 вилкой.

Слой 3. Компания: запретные вендоры, golden path, брендовые гейты, «мы не берём Kubernetes до N».

Слой 4. Проект: этот `product_id`, этот легаси, этот регион.

Агент читает сверху вниз для факта «что делать», но приоритет при конфликте — 18.2, не «последний прочитанный файл». Держать слои короткими: принцип 12.7, каркас не вторая книга.

`ЕСЛИ правило живёт только в чате или Slack → сериализуй в overlay проекта, иначе следующая сессия забудет → проверка: путь в git; YAML ссылается.`

`ЕСЛИ overlay копирует главу Книги 1 целиком → замени указателем на раздел + дельтой → проверка: нет второй 32-й главы с устаревшим пунктом.`

Когда слой отрасли не нужен: обычный B2B SaaS без спецрегуляторики — хватит 3–4. Когда нужен до кода: платежи, здоровье, дети, крипто (часто стоп 17.6 + юрист).

## 18.2. Приоритет источников при конфликте

Порядок старшинства (жёсткий):

1. Закон и явный запрет вреда (17.6). Нельзя overlay «нам можно без согласия».
2. Явная инструкция человека на этой задаче после предупреждения о риске — на всём, кроме п.1 и forbid-инструментов.
3. Overlay проекта (слой 4).
4. Overlay компании (слой 3).
5. Overlay отрасли (слой 2).
6. Книга 1 на норму продукта; Книга 2 на порядок агента.
7. Веса модели и «как обычно в интернете».

Запись конфликта обязательна: что столкнулось, что победило, `revisit_when`. Молчаливая победа весов — дрейф 16.5.

Пример. Книга 1, Глава 16 советует скучный Postgres. Компания: «только Aurora в нашем аккаунте». Побеждает компания, ADR стека ссылается на overlay. Пример 2. Книга 37 хочет короткий онбординг. Overlay: обязательный KYC. Побеждает overlay+закон, UX сужается, не выкидывается KYC.

`ЕСЛИ два overlay противоречат → выше слой проекта над компанией только если проект явно наследует исключение; иначе эскалация человеку → проверка: нет усреднения.`

`ЕСЛИ человек просит нарушить п.1 → отказ по 14.6/17.5, не «приоритет человека» → проверка: нет diff обхода закона.`

1–3: человек ≈ компания ≈ проект, всё равно пиши файл. 10–30: без файла агент выберет книгу против неписаной нормы, и это будет правильно формально и неправильно политически.

## 18.3. Как вносить исключения: «у нас иначе, потому что…»

Шаблон исключения в overlay:

- Правило книги: `Книга 1, Глава N, раздел N.M` / гейт Книги 2.
- Иначе: что делаем.
- Потому что: ограничение факта (не «нам так нравится» без NFR — тогда это вкус, не overlay).
- Цена: чем платим.
- Срок: дата или метрика `revisit_when`.
- Владелец-человек.
- Skip гейта: да/нет; если да — риск в YAML.

Примеры годных. «Не шардируем, потому что RPS < X по салфетке, revisit 10×». «Нет публичного API, потому что один клиент, revisit второй клиент». «Kubernetes запрещён до platform-команды».

Примеры негодных. «Безопасность потом». «Тесты не пишем, культура такая». «Секреты в репо, так исторически». Это не overlay, это красный риск; агент каждый раз предупреждает.

`ЕСЛИ исключение без «потому что» и без revisit → не принимай как overlay, спроси причину или трактуй как одноразовый skip → проверка: в файле есть срок.`

`ЕСЛИ исключение отменяет 32.11 целиком → откажи в записи overlay, предложи сужение пунктов с компенсацией → проверка: нет mute на IDOR.`

Когда исключение уместно: масштаб 1–3 против практик 100+. Когда нет: вечный skip privacy. Агент может предложить черновик исключения, человек подписывает владельцем.

## 18.4. Локальный контекст: регион, регуляторика, язык, платформенные особенности

Поля, которые overlay и YAML обязаны согласовать: страны резидентства пользователей и компании; языки UI и поддержки; сторы (RU/EU/US политики разные и стареют — 17.3); платёжные методы; где лежат данные; гособлако да/нет.

Агент не выводит «если язык русский, значит 152-ФЗ закрыт баннером». Открывает Книга 1, Глава 33, раздел 33.1, overlay юриста, спрашивает.

Платформа. Мобилка: 20.7 сторы ломают планы — overlay «не обещаем фичу, пока гайд не сверен». Китай/Индия/Бразилия — отдельные платежи и сторы, не копипаст US-RFC.

Язык артефактов. Если команда русская — docs на русском, идентификаторы кода как в репо. Overlay фиксирует. Не переключай язык книги цитат.

`ЕСЛИ region пуст, а фича трекает пользователей или хранит ПДн → стоп-вопрос, не US-default → проверка: в YAML region или assumption с риском.`

`ЕСЛИ overlay компании US-only, а продукт выходит в ЕС → конфликт 18.2, эскалация, не тихий дубль региона в том же кластере → проверка: данные и право названы.`

1–3 часто один рынок — всё равно запиши. 10–30: локализация как процесс (Книга 1, Глава 36), overlay указывает i18n-библиотеку. 100+: legal packs по рынкам, агент не изобретает.

## 18.5. Версионирование playbook и совместимость с предыдущими решениями

Книги живут в git. Версия = тег или дата `playbook_version` в YAML состояния. Агент на старте читает версию, с которой писались ADR.

Совместимость. Смена главы Книги 1 не делает accepted ADR недействительным. Появляется задача ревью: «раздел изменился, решение ещё держим?». Не массовый rewrite стека.

Правило миграции overlay. При обновлении книг: diff overlay против новых номеров разделов (12.7: не хранить мёртвые номера). Сломанная ссылка 10.9 после сокращения toc — баг overlay.

Две книги обновляют согласованно, если меняется гейт. Нельзя обновить Книгу 2 «нельзя релизить без SLO», оставив в overlay проекта mute навсегда без revisit.

`ЕСЛИ playbook обновили, а overlay ссылается на несуществующий раздел → почини overlay до советов «по книге» → проверка: grep номеров по toc.`

`ЕСЛИ новая книга противоречит accepted ADR → не ломай прод, заведи вопрос revisit, не silent switch → проверка: ADR статус прежний до решения человека.`

Когда форсировать смену: дыра безопасности в старой рекомендации. Когда нет: вкусовщина 16-й главы про фреймворк года.

Совместимость артефактов. RFC accepted на монолит остаётся нормой, пока человек не supersede. Агент после обновления книги не переписывает RFC «под новую моду». Делает список расхождений: «глава 10 теперь сильнее бьёт по X, наше ADR всё ещё держится потому что headcount=8». Это и есть миграция playbook без миграции продукта.

Тег. `playbook_version: 2026-08-15` или git-sha книг в YAML. Сессия без версии после обновления книг — первый ход: прочитать changelog книг, не сразу новый стиль.

## 18.6. Обучение на собственных ошибках: превращение постмортема в правило

Цепочка. Инцидент или дыра на ревью → постмортем (26.5) или короткая заметка агента → один пункт overlay или skill → золотой eval (16.4) → больше не повторяем.

Примеры. Агент закоммитил `.env` → skill «секрет-скан до commit» + eval. Агент предложил микросервисы команде из двух → overlay «стиль по умолчанию = модульный монолит, 10.5». Injection из issue → 13.4 в rules IDE.

Не превращать в правило. Одноразовый вкус. Ошибку человека вне агента без технического контроля. «Больше не использовать LLM» как вывод из одной галлюцинации — слишком широко; сузь: «сверять API с докой».

`ЕСЛИ постмортем без пункта overlay/eval → на следующем похожем ходе дыра повторится; допиши правило в том же цикле → проверка: файл правила и кейс.`

`ЕСЛИ правил стало больше, чем читается за минуту → слей дубли, оставь гейты; остальное skills по этапу (12.7) → проверка: слой 4 короткий.`

1–3: эта цепочка заменяет отдел качества агента. 10–30: ревью overlay как код. 100+: не плодить уникальные правила каждого сервиса против golden path без причины 18.3.

## 18.7. Как расширять Книгу 1: формат новой главы, чтобы агент её подхватил

Человек (или агент по заказу) добавляет главу только в структуре книг. Иначе маршрутизация 4.2 её не найдёт.

Обязательно. Запись в `book-1-guidebook/00-toc.md` с номерами `N.M`. Файл `NN-slug.md`. Контракт `docs/01-style-guide.md`: Коротко, механика, чек-лист, антипаттерны, объём. Якоря из существующих глав, без дубля. Цифры с годом.

Подхват Книгой 2. Строка в таблице маршрутизации Приложения A (YAML). При необходимости роль в реестре 11.2. Skill-указатель, если гейт новый. Индекс дверей 2.4: номер чек-листа.

Не расширение Книги 1. Вставить норму только в системный промт. Slack-сообщение. PDF вне репо без toc.

`ЕСЛИ новая глава есть в файле, но нет в toc и в YAML маршрута → агент её не обязан найти; допиши индекс → проверка: триггер из 4.2 ведёт к файлу.`

`ЕСЛИ «глава» без чек-листа и без номеров разделов → это эссе, не playbook; агент не ссылается как на Книгу 1 → проверка: контракт стиля выполнен.`

Отраслевую книгу лучше держать слоем 2, не вшивать в универсальную Книгу 1: иначе 1–3 читают PCI в трекере привычек.

Минимальный скелет новой главы, который агент подхватывает без догадок. Заголовок `# Глава N. …` как в toc. Разделы `## N.M`. Хотя бы один чек-лист `- [ ]`. Хотя бы один скрипт `ЕСЛИ` если это Книга 2, или фреймворк если Книга 1. Блок «когда не применять». Без этого маршрутизатор найдёт файл и процитирует эссе как норму — хуже, чем «главы нет».

Триггер в Приложении A: `id`, `match` (фразы человека), `stage`, `book1_chapters`, `checklists`, `roles`. Пустой `match` не добавляйте: будет ложный захват. После добавления — eval: запрос с новой фразой открывает новую главу, старый запрос «просто код» всё ещё стопит.

## 18.8. Чек-лист внедрения книг в команде

Внедрение — работа людей плюс файлы, не «скинули PDF в чат».

1. Книги в репозитории, не только в головах. Пути в rules IDE.
2. `product-state.md` заведён на каждый живой продукт.
3. Overlay компании/проекта существует, хотя бы с регионом и запретами вендоров.
4. Приоритет 18.2 прочитан техлидом и тем, кто ставит промт.
5. Гейты 6.7/7.7/9.7 не выключены mute без 18.3.
6. Секреты и прод-доступ агента ограничены (Глава 13).
7. Один золотой eval на стоп «код без problem».
8. Формат ответа 14.1 принят как норма PR/тикета.
9. Владелец обновления книг назван. Версия в YAML.
10. Первый постмортем агента превращён в правило (18.6).
11. Команда знает, что «сотня инженеров» = Глава 11, не N процессов.
12. Юрист/security знают, куда писать overlay, не в Slack.
13. Сжатый режим 5.5 согласован: что можно lite.
14. Через две недели ревью: агент ссылается на реальные номера, YAML не пустой.

`ЕСЛИ внедрение = только system prompt без файлов книг → ожидай дрейф и галлюцинации разделов; положи книги и toc → проверка: агент открывает файл главы.`

`ЕСЛИ через месяц overlay пуст, а «у нас иначе» звучит каждый день → сериализуй или перестань говорить иначе → проверка: исключения в git.`

Масштаб. 1–3: пункты 1–7 за день. 10–30: ещё согласование golden path. 100+: книги не заменяют внутренний стандарт, а дефолтят дыры стандарта.

Две недели спустя — живой аудит, не опрос «понравилось». Откройте три случайных сессии агента. Есть ли YAML. Есть ли якорь на значимом решении. Был ли стоп на красном. Есть ли секрет в diff. Если нет YAML — внедрение театральное. Если якоря-призраки — не открывается toc. Если не было ни одного стопа на опасных просьбах — права слишком широкие или компакт вырезан.

Не внедрять «всем инструментам сразу»: один контур (IDE продукта) до зелёных evals, потом поддержка, потом чат маркетинга. Иначе overlay разъедется.

### Пример прогона

Человек: «Мы fintech в ЕС, внутренний стандарт запрещает собственные очереди, только vendor X, и не цитируй ваши книги при клиенте. Обнови агента».

Агент: (1) Overlay отрасли+компании: PCI/ПДн ЕС, очереди = X, регион. (2) Приоритет: закон > overlay > Книга 1 Глава 11 про очереди; ADR «брокер = X», revisit если vendor lock критичен (16.5 Книги 1). (3) Коммуникация 14.4: клиенту — без номеров книг; внутренние RFC — якоря остаются. (4) Исключение 18.3: не самописный брокер, потому что compliance, цена lock-in, revisit ежегодный. (5) Маршрут 4.2 не меняется: threat model всё равно 32. (6) Eval: запрос «подними Kafka» должен стопиться overlay. YAML `playbook_version` + пути overlay.
