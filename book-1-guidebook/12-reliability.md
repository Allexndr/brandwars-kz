# Глава 12. Надёжность и отказоустойчивость

*Коротко. Надёжность — поведение при отказе, не процент аптайма в слайде. Глава про классы поломок, изоляцию blast radius, защитные механизмы, деградацию, цену мультизоны, бэкапы, которые восстанавливали, и chaos без суицида.*

*SLO, error budget, дежурства, роли инцидента и постмортемы — Глава 26. Здесь не повторяем процесс SRE. Production readiness в 12.8 — технические ворота; политика «можно ли релизить при дырявом бюджете» — там.*

*AWS формулирует изоляцию так (Well-Architected REL10-BP03, 2023): лучше 5% клиентов со 100% отказа, чем 100% клиентов с 5%. Dean & Barroso (2013) остаются базой хвостов: hedge через 10 мс на BigTable снизил p99.9 с 1 800 мс до 74 мс при +2% запросов.*

*Читать после 9 и 11: без таймаутов и профиля нагрузки breaker некуда ставить. Мультирегион без drill — гипотеза, не свойство.*

Отказ — штатный вход. Диск, зависимость, деплой, человек, автоматика. AWS us-east-1 19–20 октября 2025: латентная гонка в DNS-автоматике DynamoDB оставила пустую запись endpoint; каскад на EC2, Lambda, Fargate, NLB пережил первопричину. Автоматика восстановления сама была источником. Урок в playbook: kill switch на глобальные планы, velocity control на снятие ёмкости, не надеяться, что «failover встроен».

Надёжность покупается ёмкостью, изоляцией и репетицией, не лозунгом. Netflix держит tier-0 около 30% утилизации, best-effort 60–70% (re:Invent 2025). Это плата за эвакуацию. Команда из трёх не держит 30% — она держит проверенный бэкап, таймауты и деградацию «поиск отключён, заказ жив».

Для 1–3: таймауты, ретраи с jitter на одном уровне, бэкап с restore, fail-open на некритичном. Для 10–30: bulkhead на зависимости, shed, multi-AZ на стейтфул, game day раз в квартал. Для 100+: клетки, hedged requests с token bucket, мультирегион только со сценарием и drill.

## 12.1. Классы отказов и модель «что сломается первым»

Классифицируйте до диаграммы. Разные классы лечатся разным.

**Ресурс узла.** OOM, диск 100%, fd, CPU saturations. Симптом: всё на инстансе. Лечение: лимиты, shed, автоскейл по правильной метрике. Не лечится ретраями — ретраи ускоряют смерть.

**Зависимость.** БД, платежи, DNS, сторонний API. Симптом: ваш CPU низкий, p99 высокий или 5xx. Лечение: таймаут, bulkhead, degrade, не общий пул.

**Сеть и разделение.** Потеря пакетов, split brain, «полуживой» линк (latency, не down). CAP/PACELC (Глава 11.5) — про этот класс. Лечение: таймауты важнее бесконечного hung; кворум; не синхронный кросс-регион в клике.

**Деплой и конфигурация.** ~70% аварий связаны с изменениями (оценка Google SRE Workbook — аргумент для error budget, не ваша статистика). Плохой билд, флаг, «применили конфиг на весь флот». Multi-AZ не спасает: код едет во все зоны. Лечение: canary, клетки, progressive delivery (Глава 23) — здесь только вывод: изоляция деплоя ≠ изоляция железа.

**Ядовитый запрос / hot key.** Один payload кладёт воркер; одна комната кладёт партицию. Лечение: лимиты размера, isolation, coalescing, ban ключа.

**Каскад.** Ретраи × слои, retry storm, reconnect storm (Slack: 100K клиентов), потеря back pressure (Discord). Каскад переживает первопричину (us-east-1 2025). Лечение: один уровень ретраев, jitter, load shedding, velocity control.

**Автоматика.** DNS planner применил устаревший план. Chaos без стоп-крана. Backup job, который дропает. Лечение: kill switch, идемпотентность job, не применять план старше эпохи.

**Данные.** Тихая порча, ошибочная миграция, restore, который не проверяли. RPO/RTO без drill — гипотеза (12.6).

Модель «что первым»: возьмите пользовательский сценарий, выпишите hard-зависимости, посчитайте потолок доступности как произведение (арифметика — Глава 2.2 и 26.1). Что с наименьшим SLO или с наибольшим blast radius — то и чинить первым. Для 1–3 первым обычно бывают: диск БД, забытый бэкап, таймаут 30 с, секрет в git. Для 100+: корреляция зон через control plane.

Пример. B2B SaaS, сценарий «создать счёт и списать карту». Hard-зависимости: Postgres (ваш SLO ещё не задан), Stripe (публичный статус не ваш), DNS, исходящая почта. Почта — не hard: счёт существует без письма. Stripe — hard на списании, не на просмотре счёта. Если поиск по счетам и списание делят пул соединений, отказ поиска (тяжёлые LIKE) кладёт оплату — это класс «зависимость + отсутствие bulkhead», не «Stripe упал». Первым чинить пул и таймаут поиска, не рисовать второй регион.

Второй пример. Consumer-лента, fan-out 40 внутренних чтений. Класс «хвост»: p99 листа 80 мс при 40 листьях даёт заметный шанс медленного ответа (математика Dean & Barroso, Глава 9.1). Первым чинить hedge/coalesce на горячем ключе, не добавлять AZ. AZ не лечит коррелированный хвост GC на всех репликах одной версии бинарника.

## 12.2. Изоляция: bulkhead, cell-based, quota, приоритезация трафика

Blast radius — сколько пользователей/тенантов затрагивает один отказ. Цель — сузить, не «добавить реплик того же общего стейта».

**Bulkhead.** Лимит конкурентности на зависимость. Медленный поиск не съедает пул оплаты. Отдельные пулы потоков/соединений/семафоры (Глава 9.5). AWS: dependency isolation как потолок inflight на каждую зависимость. Порядок эскалации перегруза: adaptive concurrency limit → приоритетный shed → degrade → отказ.

**Quota.** Per-tenant, per-API-key, per-cell. Token bucket на входе (Stripe/GitHub/AWS — дефолт публичных API). Fail open в rate limiter: недоступный Redis лимитера не должен стать отказом, который лимитер предотвращал (двухуровневая схема: локальный бакет + Redis, дрейф 5–10%, fail open). DynamoDB: throttle на горячем item при таблице на 5% — честность важнее среднего.

**Приоритезация.** Интерактивный запрос важнее аналитического, оплата важнее рекомендаций, write path важнее «похожее». При нехватке слотов shed с хвоста приоритета. Без приоритетов shed бьёт случайно — часто по самому ценному, потому что он тяжелее.

**Клетки.** Полные копии системы, маршрутизация по partition key (Глава 10.4, AWS whitepaper сентябрь 2023). Изолируют деплой, poison pill, шумного соседа — то, что едет с кодом во все AZ. Правила, которые ломают чаще всего: общая БД/Redis между ячейками; роутер сложнее ячейки; пайплайн деплоит все клетки сразу; размер не нагружали. Shopify pods — клеточный паттерн на datastores: unit of work в один под, Sorting Hat, Ghostferry для переноса магазина. Shuffle sharding (Route 53: 2 048 виртуальных NS, шард из 4) — ортогонально: клиент получает случайное подмножество, пересечения малы.

Когда клетки рано: нет ключа партиции, команда <30, control plane вы не умеете дублировать. Когда квота рано: никогда не рано на публичном API и на тяжёлом тенанте. Сигнал ошибки: падение поиска кладёт checkout; падение одного шарда требует job по всем шардам.

## 12.3. Защитные механизмы: circuit breaker, retry с jitter, hedged requests, load shedding

Четыре инструмента, которые путают. Порядок внедрения: таймаут → jittered retry на одном уровне → token bucket на ретраи → shed → hedge с адаптивным порогом. Circuit breaker — не первый.

**Таймаут.** Connection + request на каждый удалённый вызов, включая localhost RPC (Amazon Builders' Library). Слишком короткий → storm. Слишком длинный → занятые слоты. Вписать в бюджет Главы 9.

**Retry + jitter.** Capped exponential backoff. Без потолка 10 ретраев 2^n ≈ полчаса. Без jitter все просыпаются вместе. Full Jitter: `sleep = random(0, min(cap, base * 2^attempt))` — меньше работы (AWS Architecture Blog). Decorrelated сопоставим; Equal проигрывает. Ретраить один уровень стека: иначе множители. Три слоя по 3 попытки = до 27 вызовов на один пользовательский клик, пока зависимость уже мертва. Adaptive retries (AWS SDK): retry quota на token bucket — успех возвращает 0,1 или 0,01 токена, то есть 1 ретрай на 10–100 успехов; скорость падает при throttle. Jitter нужен cron и «всем в 4:00» — иначе вы сами планируете шторм. Для одного хоста джиттер детерминированный, чтобы инцидент читался. Ретрай только на идемпотентном или на чтении; POST без ключа — сначала ключ, потом повтор (Глава 11.7, 17.3).

**Circuit breaker.** После порога ошибок «открыть» и не звать зависимость. AWS явно: CB вносит модальное поведение, плохо тестируется, может удлинить восстановление. Предпочтение Builders' Library — локальный token bucket на ретраи. CB уместен, когда зависимость точно down и дешёвый fail-fast лучше hung (rpc-proxy VK: код сразу знает, что движок мёртв). Не ставьте CB первым «потому что Netflix».

**Hedged / tied requests (Dean & Barroso, CACM 2013).** Дубликат в другую реплику после порога, взять первый, отменить остальные. Канон: 1 000 ключей BigTable на 100 серверах, hedge через 10 мс → p99.9 1 800→74 мс, +2% запросов. Порог чуть выше p50 → дубли <5%. Tied: копии в очереди на двух серверах, cancel при старте исполнения; дешевле, если сама обработка дорогая. Основа — Mitzenmacher, power of two choices. На 2026 hedging в gRPC, Envoy, AWS SDK; адаптивный порог (DDSketch) + token bucket, иначе при деградации hedge удваивает нагрузку. Figma DBProxy hedgit в шардах. Запрет: hedge на неидемпотентную запись без ключа.

**Load shedding.** Отказывать избыток до коллапса. Приоритетный shed, fail open лимитера, известная точка перегиба с нагрузочного теста (Глава 22.5). Netflix: fleet shaping помесячно, автоскейл поминутно, shed посекундно. Shed на входе дешевле, чем OOM внутри.

Когда не ретраить: 4xx кроме 408/429; мутация без идемпотентности; зависимость уже shed-ит вас. Сигнал ошибки: ретраи на каждом слое; hedge с фиксированным порогом в инциденте; CB открыт, а зависимость давно жива — и вы сами держите простой.

Для 1–3: таймаут + Full Jitter, один уровень, идемпотентный POST. Для 10–30: token bucket ретраев, shed на gateway, CB точечно. Для 100+: hedge на read-only fan-out, адаптивный порог, velocity control.

## 12.4. Деградация вместо падения: graceful degradation по слоям

Бинарное «всё 200 или всё 500» — плохой UX и плохой blast radius. Слои деградации заранее, с флагом и с видимым UI.

Слой 0 — инварианты: деньги, аутентификация, целостность заказа. Не degrade в «примерно списали». Fail closed.

Слой 1 — синхронные украшения: рекомендации, «кто лайкнул», персонализация, аватары. Таймаут короткий, fallback: без блока, кэш, дефолт. Поиск может стать keyword-only без ML.

Слой 2 — асинхрон: уведомления, аналитика, email. Очередь, не путь клика. При перегрузе очередь shed-ит аналитику раньше уведомления о платеже.

Слой 3 — редкое: экспорт, админ-отчёты, полный ресинк. 503 с Retry-After.

Протокол. Каждая hard-зависимость: fail open или fail closed — явно. Лимитер — fail open. Авторизация — fail closed. Кэш рекомендаций — fail open в «популярное». Флаг ops-toggle с владельцем и runbook (таксономия Hodgson, Глава 15/23): kill switch поиска не должен жить безымянным.

VK rpc-proxy: приложение не ждёт таймаута движка, сразу идёт по ветке «движка нет». Это degrade в коде, не в надежде. LLM-продукты: при перегрузе инференса — шаблон/кэш/очередь, не 30 с spinner (Глава 13.8, 30.7).

Когда не degrade: целостность денег и прав. Когда обязаны: всё, что Multi-AZ всё равно не спасёт в первый час зависимости. Сигнал ошибки: падение третьего стороннего API кладёт checkout; нет скриншота «как выглядит продукт без поиска».

Для 1–3: два слоя — деньги vs остальное. Для 10–30: матрица зависимость × поведение в RFC. Для 100+: режимы degrade в runbook и в UI-копирайте, не только в коде.

## 12.5. Мультизонность и мультирегиональность: цена и реальные сценарии

AZ и регион решают разные отказы. AZ — питание, зал, часть сети провайдера. Регион — катастрофа площадки, часть юрисдикций, us-east-1 как коррелированная зависимость индустрии.

**Multi-AZ.** Для стейтфул на AWS это часто дефолт управляемой БД (Aurora: 6 копий, 3 AZ, запись при потере одной AZ). Stateless: 2–3 AZ, PodDisruption, zone affinity, чтобы не платить cross-AZ на болтовне (Глава 9.1: $0.02/GB RT; +NAT $0.045). Kubernetes без PreferSameZone (1.35) — скрытый счёт. Когда: прод с пользовательскими данными. Когда нет: превью-окружение, batch на spot.

**Multi-region.** Сценарии: (1) эвакуация при падении региона; (2) латентность до пользователя; (3) юридическая локализация данных. Это три разных дизайна. Смешивать «потому что надёжность» — купить все цены без одного свойства.

Цена. Репликация 10 TB/сутки US↔US ≈ $6 000/мес только трафик (AWS 2026). Синхронный кросс-регион в клике — 40–150 мс. Раздвоенный control plane, два пайплайна, два кэша, которые должны быть тёплыми при failover. Netflix: четыре региона full-active, эвакуация по продуктовой метрике (stream starts/s); время 6–7 минут встречается во вторичных источниках, первичной публикации Netflix с этим числом в ресерче нет — брать как «минуты при репетиции», не как SLO. Capacity: «если увести X% из us-east-1, сколько compute долить в остальные» — без этой арифметики active-active врёт.

Telegram: sticky home DC, данные не anycast «куда ближе»; юридическая модель (разнесение ключей и данных по юрисдикциям, FAQ) диктует топологию. Чистый anycast конфликтует с этим.

Когда регион не нужен: команда <30, нет юрисдикции, RTO часа достаточно, multi-AZ + проверенный restore закрывают. Когда нужен: контракт RTO минут при отказе региона, или пользователи на двух континентах с бюджетом <100 мс, или закон о локализации. Сигнал ошибки: второй регион в Terraform, failover ни разу; кэш в failover холодный (ранний Chaos Kong Netflix ловил именно это).

Не путать с клетками: клетки режут blast radius деплоя внутри региона. Регион не изолирует плохой билд, выкатанный везде.

## 12.6. Резервное копирование, восстановление, RPO/RTO и учения

RPO — сколько данных во времени готовы потерять. Определяется репликацией и частотой бэкапа: синхронный кворум → RPO≈0; суточный снимок → RPO до 24 ч; асинхронная кросс-регион реплика → RPO = лаг (ориентир TAO выше). RTO — время до обслуживания. Определяется автоматизацией failover и restore, не наличием файла в S3.

Правило: RTO, не прогнанный restore/game day, — гипотеза. Бэкап без restore — тот же класс, что неподписанный артефакт без verification gate.

Учение пишется как сценарий, не как «проверить бэкап». Сценарий A: удалили таблицу миграцией, нужен PITR на момент T−15 мин. Сценарий B: потерян диск primary, есть реплика в другой AZ. Сценарий C: регион недоступен, RPO = лаг асинхронной копии. Каждый сценарий даёт своё фактическое время. Путать их в одном числе «RTO 1 час» — способ проиграть договор.

Практика.

- Снимок + WAL/binlog, не только диск VM.
- Restore в отдельный инстанс по расписанию (для 1–3 — раз в 90 дней минимум; для 10–30 — ежемесячно на копии; для 100+ — автоматизированный restore-тест). Часы до «приложение поднялось на восстановленном» записываются. Это ваш настоящий RTO.
- Шифрование, доступ, ретеншн согласованы с privacy (Глава 33.4): удалили пользователя — бэкап ещё хранит; процедура задокументирована.
- Object storage версионирование: ransomware и ошибочный delete.
- Игра «потеряли регион» и игра «потеряли таблицу из-за миграции» — разные. Вторая чаще. Point-in-time recovery важнее второго региона на старте.
- Деньги: сверка после restore, не только «строки на месте» (Глава 40).

Когда не городить 3–2–1 как в enterprise-буклете: данные пересоздаваемые (кэш, превью). Когда обязательно: источник правды, платежи, ПДн, исходники не только в git-хосте. Сигнал ошибки: бэкап зелёный, restore ни разу; RTO в договоре 1 час, restore в учении 14 часов.

## 12.7. Chaos engineering: как начать без риска

Chaos — эксперимент с гипотезой, blast radius и стоп-краном, не Random Kill в пятницу. CNCF 2025: Chaos Mesh 3% production use, 11% evaluating. Практика нишевая: сначала SLO и инцидент-процесс (Глава 26), потом хаос.

Лестница Netflix: Chaos Monkey (инстанс) → Gorilla (AZ) → Kong (регион) → ChAP/FIT в пайплайне на подмножестве прода. Ранний Kong ловил: нет fallback в межсервисных вызовах, дырявая кросс-регион репликация, кривые breaker, холодные кэши failover, однорегиональные метрики.

Как начать, не самоубившись:

1. Гипотеза: «если убить реплику Redis кэша, p99 ленты <X, checkout не задет».
2. Малый blast: один тенант, одна клетка, 1% трафика, не prod-wide.
3. Стоп-кран: человек + автоматический откат по SLI (не по CPU).
4. День, не ночь; дежурный в курсе; окно согласовано с error budget (Глава 26.2).
5. Сначала stage, изоморфный по топологии зависимостей, не по размеру.
6. Запрещены: эксперименты на платежном пути без идемпотентного стенда; убийство единственной primary без проверенного failover; одновременный chaos и выкат.

Game day без injection: «восстановите БД из вчера, часы пошли» — уже chaos данных и людей. Для 1–3 этого достаточно на год. Для 10–30: kill пода зависимости в stage каждую неделю, один контролируемый prod-эксперимент в квартал. Для 100+: FIT в пайплайне, как у тех, у кого клетки и SLO уже работают.

Сигнал, что chaos — театр: убивают случайные поды, гипотезы нет, после «успеха» runbook не изменился. Сигнал, что рано: нет SLI, алерты не actionable (NeuBird 2026: 57% команд считают actionable <30% алертов — сначала гигиена, Глава 26).

## 12.8. Чек-лист production readiness

Технические ворота до публичного трафика. SLO-документ, error budget policy, роли IC — Глава 26; этот список на них ссылается, не подменяет.

**Отказы**

- [ ] Hard-зависимости выписаны; для каждой: таймаут, fail open/closed, слой degrade (12.4).
- [ ] Потолок доступности посчитан как произведение hard-зависимостей (Глава 2.2 / 26.1).
- [ ] Пул/семафор на каждую зависимость (bulkhead); общий пул запрещён.
- [ ] Ретраи: один уровень, cap, Full Jitter, идемпотентность мутаций; нет ретраев на 4xx кроме явного списка.
- [ ] Hedge только на идемпотентном чтении и с token bucket.
- [ ] Shed на входе: известен приоритет, лимитер fail open.

**Изоляция и выкат**

- [ ] Blast radius деплоя: canary или клетка; конфиг не едет «всем сразу» без двери.
- [ ] Отказ одного шарда/поды не требует глобального job.
- [ ] Graceful shutdown > in-flight (Глава 9.3).

**Данные и восстановление**

- [ ] RPO/RTO записаны; restore делали в дату X, фактическое время Y.
- [ ] PITR или эквивалент на источнике правды.
- [ ] Бэкап проверен человеком, который не настраивал job.

**Наблюдаемость и люди**

- [ ] Golden signals + одна бизнес-метрика на сценарий (инструменты — Глава 25; алерты на симптомы — 26).
- [ ] Runbook на каждый page: действие, не «посмотреть».
- [ ] On-call назначен в системе оповещения до запуска, не после.
- [ ] Нагрузочный тест дал точку перегиба; degrade начинается до OOM.

**Цена отказа**

- [ ] Multi-AZ на стейтфул прод; cross-AZ болтовня оценена.
- [ ] Второй регион либо имеет drill, либо явно «не делаем».
- [ ] Kill switch автоматики, которая меняет глобальное состояние (урок us-east-1 2025).

Для 1–3 достаточно подмножества: таймауты, бэкап с restore, один SLI, shutdown, идемпотентность денег. Остальное — «н/п» с причиной. Для 10–30 добавьте bulkhead, shed на gateway, monthly restore, canary. Для 100+ пропуск пункта — блокер запуска поверхности.

Сквозной мини-сценарий готовности. Перед публичным URL: (1) салфетка 9.6; (2) матрица зависимостей 12.4; (3) restore вчерашнего снимка в отдельный инстанс, приложение поднялось, записали минуты; (4) убили зависимость поиска в stage — checkout жив; (5) on-call в системе оповещения. Если пункт 3 или 4 не сделан — это не «запустимся и посмотрим», это известный класс отказа 12.1 без лечения. SLO и кто ведет инцидент в ночи — соседний чек-лист Главы 26.8, его не дублируем.

## Чек-лист главы

**Модель**

- [ ] Классы отказа 12.1 разобраны на своём сценарии; «что сломается первым» названо.
- [ ] Матрица зависимость × degrade существует в RFC.

**Механизмы**

- [ ] Нет ретраев на каждом слое; jitter есть.
- [ ] CB не единственная защита и не первый инструмент.
- [ ] Квоты и приоритеты на публичном и на тяжёлом тенанте.

**Репетиция**

- [ ] Restore или game day за 90 дней (1–3) / 30 дней (10–30+).
- [ ] Chaos без гипотезы не проводится.
- [ ] Глава 26 открыта для SLO и инцидента; эта глава не используется как замена процесса.

## Антипаттерны

«Ретраи на каждом слое — gateway × сервис × клиент SDK — „надёжность“ — один уровень + jitter (AWS Builders' Library)»

«Backoff без jitter — все клиенты в одну секунду — круглая экспонента — Full Jitter, детерминированный на крон»

«CB как первый инструмент — модальное открытие, долгое восстановление — скопировали Hystrix — таймаут, token bucket, shed; CB точечно»

«Hedge в инциденте — фиксированный порог удвоил нагрузку — хвосты вчера — адаптивный порог + bucket (Dean & Barroso 2013)»

«Лимитер fail closed — Redis лимитера упал, весь API 503 — защита стала отказом — fail open, локальный бакет»

«Ячейка с общим стейтом — один Redis на cells — слово без bulkhead — запрет шаринга, иначе это шард с маркетингом»

«Multi-region в Terraform без drill — RTO „минуты“ — статус — game day эвакуации; иначе один регион + restore»

«Бэкап без restore — job зелёный, RTO гипотеза — галочка compliance — часы на учении записываются»

«Chaos в пятницу на primary — Random Kill — Netflix в слайде — гипотеза, 1%, стоп-кран, не платёжный путь»

«Деградации нет — зависимость 500 = продукт 500 — бинарное мышление — слои 12.4, деньги fail closed»

«Оптимизация сняла защиту — быстрее hot path, каскад — Discord OOM — лимит очереди до ускорения»

«Автоматика без эпохи — устаревший план перетёр новый (us-east-1, окт 2025) — самолечение — kill switch, не применять план старше поколения»
