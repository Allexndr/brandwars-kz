# Глава 19. Фронтенд-инженерия

*Коротко. Фронтенд — архитектура клиента, стратегия рендеринга, бюджеты Core Web Vitals, данные с кэшем и офлайном, формы, контракт с бэкендом и дисциплина бандла. Дизайн-система, a11y и i18n как продуктовые практики — Глава 36; исследования и эвристики UX — 35; натив — 20. Здесь — инженерия, из-за которой страница проходит полевые метрики и не врёт пользователю при сетевом сбое.*

*Глава даёт таксономию состояния, выбор CSR/SSR/SSG/PPR, пороги CWV 2026, работу с данными, формы со схемой, типобезопасность контракта, аудит зависимостей и гейт релиза.*

*Читать после 14 (контракт API) и 16 (стек UI). Real-time транспорт — Глава 21. AI-паттерны стриминга в UI — 30.7; здесь только общее про ожидание и откат.*

Фронтенд путают с выбором фреймворка. State of JS 2025 (опрос ноябрь 2025, публикация февраль 2026): React — 83,6% использования; средний разработчик за карьеру сменил 2,6 фреймворка. На 2026 React 19.x — текущий мажор (патч 19.2.8, 21 июля 2026; React 20 не анонсирован). Vite 8 стабилен с 12 марта 2026 (Rolldown+Oxc вместо esbuild+Rollup). Принцип переживает логотип: граница ошибки, бюджет JS, источник истины для серверных данных, схема формы.

Вторая путаница — лабораторный Lighthouse как истина. CWV меряются на 75-м перцентиле поля CrUX, 28 дней. Страница проходит, только если LCP, INP и CLS одновременно в «good». INP заменил FID 12 марта 2024. Порогов на 2026 Google не менял. Идеальный Lighthouse при провале Search Console — типичная ситуация.

Третья — класть серверные данные в клиентский глобальный стор. Тогда loading/error/refetch пишут руками. TanStack Query (и аналоги) закрывают серверное состояние; в Redux/Zustand остаётся эфемерное и клиентские предпочтения.

Для 1–3: один фреймворк, Vite или Next по типу продукта, Zod на формах, бюджет бандла в CI. Для 10–30: BFF/контракт, RUM, error boundaries по маршрутам, аудит зависимостей. Для 100+: дизайн-система как пакет (Глава 36), Module Federation только при реальной независимой поставке, не «потому что микрофронтенды».

## 19.1. Архитектура клиентского приложения: маршрутизация, состояние, данные, границы ошибок

Четыре слоя, которые нельзя смешивать в одном хуке.

**Маршрутизация.** URL — источник истины для навигации и фильтров (`searchParams`). Состояние, которым делятся вкладки и которым можно поделиться ссылкой, живёт в URL, не в памяти. Вложенные маршруты режут бандл и границы ошибок. Layout не должен перезапрашивать всё дерево при смене ребёнка.

**Состояние — таксономия, не библиотека.** Локальное эфемерное (модал, hover) — `useState`/сигналы. Клиентское персистентное (тема, ширина сайдбара) — Zustand (~1 КБ) с `persist` или аналог; Redux Toolkit — когда команда уже на нём и есть реальный общий клиентский граф. Серверное (списки, профили, заказы) — кэш запросов (TanStack Query): ключ, staleTime, инвалидация, дедуп, retry. Не дублировать сервер в Redux.

**Данные.** Prefetch на сервере → гидратация того же `queryKey` на клиенте. Без пропс-дриллинга дерева «всё сразу». Мутации инвалидируют ключи точечно, не `invalidateAll`.

**Границы ошибок.** Error boundary на маршрут и на виджет с чужим SDK (чат, карта, видео), не один на всё приложение. Падение виджета рекомендаций не должно сносить checkout. Непойманный промис и ошибка рендера — разные каналы: последняя ловится boundary, первая — глобальным handler + телеметрия. Fallback — осмысленный UI (Глава 35.8), не пустой экран.

RSC (стабильны с React 19.0, 5 декабря 2024): серверные компоненты не ломаются между минорами, но API бандлера для RSC **не следует semver** внутри 19.x — пинить версии фреймворка. Advisory 2026 по `react-server-dom-*` (DoS на server functions, CVE-2026-23870, CVSS 7.5, патчи 19.0.6/19.1.7/19.2.6): приложения без RSC-бандлера не затронуты; lockfile проверять.

Микрофронтенды. Оправданы, когда независимый релиз и независимый отказ команд стоят цены дублирования runtime. Иначе — монорепо пакетов (19.7). Web Components — когда дизайн-система переживает смену фреймворка в большой орг; для одного React-продукта выгоды нет (худший DX, SSR/формы).

Когда глобальный стор вреден: туда попали заказы. Когда boundary вреден: глотает ошибку оплаты без телеметрии. Сигнал ошибки: фильтры каталога сбрасываются при обновлении; один `catch` на App.tsx.

Для 1–3: маршруты = страницы, Query, одна boundary на layout. Для 10–30: вложенные boundaries, запрет серверных данных в Zustand линтером/ревью. Для 100+: пакеты по доменам, контракт маршрутов.

## 19.2. Стратегии рендеринга и когда какая уместна

Стратегия выбирается по странице, не «всем SSR».

CSR. Хостинг дешёвый, SEO не нужен, за логином. Внутренние админки. Цена: пустой HTML до JS, плохой LCP на слабом мобильном.

SSR. HTML с данными запроса. Персонализация, SEO, первый осмысленный paint. Цена: TTFB зависит от бэкенда; кэш сложнее.

SSG. Сборка HTML заранее. Документация, маркетинг, редкий контент. Максимальная скорость, дешёвый CDN. Цена: пересборка на изменение.

ISR / фоновая ревалидация. Каталог и блоги, где «минута лага» допустима. Цена: два мира (stale/fresh) и инвалидация по тегу.

Streaming SSR. Оболочка сразу, хвост данных доезжает. Смешанная латентность блоков на одной странице.

Islands (Astro). Минимум JS на контентных сайтах. Astro лидирует по удовлетворённости среди мета-фреймворков (State of JS 2025, +39 п.п. к Next). Не для плотного приложения с общим клиентским графом.

PPR / Cache Components (Next.js 16 стабилизировал PPR и поглотил его этой моделью). Статическая оболочка с CDN + стрим динамики в том же ответе. Дефолт перевёрнут: данные динамические, кэш явный (`'use cache'`, `cacheLife`/`cacheTag`). Всё, что читает `cookies()`, — внутри `<Suspense>`, иначе сборка падает. Когда: витрина + персональная корзина на одной странице. Когда нет: целиком залогиненное приложение без публичного HTML — обычный SSR/CSR проще.

Правило: публичный первый экран — SSG/PPR/SSR; интерактив после логина — клиент. Смешивать персонализацию в SSG без слоя cache/cookie — утечка одного пользователя другому.

Когда SSR вреден: каждая ячейка таблицы — серверный круг без кэша, TTFB 2 с. Когда CSR вреден: лендинг с рекламы, LCP 4 с. Сигнал ошибки: `force-dynamic` на весь сайт «на всякий случай».

Для 1–3: маркетинг SSG, приложение SSR или SPA по SEO. Для 10–30: PPR/Cache Components на смешанных витринах. Для 100+: политика кэша как fitness: запрет персонализации вне Suspense.

## 19.3. Производительность в браузере: бюджеты, Core Web Vitals, критический путь

Пороги поля (75-й перцентиль, 28 дней):

- LCP ≤ 2,5 с good; 2,5–4 needs improvement; >4 poor.
- INP ≤ 200 мс good; 200–500 ni; >500 poor.
- CLS ≤ 0,1 good; 0,1–0,25 ni; >0,25 poor.

Все три одновременно. Поле 2025 (Web Almanac через вторичный источник): на мобильных хороший LCP ~62%, INP ~77%, CLS ~81%; все три — чуть меньше половины сайтов. Вы не «как медиана интернета», вы против своего SLO и против конкурента в выдаче.

Экономика. Deloitte × Google «Milliseconds Make Millions» (2020; 37 брендов, 30+ млн сессий): +0,1 с мобильной скорости → retail конверсия +8,4%, средний чек +9,2%; travel конверсия +10,1%; lead gen формы +21,6%. Vodafone: LCP −31% → продажи +8% (A/B). Akamai (порядок, ~10 млрд визитов): 100 мс ≈ −7% конверсии. Классика Amazon «100 мс = 1%» ~2006, цитировать как возраст, не как ваш коэффициент. Считать свою воронку.

Стартовый бюджет (mobile, mid-range, 4G): JS критического пути ≤170 КБ сжатый; CSS ≤50 КБ; hero-изображения ≤300 КБ; шрифты ≤100 КБ и ≤2 начертания; TTFB ≤800 мс; сторонние скрипты ≤5, все отложенные; long tasks >50 мс в первые 5 с — ноль. Бюджет без падения CI — пожелание.

Критический путь. LCP-элемент: `fetchpriority="high"`, без lazy, AVIF/WebP, `sizes`, preload. INP: дробить long tasks (`scheduler.yield()`, `isInputPending`), убрать синхронную работу из click, дебаунс ввода, worker на тяжёлое, аудит третьих (чат, теги, эмбеды). CLS: width/height или aspect-ratio на медиа, слоты под баннеры, `font-display: swap` + size-adjusted fallback (иначе swap сам даёт сдвиг), не вставлять блоки над отрисованным.

Lab vs field. Lighthouse/WebPageTest — регрессия в CI, не соответствие CWV. INP в лабе принципиально врёт: нет реального ввода. Свой RUM (`web-vitals` JS) с разбивкой по устройству, стране, типу страницы. CrUX — только Chrome и сайты с достаточным трафиком.

Восприятие. Порог «мгновенно» ~100 мс; 1 с — непрерывность мысли; 10 с — удержание внимания (Nielsen; рифмуется с INP 200 мс). Скелетон работает ~до 1 с; на 2–3 с серые блоки читаются как зависание. Спиннер — для необратимого действия (оплата). Процент — когда нужна предсказуемость остатка.

Когда оптимизация p50 вредна: INP на слабых Android не двигается, а вы жмёте Lighthouse desktop. Сигнал ошибки: hero с `loading="lazy"`; шрифт без резерва места.

Для 1–3: бюджет JS в CI, RUM хотя бы через CrUX Search Console. Для 10–30: свой RUM, лимит third-party. Для 100+: перф-бюджет в PR как тесты, владельцы метрик по типам страниц.

## 19.4. Работа с данными: кэш, оптимистичные обновления, офлайн, синхронизация

Кэш клиента. Query cache с ключом `(entity, id, params)`. `staleTime` по природе данных: справочник минуты–часы, баланс — 0. Инвалидация по мутации той же сущности. Prefetch на hover маршрута — дешёвый LCP следующей страницы.

Оптимистичные обновления. Только обратимые низкорисковые действия: лайк, чекбокс задачи, отправка сообщения в чат (с пометкой «не доставлено»). Обязателен rollback на ошибке: молчаливый откат хуже спиннера. Оплата, смена email, удаление аккаунта — пессимистично, со спиннером и идемпотентным ключом (Глава 14.1, 17.3).

Конфликты. Last-write-wins допустим на настройках. На совместном документе — CRDT (Yjs де-факто для редакторов) или сервер-авторитет. Tombstones и actor id — Глава 21; здесь не изобретать свой merge JSON.

Офлайн. PWA на iOS: Home Screen, SW-кэш, Web Push только с iOS 16.4 и только у установленного PWA, без `beforeinstallprompt`, без Background Sync. Это «сайт как иконка», не замена нативу (Глава 20). Если офлайн — ценность продукта: Electric / PowerSync / Zero поверх Postgres, очередь мутаций, явный статус синка. Не притворяться, что `localStorage` — БД заказов.

Когда оптимизм вреден: двойной клик «купить» без ключа. Когда офлайн вреден: пользователь думает, что оплатил в самолёте. Сигнал ошибки: кэш показывает чужого пользователя после logout (не сбросили QueryClient); или retry POST без ключа.

Для 1–3: Query + сброс кэша на logout + пессимизм на деньгах. Для 10–30: prefetch, точечная инвалидация, очередь офлайн только если PM это назвал. Для 100+: sync-движок как продукт, не как библиотека в одном экране.

## 19.5. Формы, валидация и сложные интерфейсы

Схема — единственный источник: Zod/Valibot → тип TS → рантайм на клиенте и тот же контракт на сервере → тексты ошибок. Клиентская валидация — UX, не защита. Сервер валидирует всегда (Глава 17, 32).

Поведение. Валидация на blur и на submit, не на каждый keystroke (кроме форматов вроде карты, где маска помогает). Сообщение: что не так и как исправить, рядом с полем. Disable кнопки до валидности — только если понятно почему; иначе пользователь не знает, чего не хватает. WCAG 2.2: 3.3.7 не заставлять вводить то же дважды; 3.3.8 Accessible Authentication — не требовать распознавание/транскрипцию без альтернативы (капча с картинкой без другой дороги валит AA).

Сложные UI. Wizard хранит черновик (сервер или явный local draft) и позволяет назад. Таблицы: виртуализация на сотнях строк, не тысяча DOM-нод. Drag обязан иметь альтернативу одним указателем (WCAG 2.5.7). Confirm — только необратимое; иначе undo.

Angular 22 (июнь 2026): Signal Forms стабильны — тот же принцип схемы и реактивности на другой экосистеме. Не мигрируйте React-форму «потому что сигналы».

Когда схема вредна: три поля, обвязка на 200 строк абстракции. Когда обязательна: деньги, ПДн, многошаговый онбординг. Сигнал ошибки: валидация только в UI; или ошибка 422 без маппинга на поля.

Для 1–3: одна схема на endpoint. Для 10–30: генерация типов из OpenAPI + ручная схема формы, сверка в CI. Для 100+: дизайн-системные поля (Глава 36) уже с a11y; не собирать input с нуля.

## 19.6. Типобезопасность и контракты с бэкендом

Граница — Глава 14. На клиенте три рабочих пути 2026:

1. Монорепо TS: tRPC или Server Actions (Next) — типы сквозные, цена — один язык и аккуратность с RSC/server functions (пин версий, патчи advisory).
2. Полиглот: OpenAPI 3.1 / gRPC → кодоген клиента. Ломающее изменение ломает CI клиента, не прод через неделю.
3. GraphQL: codegen + persisted queries + лимит сложности. Без этого — урок Airbnb (CDN, авторизация). Для экрана с графом — законно; для оплаты — REST с ключом.

Запрещено: ручной `as MyType` на `fetch`. Запрещено: два JSON с разным смыслом `id`. Версии API — не ломать клиент в сторах: мобильный отстаёт (Глава 20); веб можно выкатить вместе, но кэш CDN и открытые вкладки живут часами.

Контрактные тесты потребительские (Глава 31.3): клиент публикует ожидание, провайдер гоняет в CI. Для соло — хотя бы сгенерированный клиент и ломающий PR на схему.

Когда tRPC вреден: второй клиент на Kotlin, публичный API, партнёры. Когда OpenAPI вреден: внутренняя SPA на неделю, схема из трёх ручек — избыток. Сигнал ошибки: фронт парсит `message` вместо `code`; или опциональность поля «на клиенте required, на сервере нет».

Для 1–3: Zod на входе/выходе критичных ручек. Для 10–30: кодоген обязателен. Для 100+: breaking change схемы — fitness, не договорённость.

## 19.7. Сборка, размер бандла, зависимости и их аудит

Сборщик. Новый проект — Vite 8 (12 марта 2026): единый Rust-конвейер Rolldown (1.0, май 2026) + Oxc. Легаси webpack с лоадерами — Rspack 2.0 как drop-in. Чистый Next — Turbopack в dev (стабилен в Next 16); прод-сборка вне Next как general-purpose не позиционируется. State of JS 2025: Webpack 87% использования vs Vite 84%, удовлетворённость 26% vs 98%.

Бандл. Резать по маршруту и по интеракции. Смотреть compressed и что попало в критический чанк, не «у нас tree-shaking». Момент: датапикеры, иконки всей пачки, moment.js vs dayjs/Temporal, полифилы на Baseline-фичи. На 2026 нативный CSS закрыл разрыв: nesting и `:has()` — Baseline Widely около июня 2026; container queries Widely август 2025. Runtime CSS-in-JS (emotion, styled-components) для новых проектов — legacy; Tailwind v4 / CSS modules / vanilla-extract.

Зависимости. Lockfile в git. `npm audit`/`pnpm audit` в CI с политикой: critical — блокер, остальное — срок. Лицензии: AGPL в клиентском бандле — юридический сюрприз (Глава 44.6). Дубли версий React — классика монорепо, ломает хуки; resolutions/overrides явные. SBOM фронта — Глава 23.5; здесь минимум: кто добавил пакет, зачем, размер.

Сторонние скрипты. Каждый — в бюджете INP. GTM без контроля = дыра бюджета. Consent и загрузка тегов после согласия — Глава 33.6.

Монорепо. pnpm workspaces + Turborepo/Nx: affected builds, удалённый кэш, пакет DS отдельно версионируется. Changesets на пакеты, не «всегда latest».

Когда не дробить: чанк 8 КБ ценой waterfall. Когда не обновлять мажор: нет changelog-часа и регресса CWV. Сигнал ошибки: главный чанк растёт каждый спринт без падения CI; или зависимость без репозитория в package.json.

Для 1–3: bundlesize на main, audit в CI. Для 10–30: budget per route, weekly dep review. Для 100+: платформенный бот обновлений с канарейкой.

## 19.8. Чек-лист качества фронтенда перед релизом

**Архитектура**

- [ ] Фильтры и шаринг-состояние в URL; серверные данные не в глобальном клиентском сторе.
- [ ] Error boundary на маршруте и на чужих виджетах; fallback с телеметрией.
- [ ] Стратегия рендеринга названа per-route; персонализация не утекает в SSG.

**Производительность**

- [ ] Бюджеты 19.3 в CI красные при нарушении.
- [ ] LCP-элемент без lazy; размеры медиа заданы; шрифты ≤2 начертания.
- [ ] Полевой RUM или хотя бы CrUX по типу страницы; lab не выдаётся за поле.
- [ ] Сторонних скриптов ≤ лимита; long task на старте не >50 мс.

**Данные и формы**

- [ ] Logout чистит кэш запросов и storage.
- [ ] Оптимизм только с rollback; деньги пессимистичны и с ключом.
- [ ] Схема формы = серверная валидация; 422 мапится на поля.
- [ ] Клиент сгенерирован из контракта или закрыт Zod; нет `as any` на API.

**Поставка**

- [ ] Lockfile, audit, лицензии; размер критического чанка в отчёте PR.
- [ ] RSC/server functions: версии пропатчены (advisory 2026).
- [ ] `prefers-reduced-motion` на анимациях перехода (деталь — Глава 36.4).
- [ ] Критичный поток пройден клавиатурой (a11y-гейт — 36.5, здесь — не ноль).
