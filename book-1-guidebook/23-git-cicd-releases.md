# Глава 23. Git, CI/CD и релизные стратегии

*Коротко. Доставка — машина, которая превращает коммит в изменение в проде с известным blast radius. Глава фиксирует: как устроены репозитории, как ветвиться, какие ворота стоят до merge, как собирать один артефакт, как выкатывать, как откатывать.*

*AI ускорил генерацию кода и сместил узкое место на review, интеграцию и деплой (DORA 2025; Faros, 2026: медианное время в ревью +441% г/г). Без быстрой машины поставки прирост «строк» становится приростом CFR.*

*Технические отказы деплоя — класс «изменение» в Главе 12.1. Политика «можно ли релизить при дырявом error budget» — Глава 26.2. Тестовая стратегия — Глава 31. Угрозы цепочки поставки и модель Shai-Hulud — Глава 32.7; здесь только то, что обязано стоять в пайплайне.*

*Читать, когда lead time измеряется днями, hotfix едет в обход CI, или «мы деплоим по пятницам, потому что страшно».*

Поставка — не «нажать кнопку в пятницу». Это контракт: любой коммит, включая hotfix, проходит один путь; артефакт не пересобирается под окружение; деплой отделён от активации фичи; откат дешевле починки и известен до выката.

DORA 2025 (~5000 респондентов) отказалась от ярлыков Elite/High/Medium/Low. Остались распределения. Lead time <1 часа — 9,4% команд; <1 дня — ещё 15%; >1 недели — 43,5%. On-demand деплой — 16,2%; чаще раза в день — 22,7%. Медиана change failure rate попадает в 8–16%; 39,5% команд имеют CFR >16% (DORA 2025). Последняя четырёхуровневая шкала — DORA 2024: Elite — on demand, lead time <1 дня, CFR ~5%, восстановление <1 часа (19% респондентов). Сравнивать себя с «Elite 2024» в 2026 методологически шатко: границы кластеров пересчитывались каждый год. Сравнивайте одну команду во времени, не команды между собой (см. Главу 42.9).

Инварианты пайплайна, которые нельзя нарушать:

```
commit → pre-merge CI (<10 мин) → merge queue → hermetic build
      → артефакт + SBOM + signed provenance → verification gate
      → ephemeral env / stage → smoke/contract
      → canary (метрический анализ) → progressive rollout → auto-rollback
```

Один артефакт на все окружения. Конфигурация внешняя, артефакт неизменяемый. Deploy ≠ release. Всё, что доходит до прода, включая hotfix, идёт этим путём.

Для 1–3: GitHub/GitLab, trunk, CI <10 минут на критичном пути, один артефакт, ручной canary «10% на 15 минут», флаг на рискованную фичу, кнопка отката. Для 10–30: merge queue, preview-окружения, автоматический canary по SLI, политика удаления флагов. Для 100+: remote cache, selective execution, rings, verification gate на admission, отдельная команда на build-инфраструктуру.

## 23.1. Организация репозиториев: моно или поли, и что это меняет

Репозиторий — единица атомарности изменений, владения и CI-счёта. Выбор «моно или поли» — про границы коммита и стоимость сборки, не про модульность кода. Модульность живёт в архитектуре (Глава 10.2), не в числе git-remote.

Монорепо оправдан, когда нужны атомарные изменения через границы сервисов, единая версия зависимостей, общий рефакторинг, сильная культура code ownership. Полирепо — когда независимые релизные циклы, разные юридические или лицензионные контуры, команды с разной инженерной культурой, нет ресурса на build-инфраструктуру.

Скрытая стоимость монорепо в 2026 — CI-счёт. Он растёт с числом инженеров; у организаций >50 человек часто входит в топ-3 инфраструктурных статей, иногда превышая production compute (iancloud / практика монорепо, 2026). Лечение: remote cache + selective execution. Корректно настроенные дают 60–80% сокращения стоимости CI на монорепо, которое раньше гоняло всё на каждый коммит; основная доля экономии — кэш (консенсус 2026). Hit-rate на базелифицированной кодовой базе: 70–90% для неизменённых таргетов. Кэш зависимостей обычно 90%+, кэш билд-артефактов — 30–60%.

Инструменты на 2026 год. Bazel — полиглот, 300+ инженеров, строгая гермитичность, цена входа максимальная. Nx — JS/TS enterprise, граф зависимостей, Nx Agents. Turborepo — JS/TS до ~300 инженеров, content-addressable кэш, низкая цена входа. Принцип, который переживает инструмент: считать граф зависимостей и не собирать то, что не изменилось. Сравнительные бенчмарки Nx vs Turborepo (9:20 против 19:18) исходят из одной статьи без независимого аудита — не принимать как измерение.

Гибрид допустим: монорепо продукта + отдельные репозитории для публичных SDK, мобильных клиентов со стор-циклом, форков с чужой лицензией. Не плодите «микрорепо на каждый сервис» без build-системы: получите 40 версий библиотеки логирования и невозможный атомарный рефакторинг.

Когда монорепо не применять: нет человека, который настроит affected-targets; юридически разные продукты; open-source, который должен жить отдельно. Чем платите за ранний монорепо без кэша: линейным ростом минут CI × число PR. Сигнал ошибки: «подождём зелёный CI 40 минут» при изменении README.

Для 1–3: один репозиторий, точка. Для 10–30: монорепо, если сервисы меняются вместе; поли — если мобильное приложение и бэкенд имеют несовместимые циклы (стор vs непрерывный SaaS). Для 100+: монорепо только с remote cache и ownership-файлами; иначе CI съест бюджет раньше, чем выиграет атомарность.

## 23.2. Ветвление: trunk-based против длинных веток, размер изменений

Trunk-based development: все интегрируются в общую ветку; ветки живут часы, не дни. DORA проводит границу по 24 часам. Без подпорок TBD разваливается: pre-merge CI <10 минут; merge queue (тест PR против будущего состояния main); feature flags, отделяющие merge от release; правило «main всегда релизабелен; если нет — это P1, всё остальное стоит».

При 30-минутной сборке и 50 инженерах модель ломается на постоянных поломках trunk. Pre-merge CI <10 минут — условие работоспособности TBD при команде >15 инженеров. Медиана PR у TBD-команд: <200 строк против 500+ у команд с feature-ветками; частота мержа ≥1 PR/инженер/день против 2–3 в неделю (агрегаторы TBD, 2024–2026; не первоисточник DORA — порядок величины, не норматив).

GitFlow остаётся уместным для софта с календарным релизным циклом: коробочный продукт, мобильные приложения с ревью в сторе (Глава 20.6). Для непрерывно поставляемого SaaS GitFlow — очередь за `release/*` и мёртвый `develop`. Не путайте «релизная ветка на стор» с «каждая фича живёт три недели».

Merge queue обязателен, когда параллельных PR больше, чем успевает зеленеть main: иначе семантические конфликты («оба зелёные против вчерашнего main, вместе красные») ломают trunk после мержа. Очередь тестирует PR против будущего состояния. Без неё при >15 инженерах вы либо сериализуете мержи вручную, либо чините main каждый день.

AI усиливает давление на размер батча. Faros 2026: размер PR +51,3%, инциденты на PR +242,7%, 31% PR мержится без ревью. DORA 2025: работа малыми батчами и сильные практики version control (частые коммиты, уверенный rollback) — два из семи усилителей положительного эффекта AI. Правило: AI-сгенерированный дифф не освобождает от лимита размера и от ревью. Одинаковый процесс review для человека и модели — антипаттерн (см. Главу 42.4).

Когда TBD не применять: регулятор требует signed-off релизный артефакт с заморозкой; стор-цикл с внешним ревью; команда не умеет флаги. Чем платите за длинные ветки: merge hell, CFR на интеграционном дне, невозможность отката малого изменения. Сигнал ошибки: ветка живёт дольше, чем CI-кэш, и мержится «большой пятницей».

## 23.3. Пайплайн от коммита до прод: стадии, время, кэширование, параллелизация

Стадии режьте по вопросу, который каждая отвечает.

Pre-merge (<10 минут): линт, unit, secret scan, typecheck, affected tests. Цель — не пустить в trunk то, что сломает следующих. Если не укладываетесь: selective execution, кэш, вынести e2e из pre-merge.

Post-merge / build: гермитичная сборка одного артефакта, SBOM, подпись, публикация в registry по digest. Сборка на машине разработчика для прода запрещена.

Verify: контрактные тесты, SCA, лицензии, размер бандла, сканирование образа. Можно параллелить с публикацией в staging, нельзя пропускать на hotfix.

Deploy: один и тот же артефакт в preview → stage → prod. Конфиг — переменные окружения, флаги, секреты; не «пересобрать с `ENV=prod`».

Release: активация через флаг, кольцо, процент. Деплой может быть «на 100% подов», а фича — на 1% пользователей.

Кэширование. Кэш зависимостей (lockfile → store) даёт высокий hit-rate и дешёвый выигрыш. Кэш компиляции/тестов — по графу: ключ = хеш входов, не имя ветки. Remote cache окупается, когда локальный кэш не шарится между раннерами. Не кэшируйте то, что должно быть гермитичным и воспроизводимым, без учёта времени и «что стояло на раннере».

Параллелизация: независимые джобы (lint ∥ unit ∥ SCA) на pre-merge; e2e — после артефакта, на том же образе. Шардирование тестов по времени, не по алфавиту папок: иначе один шард 8 минут, остальные 40 секунд.

Hotfix. Тот же пайплайн, можно сузить набор тестов только если есть явный allowlist «skip с обоснованием» и обязательный canary. Обход CI — отдельный класс отказа 12.1: изменение без ворот.

Пример. Команда 18 человек, монорепо, CI 28 минут, 40 PR/день. Очередь на зелёный main — полдня. Лечение по порядку: (1) affected tests по графу — −12 минут; (2) remote cache зависимостей — ещё −6; (3) e2e из pre-merge в post-merge на артефакте; (4) merge queue. Итог: pre-merge 8 минут, main зелёный. Не начинайте с «переехать на Bazel», пока не выкинули e2e из критичного пути.

Для 1–3: GitHub Actions / GitLab CI, кэш зависимостей, один workflow. Для 10–30: разделение pre/post, артефакт по digest, preview. Для 100+: отдельный build cluster, очередь, бюджет CI как статья FinOps (Глава 22.7).

## 23.4. Качество ворот: линт, тесты, безопасность, лицензии, размер бандла

Ворота — порог с действием, не «джоб, который все игнорируют». На каждое ворота: что проверяет, порог, что происходит при нарушении (блок merge / блок deploy / тикет).

Линт и формат — на pre-commit и в CI одинаковым конфигом. Спор о стиле не должен доходить до ревью (Глава 42.6).

Тесты. Pre-merge: unit + быстрые интеграционные на affected. Контрактные тесты между сервисами — до деплоя потребителя (Глава 31.3). E2E — минимальный набор на артефакте, не 200 сценариев в каждом PR (Глава 31.4). Флейк > порога (например, 2% за 7 дней) — карантин, не retry 5 раз до зелёного (Глава 31.5).

Безопасность в пайплайне, не вместо Главы 32. Порядок для маленькой команды: (1) secret scanning с блокировкой push; (2) SCA с reachability; (3) SAST на diff с узким набором правил; (4) сканирование образа перед деплоем. SAST на весь репозиторий в каждом PR даёт 30–60% ложных на дефолте (отраслевые оценки 2026) и убивает ворота. Reachability снижает критичность ~82% «критичных» SCA-алертов — без неё ворота либо красные всегда, либо их обходят.

Лицензии. Политика: запрещённые (GPL в проприетарном SaaS без юррешения), требующие notice, разрешённые. Проверка на lockfile, не «когда юрист спросит». Сбой — блок merge на новых зависимостях.

Размер бандла / образа. Бюджет в CI: JS-бандл — порог из Главы 19.7; Docker-образ — лимит слоёв и веса, запрет `:latest`. Превышение — блок или требование ADR «почему выросли на N МБ».

AI-код. 30% респондентов DORA 2025 не доверяют качеству сгенерированного кода; Stack Overflow 2025: 46% активно не доверяют точности. Ворота не ослабляются, потому что «модель написала». Наоборот: secret scan и SCA важнее — модель чаще тащит устаревшие пакеты и вставляет ключи в примеры.

Когда не ставить все ворота сразу: команда из трёх, ещё нет пользователей. Минимум: секрет-скан, тесты на деньги/auth, сборка. Чем платите за 15 красных джобов: `--no-verify` и потерянный сигнал. Сигнал ошибки: доля skipped jobs растёт, CFR не падает.

## 23.5. Артефакты и цепочка поставки: воспроизводимые сборки, подпись, SBOM

Артефакт — неизменяемый объект с digest. Тег `v1.2.3` и `:latest` — указатели, не идентичность. Деплой по digest; тег — алиас после проверки.

Один артефакт на stage и prod. Пересборка «с прод-флагами компилятора» уничтожает смысл тестирования: выкатываете не то, что проверяли.

SBOM перечисляет компоненты. Provenance доказывает целостность процесса сборки. Это разные артефакты. SLSA поле `resolvedDependencies` заполняется best-effort и не заменяет SBOM (SLSA FAQ). Генерируйте SBOM (CycloneDX или SPDX) на каждой сборке, храните рядом с digest. Зачем: за час ответить «где у нас log4j / xz / заражённый npm», а не за недели. Полная модель угроз, Shai-Hulud, soak-период зависимостей, pin Actions по SHA — Глава 32.7. Здесь — что обязано быть в CI.

SLSA Build track v1.2 (одобрена ноябрь 2025): L1 — provenance существует; L2 — подписана hosted build service; L3 — hardened build, provenance недоступна для подделки самой сборкой. Модель «SLSA 1–4» с гермитичностью на L4 отменена в v1.0 (2023); гермитичность отложена в будущий Build L4. GitHub Artifact Attestations дают Build L2 из коробки; L3 — через reusable workflows / изолированных раннеров. npm trusted publishing генерирует provenance без отдельной конфигурации.

Sigstore: keyless-подпись — краткоживущий сертификат Fulcio по OIDC-идентичности CI, запись в Rekor. Отменяет хранение ключа подписи. Подпись, которую никто не проверяет на деплое, — декорация. Verification gate: admission controller / deploy job отклоняет образ без валидной attestation и без совпадения policy (репозиторий, workflow, digest).

Pin: lockfiles в репозитории; базовые образы и CI-actions по digest, не по тегу. Никаких релизов с ноутбука. В атаке Shai-Hulud 2 59% скомпрометированных машин были CI/CD-раннерами, не рабочими станциями (GitGuardian / разборы 2026). Раннер — часть TCB. Статические облачные ключи в CI в 2026 — антипаттерн; OIDC-федерация — Глава 24.6.

Воспроизводимость. Полная бит-в-бит воспроизводимость на L4 ещё не требование рынка. Практический минимум: гермитичный toolchain, зафиксированные версии, отсутствие «скачать latest в скрипте сборки». Если два прогона одного коммита дают разный digest из-за timestamps — это не «норма Docker», это дыра в кэше и в provenance.

Для 1–3: сборка в CI, образ по digest, SBOM рядом, GitHub Attestations включены. Для 10–30: verification на деплое, запрет `:latest` admission-политикой. Для 100+: SLSA L3, внутренний registry как единственный источник, политика «в кластер только подписанное».

## 23.6. Стратегии выката: canary, blue-green, progressive delivery, кольца

Canary отвечает: безопасен ли этот билд. Единица — деплой. Сигналы — error rate, latency, saturation, один бизнес-SLI. Feature flag отвечает: должна ли аудитория видеть поведение. Единица — флаг. Владелец — продукт. Флаг не заменяет canary: он управляет поведением тех, кто уже на новом билде, и ничего не говорит о здоровье билда.

Матрица:

- Rolling update — дефолт для stateless. Не применять: несовместимая схема БД, долгие соединения без drain.
- Blue-green — мгновенный откат, есть бюджет на двойную ёмкость. Не применять: дорогой стейт, большие БД, которые нельзя дублировать.
- Canary + автоанализ — высокий трафик, богатая телеметрия, зрелые SLI. Не применять: <100 rps (нет статистики), нет метрик качества.
- Кольца (внутренние → бета-тенанты → 1% → 10% → 100%) — разные продукты/тенанты, нужна изоляция blast radius. Не применять: один тенант = весь бизнес.
- Dark launch / shadow — валидация производительности на реальном трафике. Не применять: побочные эффекты (запись, платежи) без изоляции.

На Kubernetes в 2026: Argo Rollouts (Rollout CRD, AnalysisTemplate, свой UI, экосистема Argo CD) или Flagger (обёртка Deployment, непрерывные проверки, экосистема Flux). Оба CNCF, оба говорят с Prometheus/Datadog и Gateway API (GA; SMI архивирован). Выбор — по GitOps-движку, не по «кто моднее».

Практическое ограничение: при 10 репликах вес 5% не существует — 0,5 пода нет. Гранулярность canary ограничена числом реплик. Лечение: больше реплик на время выката, или флаг/кольцо на уровне запросов (service mesh / gateway), не на уровне подов.

Миграции схемы деплоятся отдельно от кода. Expand-contract: (1) expand — новая структура, старая жива, индекс `CONCURRENTLY`, nullable; (2) migrate — backfill батчами, двойная запись; (3) switch — чтение из нового; (4) contract — удалить старое. `SET lock_timeout = '3s'` на сессии миграции: лучше упавшая повторяемая миграция, чем блокировка на час. Порог: <1 млн строк — прямой DDL часто терпим; 1–100 млн — онлайн-инструменты (gh-ost, pg-osc, pgroll); >100 млн — expand-contract с троттлингом. Решает не только размер: 10 млн строк при 2000 записей/с сложнее, чем 500 млн при 5 записях/с. Новый код всегда обратно совместим с текущей схемой — иначе откат кода невозможен (Глава 15.4).

Автооткат по метрикам, не по решению человека в 3 часа ночи. Пороги canary = те же SLI, что в Главе 26.1, урезанные по окну (5–15 минут). Нет SLI — нет автоматического canary, есть ручной таймер и ручной откат.

Для 1–3: rolling + ручная пауза 15 минут на staging URL. Для 10–30: canary 5–10% на 20 минут по error rate и p99. Для 100+: кольца и автоанализ; конфиг-флаги отдельно от билда.

## 23.7. Feature flags: жизненный цикл, уборка, риски

Флаг — временный шов в коде, не платформа для вечной конфигурации. Жизненный цикл: создать с владельцем и датой удаления → выкатить билд (флаг off) → включить кольцу → открыть → удалить код и флаг в согласованном PR.

Типы, которые нельзя смешивать в одном ключе: release flag (дожать выкат), experiment (A/B, Глава 28), ops flag (kill switch), permission flag (тенант купил фичу). Ops и permission живут дольше; release — нет. Смешение даёт «эксперимент, который три года включает оплату».

OpenFeature (CNCF incubating) — слой абстракции над провайдером. Смысл — сменить LaunchDarkly/Unleash/свой Redis без переписывания каждого `if`. Не ставьте абстракцию, пока флагов <10 и провайдер один.

Риски. Комбинаторный взрыв: 10 булевых флагов = 1024 мира, ни один не протестирован. Зависимости флагов («B имеет смысл только если A») не документируются и ломаются в кольце. Флаг в критичном пути без локального дефолта: недоступность flag service кладёт продукт — fail open/closed выбран явно, как для лимитера (Глава 12.2). Секрет в флаге (API-ключ «для бета-тенанта») — секрет вне secret manager.

Уборка. Бюджет: флаг без изменения состояния 30 дней и без владельца — кандидат; release-флаг старше одного квартала — P1 на удаление. Инвентарь флагов — файл или дашборд, не Slack-память. CI может падать на `FIXME_FLAG` старше даты.

Когда флаги не применять: нет процесса удаления; команда из трёх и фича выкатывается целиком за день. Чем платите: мёртвыми ветками кода и инцидентом «включили старый флаг на 100%». Сигнал ошибки: никто не знает, что будет, если удалить ключ `new_checkout`.

Пример. Checkout v2 за флагом 14 месяцев, 40% кода — `if (newCheckout)`. Canary билда проходит, потому что 90% трафика на старом пути. Выкат «на 100%» в час пик вскрывает N+1 и отсутствие индекса. Флаг скрыл отсутствие canary на реальном пути. Лечение: прогрев пути shadow-трафиком, затем кольцо, затем удаление старого кода в том же спринте, что и 100%.

## 23.8. Откат: что должно быть готово до релиза

Откат дешевле и быстрее починки. Целевое время — минуты. DORA 2025: уверенное владение rollback/revert усиливает положительный эффект AI. Оценка Google SRE Workbook: порядка 70% аварий связаны с изменениями — аргумент иметь откат, не ваша статистика.

Разведите операции. Rollback кода — предыдущий артефакт по digest, тот же пайплайн в обратную сторону. Rollback флага — выключить ключ, билд не трогать. Rollback схемы — отдельная, обычно невозможная операция; поэтому expand-contract. Rollback конфига — предыдущая ревизия GitOps. Смешать «откатим всё кнопкой» — способ получить схему нового и код старого.

Автооткат. Порог: burn rate SLI, error rate, saturation. Человек подтверждает только если сигнал двусмысленный (выкат сам по себе меняет метрику) или ставка необратима (миграция данных, пуш в стор). Мобильный стор — не откат в минутах: staged rollout и форс-апдейт, Глава 20.6.

Готовность до релиза, не после:

- Предыдущий артефакт доступен, не стёрт GC registry.
- Команда `deploy previous` или GitOps revert прогнаны на stage за последние 30 дней.
- Схема обратно совместима с n−1 кодом.
- Флаг kill switch существует для фичи, не для «всего приложения».
- On-call знает, какая кнопка, без чтения RFC в 03:00.
- Миграция с lock_timeout; план «миграция зависла» — kill session, не reboot primary.

Когда откат не применять как первую реакцию: порча данных уже записана неотменяемо (надо forward-fix); выкат закрыл дыру безопасности (откат открывает дыру). Чем платите за «всегда чиним вперёд»: часом инцидента вместо трёх минут отката. Сигнал ошибки: «откат не пробовали со второго квартала».

## 23.9. Чек-лист релиза

Прогон перед выкатом в prod. Для 1–3 — подмножество с пометкой «н/п». Пропуск без причины — блокер.

**Артефакт**

- [ ] Digest образа/бандла зафиксирован; stage и prod получают его, не пересборку.
- [ ] SBOM рядом с артефактом; provenance подписана (хотя бы SLSA L2).
- [ ] Verification gate на деплое включён: нет подписи — нет выката.
- [ ] Секреты не в образе (сканер).

**Ворота**

- [ ] Pre-merge CI <10 минут на affected; красный — не мержится.
- [ ] Secret scan и SCA (с reachability на critical) зелёные.
- [ ] Бюджет бандла/образа не превышен либо есть ADR.
- [ ] Контрактные тесты потребителя прошли против этого артефакта.

**Выкат**

- [ ] Стратегия названа (rolling / canary / blue-green / кольца); гранулярность canary ≥1 реплика.
- [ ] Автооткат по SLI настроен или явно «ручной, потому что rps < порога».
- [ ] Миграция схемы — отдельный шаг, expand уже в проде либо DDL с lock_timeout.
- [ ] Флаги: владелец, дата уборки, дефолт при недоступности flag service.

**Откат и люди**

- [ ] Предыдущий digest доступен; revert прогоняли на stage за 30 дней.
- [ ] Код n и n−1 совместимы со схемой.
- [ ] On-call назначен; runbook на откат — команды, не «посмотреть дашборд».
- [ ] Error budget не исчерпан, либо есть исключение по политике 26.2 (security/P0).
- [ ] Коммуникация: статус-страница / внутренний канал, если выкат затрагивает пользовательский SLI.

**Мобильный / стор (если применимо)**

- [ ] Staged rollout процент и критерии паузы заданы (Глава 20.6).
- [ ] Форс-апдейт не единственный план отката.

## Чек-лист главы

**Поток**

- [ ] Моно/поли выбран с причиной; CI-счёт монорепо имеет кэш или это осознанный налог.
- [ ] Ветки <24 часов или GitFlow оправдан стор/календарём.
- [ ] Hotfix идёт тем же пайплайном.

**Машина**

- [ ] Один артефакт, конфиг снаружи, deploy ≠ release.
- [ ] Ворота имеют порог и действие; skipped jobs не растут.
- [ ] Подпись проверяется на деплое, не только генерируется.

**Риск выката**

- [ ] Canary и флаг не подменяют друг друга.
- [ ] Откат кода, флага и схемы разведены; revert репетировали.
