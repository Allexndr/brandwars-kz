# Глава 25. Observability

*Коротко. Observability — способность объяснить поведение системы вопросом, который вы не предугадали заранее. Глава: четыре сигнала, OpenTelemetry, дисциплина логов и запретные поля, RED/USE и кардинальность, сэмплинг трейсов, дашборды и алерты, которые не будят зря, стоимость наблюдаемости.*

*OpenTelemetry закрыл спор о стандарте инструментирования: graduation CNCF — май 2026; traces/metrics/logs — GA; profiling — четвёртый сигнал (alpha / OTLP profiles near-stable beta). Дальше выбираете бэкенд, не протокол.*

*Алерты на симптомы пользователя и burn rate SLO — Глава 26.3–26.4. Профилирование как метод оптимизации — Глава 22.3. Что писать в security-аудит и чего не писать из-за утечки — пересечение с 32.10 и 33.4; поля-запреты — здесь, чтобы пайплайн логов не стал теневой БД.*

*Читать, когда инцидент разбирают по SSH, счёт Datadog больше compute, или дашбордов 40 и on-call открывает один.*

Наблюдаемость покупается не «поставили агент». Она есть, если за 5 минут на неизвестном сбое вы отвечаете: какой процент пользователей, какой слой, какой деплой, какой тенант, какой dependency, и можете достать один trace_id до строки кода или запроса в БД.

Стоимость — того же порядка, что compute. Типичная доля observability — 15–30% инфраструктурного бюджета, у худших >40%; здоровый ориентир — до 20% (оценки 2025–2026, вторичные разборы Gartner/отрасли). >50% расходов приходится на логи. Gartner: 36% корпоративных клиентов тратят >$1 млн/год, 4% — >$10 млн (цитируется вторично). >60% инженерных руководителей отмечают, что observability растёт быстрее инфраструктуры. AI-функции дают рост объёма телеметрии в 2–5 раз. Парадокс: качественная инструментация наказывается рублём, если нет бюджета кардинальности и конвейера на границе.

Для 1–3: структурированные логи с request_id, RED на публичном API, один дашборд, алерты только на симптомы. Для 10–30: OTel SDK + Collector, трассировка с head-сэмплом, USE на стейтфул, cardinality review. Для 100+: tail-based sampling, профили в проде, cost per service, tiered logs.

## 25.1. Три с половиной сигнала: логи, метрики, трейсы, профили

Метрики — агрегаты: дешёвые, быстрые, для SLI и алертов. Логи — события: дорогие, для «что именно». Трейсы — граф вызовов одного запроса: для «где в fan-out». Профили — где CPU/RAM/lock внутри процесса: для «почему этот span 800 мс». Четыре сигнала не заменяют друг друга. Логи с метриками «на коленке» не дают p99 по ручке. Трейс без профиля не объясняет горячую функцию. Профиль без trace_id не клеится к пользовательскому запросу.

Golden signals Google SRE: latency, traffic, errors, saturation. RED (Rate, Errors, Duration) — для синхронных сервисов по ручке. USE (Utilization, Saturation, Errors) — для ресурсов: CPU, диск, пул соединений, очередь. RED на Postgres врёт: смотрите saturation пула и диск. USE на HTTP API не отвечает «какая ручка 500». Ставьте оба, на разных объектах.

Профили в 2026 вошли в контур OTel, но эксплуатационно это всё ещё отдельная дисциплина: sampling 1:N стеков, pprof/eBPF, непрерывный профиль в проде (Глава 22.3). Не ждите graduation profiles, чтобы включить pprof endpoint на staging. Ждите политику: профили не содержат PII, retention короткий, доступ ограничен.

Связка в инциденте: алерт по метрике (error ratio ручки) → exemplars/trace_id → trace (какой dependency) → лог по trace_id (payload-класс, без секрета) → профиль, если span локальный и толстый. Если любой шаг требует SSH и grep по четырём машинам — сигнала не хватает, не «мало опыта on-call».

Для 1–3 хватит метрик RED + логов с id. Трейсы — когда появился второй сервис или внешний SDK с хвостом. Профили — когда p99 не объясняется сетью (Глава 9.1).

Пример склейки. Checkout p99 вырос с 180 мс до 1,4 с при живом error ratio. RED говорит «медленно, не 500». Trace по exemplar: 1,1 с в `POST /v1/charges` к провайдеру, свой код 40 мс. Лог по trace_id: `outcome=timeout`, `attempt=2`, без тела карты. Профиль своего процесса плоский — чинить таймаут и hedge зависимости (Глава 12.3), не «оптимизировать JSON». Без трейса команда крутила GC. Без запрета на body в логе этот же разбор стал бы PCI-инцидентом.

Синтетика не заменяет эти четыре сигнала, но закрывает дыру «никто не ходит, SLI зелёный». Один probe на сценарий оплаты снаружи каждую минуту — дешёвый SLI, когда трафик ночью падает ниже статистической значимости canary (Глава 23.6). Синтетика без совпадения с пользовательским путём (другой регион, другой CDN, пропуск auth) врёт так же, как ping вместо checkout.

## 25.2. Инструментирование: OpenTelemetry, семантические соглашения, идентификаторы запросов

Инструментировать против OTel — дефолт 2026. Collector на границе: приём, фильтр, сэмплинг, маршрутизация в бэкенд. Смена Datadog на Grafana Cloud / Honeycomb / своего Tempo — смена exporter, не переписывание кода. Vendor SDK «потому что агент уже стоит» закрывает выход.

Semantic conventions зафиксированы в core: `http.request.method`, `http.response.status_code`, `db.system.name`, `db.query.text`, `messaging.system`, `service.name`, `deployment.environment.name`. Имена больше не меняются — дашборды и алерты стабилизировались. Не изобретайте `http_status` рядом с конвенцией. Roadmap 2026: стабилизация `rpc`, `system`/`process`, K8s, error/exception; GenAI conventions для агентных workflow; browser/mobile. Для LLM-контура — Глава 30.9, не дублируем.

Идентификаторы. `trace_id` / `span_id` — W3C Trace Context в заголовках (`traceparent`). `request_id` публичный, уходит клиенту в ответе и в support. `deployment.environment.name`, `service.version` (digest, не «latest»), `deployment.id`. Без version на метриках canary из Главы 23.6 слеп. Контекст обязателен через границы: HTTP, очередь (inject в metadata), job. Обрыв контекста на брокере — типичная дыра: «трейсы есть, а воркер — отдельная вселенная».

Автоинструментирование (Java agent, OTel JS) закрывает HTTP и драйверы БД. Бизнес-спаны («reserve_inventory», «charge_card») — руками. Без них трейс — лес framework-спанов. Атрибуты бизнеса: `tenant_id` в спане и логе, не в метке метрики (см. 25.4).

Collector: не шлите SDK прямо в SaaS с продакшн-флота, если объём уже заметен. Фильтр и tail sampling на границе дешевле, чем ingest. Заявленная экономия собственного конвейера — 50–70% на логах и трейсах (отраслевые разборы 2026, вендорски окрашены — проверяйте на своём объёме).

Resource detectors: `service.instance.id`, `k8s.pod.name`, `cloud.region`, `host.name` — достаточно, чтобы ответить «какой реплика-канар». Не тащите hostname пользователя или device_id в resource метрик. Baggage в OTel — для контекста, который должен дойти до дочерних спанов (tenant_tier, experiment_id); не для PII и не для секретов: baggage часто логируется промежуточными слоями целиком.

Когда не внедрять OTel сразу: один процесс, один регион, нет очередей — JSON-лог + Prometheus client закрывают 25.8. Чем платите за ранний Collector: ещё одним сервисом, который надо дежурить. Сигнал ошибки: SDK шлёт в три бэкенда параллельно «на переход» и счёт ×3.

Для 1–3: один `service.name`, traceparent, request_id в логах, облачный бэкенд. Для 10–30: Collector, конвенции, context в очередях. Для 100+: отдельный телеметрический pipeline как платформенный сервис (Глава 24.8).

## 25.3. Структурные логи и дисциплина полей; что нельзя логировать никогда

Лог — JSON-событие с схемой, не строка для grep. Обязательные поля: timestamp (UTC), level, service, env, version, trace_id, span_id, request_id, event (стабильное имя), outcome. Дальше — атрибуты класса события. Текст сообщения — для человека, не носитель структуры: `user 12 paid` без `user_id` и `amount_minor` бесполезен в агрегации.

Дисциплина имён. Словарь полей общий (OTel + свои 20 имён). `userId` / `user_id` / `uid` в трёх сервисах — три дашборда. Ревью новых полей в PR, как ревью API.

Уровни. DEBUG не в prod по умолчанию; INFO — бизнес-события и границы запроса; WARN — деградация; ERROR — отказ с действием. Не ERROR на 404 пользовательского URL. Sampling DEBUG динамически по trace_id при инциденте (override на 5 минут), не «включили verbose на сутки на весь флот».

Что нельзя логировать никогда. Пароли и их хеши. Полные токены сессий, refresh, API keys (только префикс + хеш). Полный PAN и CVC (PCI). Секреты из заголовков `Authorization`. Содержимое личных сообщений и тела документов пользователя. Спецкатегории ПДн «на всякий случай». Приватные ключи, JWT целиком, connection string с паролем. Промпты и tool-аргументы агента с секретами внутри — редакция обязательна (Глава 30.6). MCP-конфиги с ключами — отдельная дыра (GitGuardian 2026: 24 008 секретов в MCP-конфигах на публичном GitHub).

Почему это жёстко. Логи — теневая БД персданных: попадают под GDPR/152-ФЗ, право на удаление, утечку, тикеты поддержки. Salesloft/Drift 2025: секреты в тикетах стали цепочкой компрометации. Retention логов приложения с PII — 14–30 дней дефолт; access-логи с IP — 30–90; audit безопасности — год (Глава 33.4). TTL — свойство хранилища, не cron.

Тела запросов. Не логировать raw body на публичном API. Если нужен класс ошибки валидации — коды полей, не значения. Исключение: sandbox с синтетикой.

Индекс vs хранение. В горячий индекс — поля фильтрации: service, env, level, event, tenant_id (если тенантов сотни, не миллионы), route. Не индексировать message целиком и не индексировать payload. Full-text по сырому JSON на 30 днях — типичный источник счёта «сканирование». Сэмплирование INFO (1:10) при сохранении 100% WARN/ERROR — рычаг после redaction. Не сэмплировать audit: вход, смена прав, экспорт данных (Глава 32.10).

PII в логах и право на удаление. Если `user_id` в логе — DSR должен либо ждать TTL, либо иметь процедуру не искать по 12 индексам руками. Проще: короткий TTL app-логов и не класть содержимое. «Удалим из логов по запросу» на Loki/ELK без ключа пользователя — ложное обещание.

Для 1–3: JSON, request_id, запрет секретов линтером (secret scan на лог-строках в тестах). Для 10–30: схема полей, redaction middleware, отдельные audit vs app logs. Для 100+: DLP на конвейере, запрет high-cardinality в лог-индексе.

## 25.4. Метрики: RED, USE, кардинальность, агрегация, хранение

Метрика — временной ряд с ограниченным множеством лейблов. Кардинальность: одна метрика × уникальные комбинации лейблов = биллинговые ряды. `http_requests_total{code,route,method,service}` — норма. Добавить `user_id` / `request_id` / `tenant_id` при 10⁵ тенантов — взрыв счёта, не «лучшая наблюдаемость». Теги высокой кардинальности живут в логах и спанах, не в метриках.

Cardinality budget: лимит рядов на сервис, review новых лейблов в PR, runtime drop/агрегация сверх порога. Это рычаг №1 снижения счёта. Метрики самой observability: ряды на сервис, скорость роста кардинальности, cost per service.

RED на каждую публичную ручку и на каждый критичный RPC: rate, error ratio (5xx и бизнес-ошибки раздельно), duration (p50/p95/p99, не среднее). USE на пул соединений БД, CPU, heap, очередь брокера, disk fill, лимиты API зависимости. Saturation важнее utilization: 40% CPU при полном пуле соединений — простой USE-промах.

Агрегация. Histogram/summary для latency; не среднее из среднего. Exemplars связывают бакет гистограммы с trace_id — мост к 25.5. Recording rules: предрасчёт SLI, не «считаем ratio на лету по 90 дням raw».

Хранение. Горячие метрики SLI — 15 суток с высоким разрешением; 90 суток — 1m; год — 5m для ёмкости. Не хранить scrape 15s год: вы платите за то, что не читаете. Для ёмкости и сезонов нужны длинные ряды низкой гранулярности (Глава 26.7).

Когда не плодить custom metrics: событие редкое — лог. Высокая кардинальность нужна для разбора — trace attribute. Custom metric на каждый if в коде — путь к счёту > compute.

Пример. Сервис биллинга добавил лейбл `invoice_id` «чтобы быстро фильтровать». За неделю ряды ×10⁴, счёт метрик утроился, scrape начал drop. Лечение: лейбл снят, `invoice_id` в спане и логе, метрика осталась `{route,status,tenant_tier}` где tier — десятки значений, не миллионы.

## 25.5. Распределённая трассировка: сэмплинг, контекст, польза в разборе инцидентов

Трейс полезен, когда показывает критический путь и ожидание зависимости, а не когда «100% запросов в Jaeger». 100% на высоком rps — либо банкротство ingest, либо sampling всё равно где-то молча включён.

Head-based sampling: решение на входе (1% или 10/с). Дёшево, просто, режет редкие ошибки: 1% может не поймать 0,1% 500. Tail-based: держать trace в Collector, решить по ошибке/latency/атрибуту. Дорого по памяти на границе, ловит хвосты. Гибрид: head 1% всегда + tail keep errors и p99 + явный `trace=1` с клиента support.

Сэмплинг должен быть согласован по графу: иначе у gateway есть спан, у БД нет. Parent-based: дочерний наследует решение. W3C `tracestate` несёт vendor-флаги.

Польза в инциденте. Каскад: кто ретраит (Глава 12.3). Fan-out: какой лист держит p99 (Dean & Barroso, Глава 9). Canary: версия в ресурсе спана. Не польза: трейс как audit денег — неполный сэмпл; для денег нужен полный бизнес-лог/outbox.

Глубина. Бесполезны тысячи спанов ORM на запрос: либо span на репозиторий, либо логи slow-query. Бесполезен один спан на весь процесс. Бюджет: десятки спанов на запрос типичного API, не тысячи.

Разбор инцидента по трейсу, который должен получаться за минуты. Фильтр: `error=true` за окно алерта + `deployment.version` канарейки. Смотрите не корневой спан («HTTP 500»), а самый длинный дочерний waiting. Если waiting — чужой API: это класс зависимости 12.1, не ваш GC. Если waiting — БД и `db.query.text` (обрезанный, без литералов) показывает seq scan — это индекс, не «добавить реплик». Если трейсов ошибок 0 при красном RED — сэмпл съел хвост: временно поднимите keep errors до 100% на сервис, не включайте 100% всех запросов.

Когда трейсы не применять как источник истины: биллинг, идемпотентность, антифрод-решения. Сэмпл юридически и операционно неполный. Там — полный outbox/audit. Чем платите за always-on APM на CRUD: второй прод по ingest. Сигнал ошибки: on-call в инциденте открывает логи, потому что «в трейсах всё зелёное» из-за 1% head sample.

Для 1–3: head 10% или always-on при низком rps. Для 10–30: 1% + errors. Для 100+: tail-based на Collector, отдельные политики на платёжный путь (100% traces или полный лог, не «как всем»).

## 25.6. Дашборды, которые реально используют; и алерты, которые не будят зря

Дашборд — рабочее место роли, не галерея графиков. Три, которые живут: (1) on-call: RED сервиса, зависимости, saturation, деплой-аннотации, error budget burn; (2) продукт/ёмкость: бизнес-SLI, очередь, headroom; (3) стоимость телеметрии: GB логов, ряды, сэмпл-рейт. Остальное — ad-hoc из Explore в инциденте. Дашборд без владельца и без открытия за 30 дней — удалить.

Правило страницы: будить человека только на симптом, видимый пользователю (или на burn rate SLO, Глава 26). CPU 90% в 3 ночи при живом SLI — не page. Алерты на причины плодят fatigue и игнор.

Данные февраля 2026 (1039 SRE/DevOps): 77% on-call команд получают ≥10 алертов в день; 57% говорят, что actionable <30%; 83% игнорируют алерты хотя бы иногда; 44% организаций пережили аварию из-за подавленного алерта; 78% имели инцидент, при котором не сработал ни один алерт. Alert fatigue — фактор отказа, не «morale». Гигиена: каждый page имеет runbook и действие; алерт без действия за 30 дней удаляется; ticket-уровень отдельно от page.

Multiwindow multi-burn-rate (Google SRE Workbook) — канон для SLO-алертов, детали порогов в Главе 26.1–26.2. Здесь: не заменяйте его порогом «error rate >1% за 1 минуту» без длинного окна — получите ночные всплески и слепоту к медленной утечке бюджета.

Аннотации деплоев на графиках обязательны. Без них on-call не свяжет p99 с выкатом 23.6. Ссылка из алерта в дашборд с уже проставленным интервалом и service — иначе 5 минут на «какой Grafana».

Раскладка дашборда on-call, которая не требует прокрутки на три экрана: ряд 1 — SLI и burn (остаток бюджета, 1h/6h); ряд 2 — RED по ручкам с аннотацией деплоя; ряд 3 — saturation зависимостей (пул БД, очередь, лимит Stripe); ряд 4 — версия/реплики/canary weight. Цвет — от порога SLO, не от «зелёный, потому что CPU <80%». Ссылка «Explore traces for this panel» с уже проставленным фильтром service+version.

Алерты как код: порог, for, severity, runbook URL, owner. PR на новый page требует: какой пользовательский симптом, какой runbook, какой auto-resolve. Без трёх полей — не мержится. Дубли page на CPU и на latency той же ручки — оставить latency.

Для 1–3: один дашборд, 3–5 алертов на симптомы. Для 10–30: burn-rate page+ticket, каталог алертов в git. Для 100+: error budget policy связывает алерт с заморозкой релизов (26.2), не с «ещё одним Slack-каналом».

## 25.7. Стоимость наблюдаемости и как её удержать

Почему счёт непредсказуем. Мультидименсиональный биллинг: GB × хост × custom metric × cardinality растут одновременно и мультиплицируются. Логи растут с verbosity, трейсы — с fan-out, метрики — с лейблами; ни одно из трёх не пропорционально rps.

Рычаги по убыванию эффекта:

1. Cardinality budget на SDK и ревью лейблов.
2. Tier routing логов: горячий индекс (7–14 дней, ошибки и audit), тёплый cheap store, холодный object storage. Типично 30–50% сокращения при умеренных усилиях.
3. OTel Collector: фильтр, суммаризация повторов, сэмплинг на границе — заявленные 50–70% на логах и трейсах.
4. First-mile: не слать DEBUG, access-логи веб-сервера отдельно от app, без тел.
5. Tail-based для трейсов + преагрегированные метрики вместо «каждое событие как metric».

Метрики управления: cost per service, запросы с наибольшим сканированием (дорогие LogQL/Datadog queries), сервисы с самым быстрым ростом рядов, доля логов в счёте. Порог: >20% инфрасчёта — разбор; >30% — красный флаг, заморозка новых custom metrics без удаления старых.

Не экономить на audit безопасности и на SLI, по которым page. Экономить на debug-индексе, на 100% traces CRUD, на лейблах «на будущее».

Для 1–3: не включать verbose, не ставить user_id в метрики — этого хватит на год. Для 10–30: Collector + TTL. Для 100+: FinOps-строка «observability», как compute (Глава 22.7).

Пример. Команда 40 человек, Datadog $80k/мес при compute $120k (40%). Разбор: 70% $ — APM spans 100% + логи без TTL 90 дней. Включили tail keep errors+5% и lifecycle 14/45/180. Счёт $38k при том же MTTD на пользовательских сбоях. Не трогали SLI-метрики.

## 25.8. Чек-лист «видим ли мы продакшн»

**Сигналы**

- [ ] RED на публичных ручках; USE на БД, пулах, очередях, диске.
- [ ] Логи структурированы; trace_id сквозной, включая воркеры.
- [ ] Версия/digest на телеметрии; деплои аннотированы.
- [ ] Профиль доступен для сервисов, где p99 «в нашем коде».

**Запреты и схема**

- [ ] Нет паролей, токенов, PAN, тел сообщений, сырых Authorization в логах.
- [ ] Новые лейблы метрик ревьюятся; user_id/request_id не в метриках.
- [ ] Retention задан TTL хранилища; app PII 14–30 дней.

**Люди и алерты**

- [ ] Есть дашборд on-call, который открывали в последнем инциденте.
- [ ] Page только на пользовательский симптом или SLO burn; runbook есть.
- [ ] Алерт без действия 30 дней удалён.
- [ ] Клиенту и support доступен request_id.

**Деньги**

- [ ] Доля observability к инфре известна; >20% разобрана.
- [ ] Collector или эквивалент фильтра на границе, если счёт уже заметен.
- [ ] Cost per service телеметрии виден хотя бы квартально.

Для 1–3 достаточно: JSON-логи с id, RED, 3 алерта, запрет секретов. Остальное — «н/п».

## Чек-лист главы

**Инструментирование**

- [ ] OTel (или совместимый экспорт) + конвенции имён; не уникальный vendor-only API без exporter.
- [ ] Контекст не рвётся на очереди.

**Дисциплина**

- [ ] Словарь полей; redaction; cardinality budget записан.
- [ ] Дашбордов мало, алертов меньше, чем людей в ротации.

**Стоимость**

- [ ] Рычаги 25.7 применены в порядке, не «сменить вендора первым».

## Антипаттерны

«user_id в метрике — миллион рядов, счёт ×10 — „удобно фильтровать“ — лейбл в спане/логе, метрика по route»

«Вся телеметрия в SaaS без Collector — ingest 100% DEBUG — быстрее подключить агент — фильтр на границе»

«Алерт на CPU — page в 03:00 при живом SLI — скопировали шаблон хоста — симптомы и burn rate (Глава 26)»

«Лог тела запроса — PAN и пароль в Elasticsearch на 90 дней — „так проще дебажить“ — коды ошибок, redaction, TTL»

«100% traces на CRUD — APM = вторая прод-нагрузка — страх пропустить — гибридный сэмпл, 100% только деньги»

«40 дашбордов — ни один с деплой-аннотацией — платформенный „пакет Grafana“ — три роли, остальное удалить»

«ERROR на 404 — error ratio врёт, on-call слеп — status как level — 5xx и бизнес-fault раздельно»

«Свой формат вместо OTel — `http_status` в каждом сервисе — исторический агент — semantic conventions»

«Пропуск ticket-алерта — ловят только взрыв, не утечку 0,2% — „не шуметь“ — 1× / 3 дня (Workbook, Глава 26.2)»

«Observability без бюджета — 40% инфры, новые метрики каждую неделю — качество = больше точек — cardinality cap, freeze»

«Трейс без очереди — воркер не в графе — „HTTP покрыли“ — inject в metadata брокера»

«SSH как observability — grep по четырём нодам в SEV1 — агент не успели — минимум 25.8 до публичного URL»
