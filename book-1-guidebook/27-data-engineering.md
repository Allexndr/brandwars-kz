# Глава 27. Data engineering и аналитический контур

*Коротко. Операционный контур хранит инварианты и отвечает на «какой заказ сейчас». Аналитический — события, слои lakehouse и метрики, на которых решают. ML-контур ест те же события иначе: point-in-time фичи, не дашборд. Смешать три контура на одном Postgres — убить оплату дашбордом.*

*Глава: три контура и граница с OLTP; таксономия событий и валидация на ingest; batch vs stream; bronze/silver/gold и каталог Iceberg; dbt, оркестрация, тесты; контракты и lineage; стоимость данных.*

*OLTP, типы, бэкап, право на забвение в операционной БД — Глава 18. Метрики и A/B — Глава 28. Фичи для моделей — Глава 29.6. Privacy аналитики — Глава 33.*

Аналитика продукта ломается не в Snowflake. Она ломается на SDK, который шлёт `clicked_btn_3`, на джобе, который переписывает историю без `event_time`, и на дашборде, который читает primary. Warehouse без контракта — дорогое кладбище Parquet.

Вторая ошибка — стриминг «потому что real-time». Если решение принимают утром, часовой батч дешевле и воспроизводимее. Стрим оправдан, когда решение автоматическое и ценность падает за секунды: антифрод, персонализация, операционный алерт.

Третья — mesh как оргсхема без CI. Domain ownership в отраслевых обзорах 2026 — порядка 70%; self-serve платформа — ~25%, federated governance — ~20%. Load-bearing часть — контракт, который ломает PR продюсера, не слайд про «данные как продукт».

Для 1–3: typed SDK, 8–15 событий пути к ценности, выгрузка в warehouse (BigQuery/Snowflake/ClickHouse), dbt tests, bronze неизменен. Для 10–30: schema registry, freshness SLO, семантический слой, каталог с владельцем. Для 100+: Iceberg + REST-каталог, контракты в CI, оркестрация как платформа, FinOps на scan и на partition.

## 27.1. Архитектура данных продукта: операционный, аналитический и ML-контуры

Три контура, три SLO, три права на запись.

**Операционный (OLTP).** Источник правды заказа, баланса, сессии. Транзакция, ограничения, p99 в десятках миллисекунд. Модель — Глава 18. Сюда не кладут «все клики за год» и не считают North Star.

**Аналитический.** События продукта, CDC-снимки измерений, витрины, семантический слой. SLO — freshness (p99 ≤ N минут/часов) и воспроизводимость: любой агрегат пересчитывается из bronze. Читатели — люди, BI, эксперименты (Глава 28).

**ML.** Обучающие срезы и online-фичи с point-in-time семантикой. Тот же клик, что в аналитике, здесь — фича на момент t, без утечки будущего (Глава 29.6). Serving-latency — миллисекунды на lookup, не «дашборд за 30 с».

```
OLTP ──CDC/outbox──► bronze (immutable)
SDK events ─────────► bronze
                         │
                    silver (качество, ключи, SCD)
                         │
              ┌──────────┼──────────┐
           gold/marts   feature   exp assignment
           (BI, NSM)    store     (Глава 28)
```

CDC — однонаправленный. Аналитика не пишет в OLTP «чтобы поправить заказ». Исправление факта — событие коррекции или бэкфилл bronze по правилам, не UPDATE в витрине как истине.

Граница с Главой 18: идентификаторы, деньги, время в событиях подчиняются тем же типам (UUIDv7 как `event_id`, minor units, `timestamptz`). Моделирование звезды, Data Vault, OBT — здесь, не в Postgres заказа. Data Vault в silver имеет смысл при многих волатильных источниках и статутарном аудите; для mid-size SaaS с 5 источниками и dbt это over-engineering (отраслевой консенсус 2026). OBT — serving gold, выводится из звезды, не вместо неё: иначе пять определений revenue.

Outbox + CDC. Сначала transactional outbox, затем Debezium по таблице outbox, не «стримим строки `orders` и собираем `OrderPlaced` в консьюмере». Прямой CDC с таблиц даёт 1 заказ + 3 линии = 4 события вместо одного доменного. Когда CDC не нужен: один потребитель-батч с `WHERE updated_at > :ts`. Event sourcing как система записи — узкий класс (temporal queries, полный replay как требование), не дефолт аналитики.

Для 1–3: OLTP + выгрузка событий в один warehouse, без mesh. Для 10–30: отдельный ingest, replica OLTP не является warehouse. Для 100+: cell/shard OLTP (Глава 11) и lakehouse; сверка сумм OLTP↔gold — джоба, не « tap на primary».

Когда три контура рано сливать в «одну платформу»: команда ещё не отличила заказ от клика. Чем платите за раннее разделение: двумя пайплайнами. Сигнал ошибки: BI-запрос в `postgresql://primary`; фича модели считается SQL'ом по gold в момент предикта.

## 27.2. Сбор событий: таксономия, схемы, версионирование, качество на входе

Контур ломается на SDK. Warehouse только проявляет гниль.

Три слоя таксономии, не «список ивентов».

1. **Канонические глаголы** (годы стабильности): `Signed Up`, `Activated`, `Purchased`, `Invited`, `Churned`. Язык North Star (Глава 28.1).
2. **Доменные события** (версионируются): `InvoiceIssued`, `SearchPerformed`, `MessageSent`. Имя — прошедшее время, объект в центре. Схема = контракт.
3. **UI-телеметрия** (шум, короткий TTL): клики, импрессии, scroll. Нужна UX и ранжированию. Переименование кнопки не должно ломать retention.

Правила. Объект + действие + свойства: `project.created` с `project_id`, `source`, `template_id`. Не `clicked_create_project_modal`. На каждом событии: `user_id` или `anonymous_id`, `session_id`, `event_id` (UUIDv7), `event_time`, `ingest_time`, `app_version`, `schema_version`. Без `event_id` нет дедупа. Без пары времён поздние события молча портят воронки. Свойства типизированы, enum закрыт (`plan: free|pro|enterprise`). `revenue` — integer minor + `currency` ISO-4217, не float. PII по умолчанию не в properties: email/phone — identify-трейт, с retention. Отсутствие PII-тега ломает CI.

Версионирование — expand/contract, как API (Глава 14.3, Глава 15.4). Новое поле optional. Удаление — deprecation не короче одного аналитического квартала. Breaking — новая major, dual-write, потребители мигрируют. Имя события не «версия 2 в суффиксе навсегда».

Два полюса ingest. Snowplow: JSON Schema на событие, registry (Iglu), нарушение → bad-stream, в warehouse не попадает. Segment / мягкий CDP: Spec `track`/`identify`/`group`/`page`/`screen`; Protocols опциональны; мусор часто доезжает до таблиц. Практический минимум mid-size: typed SDK (TypeScript/Kotlin/Swift) + JSON Schema в CI клиента + collector отвергает неизвестный major. dbt tests — задняя линия: ловят гниль после того, как она отравила дашборд.

Проверки, которые ломают ingest или CI продюсера: schema vs registry; `event_time` не в будущем > N минут и не старше watermark без флага late; `user_id` XOR `anonymous_id`; уникальность `event_id` в окне дедупа; обязательные поля; enum; volume anomaly (−80% типа за 15 мин — сломанный SDK, релиз, adblocker, flag, не «тихий день»); denylist ключей `email`/`password`/`ssn`.

С дня 1: 8–15 событий пути к активации и NSM плюс identify. Не 200 «на всякий случай». У события: зачем (метрика/гипотеза), владелец, схема. Нет потребителя 90 дней — кандидат на удаление. Инструментирование как продуктовая дисциплина — Глава 28.3; здесь — пайплайн, который это не врёт.

Для 1–3: typed события в коде, один collector (PostHog/Snowplow mini/свой endpoint), bad-queue хотя бы в лог. Для 10–30: registry, алерт volume, запрет PII линтером. Для 100+: контракт at source ломает деплой сервиса.

Когда жёсткий schema-on-write вреден: день 1 стартапа, схема продукта меняется каждые двое суток — тогда typed SDK и неделя deprecation, не Iglu-процесс на 12 команд. Сигнал ошибки: аналитик правит `clicked_btn` в SQL двенадцатью CASE; или `event_time` заполняют `now()` на сервере ingest.

## 27.3. Batch и streaming: когда нужен реальный стрим, а когда достаточно часового батча

Вопрос не «Kafka или нет». Вопрос: какое решение по этим данным и за какое время оно теряет ценность. «Дашборд смотрят утром» — батч. Стрим добавляет state, exactly-once, late data, replay — порядок 3–5× инженерии против батча (отраслевые сравнения; ваш множитель проверьте).

| | Batch | Streaming |
|---|---|---|
| Latency | минуты–часы | секунды |
| Стоимость инженерии | 1× | 3–5× |
| Отладка | воспроизводимо | нужен replay |
| Когда | отчётность, обучение, витрины | антифрод, персонализация, операционный алерт |

Micro-batch 1–5 минут закрывает большинство требований, которые слайд называет real-time: лента метрик, «пользователь только что оплатил — обновить сегмент». Настоящий стрим: решение автоматическое, ценность падает за секунды.

Стек на 2026. Лог — Kafka (или managed: MSK/Confluent; diskless-линия KIP-1150 — Глава 13, не дефолт аналитики). Stateful processing — Flink. Если уже Spark — Structured Streaming, не второй рантайм «для моды». Streaming SQL как materialized views — RisingWave/Materialize, когда команда думает SQL, не job graph. Не ставить Flink, чтобы кормить часовой dbt.

Late data. Watermark + side output опоздавших. Молчаливый drop — дыра в воронке. Молчаливый overwrite gold без версии — дыра в аудите. Правило: bronze хранит как пришло; silver помечает `late=true`; gold пересчитывается в согласованном окне (час/день), не «строка уже уехала в CEO-дашборд».

Идемпотентность консьюмера: ключ `event_id`, upsert, не «append и надеемся». Exactly-once end-to-end — маркетинг брокера; на практике at-least-once + дедуп в sink. Сверка объёма SDK → bronze → gold ежедневно.

Для 1–3: hourly/daily batch, без Kafka. Для 10–30: micro-batch или один стрим на антифрод, остальное батч. Для 100+: стрим только на контурах с автоматическим решением; аналитика NSM остаётся батчем с SLO freshness.

Когда стрим вреден: обучение модели раз в сутки; финансовый отчёт; «хотим живой дашборд» при 200 событиях/мин. Чем платите: двумя режимами отказа и невозможностью бэкфилла без replay-кластера. Сигнал ошибки: один Flink job «на всё»; или стрим, который нельзя переиграть за вчера.

## 27.4. Хранилище и lakehouse: слои сырых, очищенных и витринных данных

Medallion — не названия папок. Правило: **bronze неизменен**. Ошибка трансформации чинится пересчётом, не UPDATE сырого.

**Bronze.** Сырой payload, `ingest_time`, id прогона, версия схемы. Replay-able. Партиция по времени ingest. Retention — политика (Глава 18.6 / 33), не «вечно на hot».

**Silver.** Дедуп, ключи, типизация, качество, соответствие контракту. Здесь уместны интеграция источников и, если нужен, Data Vault. Аналитики silver напрямую не любят — и не должны, если gold честный.

**Gold.** Звезда / узкий OBT под дашборд и семантический слой. Метрика определяется один раз (dbt Semantic Layer, Cube, AtScale) и уходит в BI, в эксперименты и в AI-запросы. Без слоя — «пять revenue». Колоночное сжатие и zone maps в Snowflake/BigQuery/ClickHouse сделали стоимость широкой таблицы низкой; аргумент «денормализация дорогая» в serving-слое 2026 слабый. Фундамент всё равно звезда, OBT — проекция.

Форматы. На 2026 год файловая война закончилась перемирием: Apache Iceberg — нейтральный стандарт интероперабельности (гиперскейлеры, Snowflake, Databricks читают/пишут). Delta — дефолт внутри Databricks/Fabric; UniForm пишет Iceberg-метаданные без перезаписи Parquet. Hudi — ниша upsert-heavy CDC; не мигрировать «потому что Iceberg модный», если ingest уже Hudi. Iceberg v3: deletion vectors, row tracking, VARIANT. XTable/UniForm делают выбор обратимым на метаданных. Adoption-опросы расходятся (Ventana/ISG: 51% активно внедряют Delta, 27% перешли на Iceberg; у Iceberg ~вдвое больше уникальных PR-авторов) — инкумбентность ≠ momentum.

Стратегический слой — каталог, не Parquet. Iceberg REST Catalog — де-факто API.

- **Apache Polaris** (Snowflake Open Catalog = managed): credential vending, conflict resolution, multi-table commits, OAuth2. Когда движков несколько (Spark + Trino + Flink) и метаданные не должны принадлежать одному compute-вендору.
- **Unity Catalog**: Delta + Iceberg + Hudi + файлы; ACL, lineage, Delta Sharing. К августу 2026 Managed Iceberg / Iceberg v3 / Foreign Iceberg — GA. Гравитация Databricks: каталог лучше всего живёт, когда compute тоже там.
- **AWS Glue REST / S3 Tables**: IAM + Lake Formation. На июнь 2026 в обзорах каталогов: дыры REST (`UpdateTable`, CreateTable v3, credential vending), один уровень namespace, нет branching. S3 Tables — вендорские «до 10× TPS» vs ordinary buckets, проверять.
- Hive Metastore — только federated legacy.

Правило: один source of commit на таблицу, много source of query. Два writer'а в разные каталоги на одни файлы — split-brain. Federation (Glue → Unity через `DATABRICKSICEBERGRESTCATALOG`) — чтение без копии, не второй writer.

Движок запросов. ClickHouse — событийная аналитика, sub-second, cost-performance; CostBench (ClickHouse, 2026, вендорский, методология открыта): на 100 млрд строк ближайший конкурент порядка 23× хуже по `runtime × cost`; оговорка — профиль governed concurrency, где силён Snowflake. BigQuery — serverless, capacity дешевле on-demand на больших сканах. Snowflake — много изолированных потребителей и governance. DuckDB — CI трансформаций и ноутбук, не прод-OLTP. Не класть ClickHouse на путь оплаты (Глава 18.4).

Для 1–3: один managed warehouse, три схемы bronze/silver/gold, без своего каталога. Для 10–30: Iceberg или нативный формат склада, партиции, lifecycle. Для 100+: REST-каталог, federation, запрет второго writer.

Когда lakehouse рано: 20 ГБ событий — хватит склада без Iceberg-ops. Сигнал ошибки: аналитик правит parquet руками; gold считается прямым SELECT из bronze в Looker; VACUUM/compaction никто не включил, мелких файлов миллион.

## 27.5. Трансформации и оркестрация: моделирование, тесты данных, документация

dbt — дефолт трансформаций 2026. SQLMesh — претендент (virtual environments, column-level lineage); менять dbt «потому что lineage» имеет смысл на боли, не на конференции. Модели: staging из bronze → intermediate silver → marts gold. Документация в репозитории рядом с SQL: владелец, определение метрики, grain. Каталог без этого — мёртвая витрина имён.

Тесты. dbt `not_null`, `unique`, `relationships`, `accepted_values`, custom — дефолт day-one, но реактивны: плохое уже в таблице. Model contract `enforced: true` (dbt) ломает build, если колонка пропала или сменила тип — ближе к API. Контракт источника (27.6) ломает продюсера раньше. Сборка: контракт на ingest + contract на gold + tests на инварианты + observability на неизвестное. Три тула на один `unique` хуже дыры на ingest.

Качество по слоям: Elementary — дешёвый anomaly detection на dbt (~2 недели setup, порядка 4 ч/мес). Great Expectations — Python/Spark вне warehouse. Soda — YAML для аналитиков. Monte Carlo / Anomalo — managed, $50–200k/год, окупается при 20+ дата-инженерах и нескольких складах (экономия 1–2 FTE — порядок вендорских кейсов). Валидация ловит известное на деплое; observability — неизвестное в проде (volume, null-rate, freshness вне baseline).

Оркестрация. Airflow — enterprise-инкумбент (~46,3k GitHub stars против Prefect ~23,5k и Dagster ~15,9k, срез ресерча 2026). Airflow 3.x — asset-centric. Dagster выигрывает greenfield dbt-heavy (asset lineage). Prefect — команды 20–100 без желания администрировать Airflow. Prefect приобрёл Dagster (2026, сверять первоисточник на дату чтения): смена владельца roadmap не меняет покупателя инструмента. Новая арена — оркестрация агентов, где форы Airflow нет. Для 1–3: расписание склада + dbt Cloud/CI, без своего Airflow.

Бэкфилл — рутина, не инцидент. Идемпотентный запуск по партиции даты. Без этого «починили баг в CASE» означает неделю вранья в дашбордах и невозможность пересчитать эксперимент.

Документация, которую читают: grain модели (`one row = one invoice line`), окно late data, join-ключи, известные дыры («iOS < 7.2 не шлёт X»). Не роман в Confluence.

Для 1–3: dbt + tests + ежедневный run. Для 10–30: contracts, Elementary, оркестратор, бэкфилл-runbook. Для 100+: платформенный golden path (Глава 24.8), запрет трансформаций вне репозитория.

Когда оркестратор вреден: три модели, cron склада достаточен. Сигнал ошибки: логика метрики в LookML, в dbt и в ноутбуке DS одновременно; бэкфилл = «удалим таблицу и надеемся».

## 27.6. Data contracts, governance, каталог, происхождение данных

Контракт — единственная нехрупкая часть mesh. Версионирован: схема, SLO качества, условия использования, доступ. Нарушение ломает CI продюсера. Термин: Andrew Jones, GoCardless, 2020–2021; через ~6 месяцев — порядка 30 контрактов, 50–60% async-событий. К 2025 — книги Jones / Sanderson и native dbt contracts. Linux Foundation консолидирует спецификации — следить за версией, не за брендом тула.

Минимальный YAML: имя, владелец, типы, PK, uniqueness, freshness SLO (p99 ≤ X мин), volume floor, PII-теги, changelog, consumers. Freshness — пейджер владельца, не тикет в «платформу».

Где ловить:

| Слой | Что | Когда |
|---|---|---|
| Typed SDK / registry | форма события | CI клиента |
| Contract at source | breaking продюсера | ingest / деплой сервиса |
| dbt model contract | shape витрины | preflight build |
| dbt tests | семантика | post-run |
| Observability | неизвестное | прод |

Каталог (DataHub, OpenMetadata, Unity). Минимальный набор, без которого он мёртв: владелец не пустой, SLO свежести, определение метрики, upstream/downstream, PII-тег. Lineage до колонки — на критичных путях (revenue, эксперименты, фичи фрода), не «весь граф компании в год проекта».

Governance. Policy-as-code: «PII домена finance видят роли X, остальным маска». Mesh без этого — 200 схем и swamp. Гибрид 2026: mesh (владение) + fabric (метаданные) + lakehouse (хранение); >60% начинавших с чистого mesh или fabric сошлись на гибриде (отраслевые обзоры).

Сверки аналитики (операционные сверки денег — Глава 18.5): count событий SDK vs bronze; сумма `Purchased.amount` vs OLTP paid за сутки; уникальные `user_id` vs таблица users. Расхождение сверх порога — инцидент владельца контура, не «подкрутим коэффициент в дашборде».

Для 1–3: README владельца и dbt tests, без mesh. Для 10–30: контракты на внешние для домена датасеты, каталог. Для 100+: policy-as-code, column lineage на деньгах и ML.

Когда контракт вреден: внутренний черновик фичи на двоих на неделю — хватит typed SDK. Сигнал ошибки: каталог из crawler'а без владельцев; breaking schema в пятницу, дашборды пустые в понедельник.

## 27.7. Стоимость данных и как не построить дорогое кладбище

Единица стоимости аналитики — scan, storage температуры, shuffle, и FTE, который чинит «пять revenue». Не «кластер красивый».

Рычаги. Партиции и predicate pushdown: запрос дня не читает три года. Lifecycle: bronze старше окна replay — cheaper class / Iceberg expire snapshots. Не хранить UI-телеметрию (слой 3) с TTL заказа. Материализация gold vs on-the-fly: если дашборд бьёт склад каждый refresh — OBT/pre-agg; если смотрят раз в неделю — не копировать. Capacity vs on-demand в BigQuery: on-demand на больших сканах даёт худшие цифры CostBench-класса. ClickHouse выигрывает cost-performance на событийном профиле; Snowflake — когда платите за isolation потребителей, не за одну query latency. Цифры CostBench (2026, вендор ClickHouse) не копировать в слайд TCO без своего replay.

Кардинальность событий. 200 имён × свободные строковые свойства × вложенный JSON без схемы — плата за scan и за людей. Резать слой 3. Сэмплировать телеметрию (1:10 импрессий) при 100% канонических глаголов.

Наблюдаемость склада. Freshness, failed runs, scan bytes на модель, слот-время. Алерт «модель сканирует 10× baseline» — как cardinality в Главе 25.4. Без этого BI «просто тормозит», а счёт вырос втрое.

Кладбище. Таблица без владельца, без потребителя 90 дней, без контракта — TTL или архив. Ноутбуки, пишущие в prod-схему. «Временная» витрина двухлетней давности. Второй warehouse «для DS», который никто не сверяет с gold.

Связь с юнит-экономикой (Глава 7) и FinOps (Глава 22): cost per MAU аналитики и cost per обученный срез должны быть видны. Иначе data platform оптимизируется как demo.

Для 1–3: один склад, TTL сырых 90 дней, не строить lake. Для 10–30: бюджет scan на команду, lifecycle. Для 100+: chargeback по домену, запрет SELECT * в gold из BI-тулов.

Когда экономить вредно: выкинуть bronze и потерять replay эксперимента. Чем платите за вечный hot bronze: счётом и GDPR-поверхностью. Сигнал ошибки: склад дороже продукта; или «данных много, решений нет» — нет семантического слоя и владельцев, не «мало Spark».

## 27.8. Чек-лист аналитического контура

**Границы**

- [ ] OLTP не обслуживает BI-сканы; CDC/outbox однонаправленный (Глава 18).
- [ ] Bronze immutable; бэкфилл — штатный запуск по партиции.
- [ ] ML-фичи не считаются ad-hoc по gold в момент предикта (Глава 29.6).

**События**

- [ ] Три слоя таксономии; канонические глаголы стабильны.
- [ ] `event_id`, `event_time` ≠ `ingest_time`, typed SDK, schema в CI.
- [ ] PII-тег обязателен; отсутствие ломает CI; denylist на ingest.
- [ ] Volume anomaly по типу события алертит за 15 мин.

**Склад и трансформации**

- [ ] Silver/gold из bronze пересчитываются; метрики в семантическом слое один раз.
- [ ] Один source of commit на таблицу lakehouse; каталог выбран (Polaris / Unity / Glue) или явно «managed warehouse без Iceberg».
- [ ] dbt tests + contract на gold; observability на freshness/null/volume.
- [ ] У датасета владелец и freshness SLO; пейджер не в «платформу».

**Стоимость и право**

- [ ] TTL/температура bronze и слоя 3; scan budget.
- [ ] Lineage до колонки на revenue, экспериментах, фроде.
- [ ] Сверка SDK↔bronze↔gold↔OLTP по суткам.
- [ ] Ретеншн и erasure аналитики в реестре ДСР (Глава 33), не «склад вечный».
