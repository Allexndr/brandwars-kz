# Глава 14. API, контракты и платформенная стратегия

*Коротко. API — граница, которую нельзя чинить тем же деплоем, что и вызывающий код. Эта глава задаёт дизайн, выбор протокола, версии, schema-first контракты и публичный API как продукт.*

*Топология платформы (gateway, квоты, вебхуки как контур) — Глава 13, раздел 13.5. Здесь — контракт: ресурсы, ошибки, идемпотентность, совместимость, DX, чужие интеграции. Надёжность вызова — Глава 12. Стиль сервисов — Глава 10.*

*Фаундеру нужна, когда появляется второй клиент (мобильный, партнёр, агент). Техлиду — чтобы команды не изобретали свой JSON ошибок. Staff — чтобы версия и LRO не стали неотменяемым долгом на пять лет.*

*Возвращайтесь перед публикацией внешнего URL, перед сменой протокола «потому что GraphQL», перед интеграцией платежей.*

*Чек-лист 14.8 — гейт публикации. Пока он красный, это внутренний API, даже если ключ уже у партнёра.*

Внутренний RPC и публичный API различаются ценой ошибки в контракте. Внутри можно выкатить клиента вместе с сервером. Снаружи чужой код, чужой релизный цикл, иногда чужой регулятор. Ломающий ответ 400 вместо 404 на «ресурс не найден» — инцидент у них, тикет у вас на годы.

Вторая цена — протокол как религия. REST, gRPC, GraphQL, WebSocket, вебхуки решают разные задачи. Airbnb с 2024 частично ушла с GraphQL на REST: CDN не кэшировал POST, авторизация росла нелинейно со схемой. Shopify в октябре 2024 наоборот задепрекейтил REST Admin API для новых приложений. Оба правы на своём профиле. Неправы те, кто копирует итог без профиля.

Третья — версия как декорация. `/v1/` в URL без политики совместимости — номер в пути, не стратегия. Google AIP-185: мажор в URI и в protobuf-пакете, channel-based (alpha/beta/stable) предпочтительнее ленты `v1beta1`, `v1beta2`; с beta — разумные 180 дней на переход. AIP-151: долгая операция (>~10 с) — стандартный `Operation`, не свой тип; жизнь Operation — 30 дней; смена `response_type`/`metadata_type` — breaking.

На 2026 год дефолт публичного surface — REST + OpenAPI 3.1 + HTTP/3 там, где доезжает; gRPC — east-west; GraphQL — BFF/агрегация; SSE — стрим модели; вебхуки — исходящие события. Оценки «83% публичных API — REST» и доли GraphQL расходятся в разы (вендор-adjacent, направление, не число). Принцип переживает долю: один стиль на один сценарий, гибрид — явным ADR.

## 14.1. Дизайн API: ресурсы, действия, ошибки, идемпотентность, пагинация, фильтрация

Ресурс — существительное с идентификатором и жизненным циклом. Действие — глагол, который не влезает в CRUD без лжи (`POST /charges/{id}/refund`). Смешивать «всё глаголы» (RPC-поверх REST) и «всё ресурсы» в одном API — заставить клиентов гадать.

Идентификаторы: UUIDv7 как дефолт внутренних ключей (RFC 9562, PG 18 нативно); публичный id может быть непрозрачным и не обязан светить время создания. Не использовать автоинкремент в URL: перечисление, утечка объёма.

Ошибки. Машиночитаемый стабильный `code`, нестабильный `message`, `details`, `request_id`. RFC 9457 Problem Details — разумный дефолт REST. HTTP-статус несёт класс (4xx клиент, 5xx вы), `code` — ветвление клиента. Не парсить `message`. 404 vs 403 на чужом ресурсе: в мультитенанте чаще 404, чтобы не светить существование; зафиксировать единожды.

Идемпотентность. GET, PUT, DELETE — по семантике HTTP. POST создания платежа, отправки, списания — ключ. `Idempotency-Key` не RFC: черновик истёк 18 апреля 2026. Документируйте свою семантику. Stripe как референс: ключ до 255 символов, рекомендуется UUIDv4, скоуп — аккаунт/песочница, retention v1 ≥24 ч, v2 30 дней, повтор помечается `Idempotent-Replayed: true`. Сохраняется **результат**, не запрос: повтор честного 500 честно вернёт 500. Иначе клиент ретраит и получает другой мир. Черновик предлагал 409 на in-flight и 422 на несовпадение fingerprint. Разнобой имён: PayPal `PayPal-Request-Id` (45 дней), Twilio `I-Twilio-Idempotency-Token`, Square — поле в теле. Если публикуете — один заголовок, одна retention, одна ошибка на конфликт.

Пагинация. Курсор непрозрачный, со схемой сортировки внутри (версия включена). Offset запрещён на больших коллекциях: деградирует линейно и прыгает при вставках. `limit` с потолком (типично 100–200, не «сколько просите»). Стабильная сортировка обязана включать уникальный ключ, иначе курсор дублирует строки.

Фильтрация и сортировка. Белый список полей. Запрет произвольного SQL-подобного фильтра в query string. Поиск — отдельный ресурс или отдельный протокол (13.2), не `GET /everything?q=`. Поля ответа: sparse fieldsets допустимы; не строить весь API вокруг «клиент сам выберет граф» — это уже GraphQL со своими ценами.

Long-running. Если p99 > ~10 с — не держать HTTP открытым минутами. AIP-151: вернуть `Operation`, клиент поллит или подписан на вебхук completion. Свой `job_id` в уникальном JSON без стандартных полей ломает единообразие SDK.

Когда «ресурсная REST-чистота» вредна: командный RPC из 30 внутренних методов без жизненного цикла. Тогда gRPC и честные RPC-имена, не `/doAction`. Чем платите за строгий ресурсный стиль: иногда неестественными `POST …:cancel`. Сигнал ошибки: два способа создать сущность; ошибки без `code`; POST без ключа на деньгах.

Для 1–3: один стиль, Problem Details, курсор, ключ на мутациях денег. Для 10–30: линт OpenAPI в CI, запрет offset, стандарт LRO. Для 100+: AIP-подобные правила как fitness function (Глава 10.7), не вики.

## 14.2. Выбор протокола: REST, gRPC, GraphQL, WebSocket, вебхуки — по сценариям

Не «что победило», а какая единица обмена и кто клиент.

**REST/JSON по HTTP.** Публичный API, браузер, мобильный клиент, кэшируемые GET, нулевой порог. OpenAPI 3.1. HTTP-кэш и CDN работают на GET. Когда: внешние интеграторы, партнёры, CRUD. Когда нет: внутренний hot-path с protobuf-нагрузкой; подписка на поток событий (это не GET с long poll в 2026).

**gRPC.** East-west: HTTP/2, protobuf, стримы, кодоген. Выигрыш 7–10× на serialization-heavy (отраслевые замеры, не ваш бенчмарк — мерить). Браузеру нужен gRPC-Web или шлюз. HTTP/3 в gRPC на 2026 экспериментален. Когда: сервис–сервис, низкая латентность, строгая схема. Когда нет: публичный API для PHP-интегратора; первый продукт соло-фаундера.

**GraphQL.** BFF: один круг на экран, агрегация поверх REST/gRPC. Federation — стандарт мультикомандного графа; операционная цена federation — отдельный runtime. Обязательны persisted queries, DataLoader/batch, лимит сложности, таймаут. Без них — как Airbnb: CDN-дырки на POST, нелинейная авторизация. Shopify принудил GraphQL на Admin — у них клиенты-приложения и гибкий граф админки как продукт. Когда: разнородные клиенты, много вложенности, команда готова нести граф. Когда нет: платежи, вебхуки, публичный кэшируемый каталог.

**tRPC.** TypeScript-монорепо, нет публичного контракта для чужого языка. Когда: внутренний BFF в одном репо. Когда нет: внешний API.

**WebSocket.** Двусторонний интерактив: чат, коллаб, live-дашборд. Один упорядоченный поток, HoL. Проходит там, где HTTPS. Не замена REST на CRUD. Presence/typing — поверх, с правом выключить (13.4).

**SSE.** Сервер→клиент, авто-reconnect. Дефолт LLM-стриминга 2026. Когда: токены модели, прогресс job. Когда нет: клиент должен слать непрерывный ввод — тогда WS или REST+WS.

**WebTransport.** Baseline март 2026. Много потоков + datagrams, без HoL, миграция соединения. Не «WebSocket на QUIC»: порт WS-протокола на один стрим выбрасывает смысл. UDP/443 фильтруется — fallback обязателен (Глава 21).

**Вебхуки.** Исходящие события партнёру. Не протокол входа. Контракт: подпись, timestamp, at-least-once, `event_id`, ретраи с jitter, DLQ, сверка. Партнёр отвечает 2xx быстро. Poll как замена вебхуков взрывает вашу квоту и их латентность.

Матрица без таблицы на десять строк: внешний CRUD → REST; внутренний hot → gRPC; экран с 12 сущностями → GraphQL/BFF или BFF-REST; стрим токенов → SSE; чат → WS; партнёр «скажи, когда готово» → вебхук; агент/MCP → HTTP request/response (MCP 2026-07-28 stateless, заголовки `Mcp-Method`/`Mcp-Name`).

Когда менять протокол: измеренный профиль (кэш miss, payload, fan-out полей), не конференция. Чем платите за гибрид: двумя SDK и двумя моделями ошибок. Сигнал ошибки: GraphQL на checkout; gRPC торчит в интернет без шлюза; вебхук без подписи.

## 14.3. Версионирование и обратная совместимость: правила и автоматические проверки

Совместимость — свойство ответа и схемы, не номер в URL. Номер нужен, когда совместимость сознательно ломают.

AIP-185 (Google): мажорная версия — первый сегмент URI и конец protobuf-пакета. Channel-based: alpha / beta / stable обновляются in-place. Release-based (`v1beta1`, `v1beta2`) плодит вечный зоопарк. Beta обязана дать переходный период — рекомендация 180 дней. Stable не ломают: только новая мажорная.

Что считается breaking: удаление поля; смена типа; смена семантики поля при том же имени; обязательность бывшего optional; смена кода ошибки, на который ветвятся клиенты; смена `response_type` LRO; переименование ресурса; default, который меняет поведение старых клиентов.

Что не breaking: новое optional поле; новый endpoint; новый код ошибки при старом HTTP-классе, если клиенты обязаны игнорировать неизвестное; новое значение enum, если клиент трактует unknown как unknown (зафиксировать).

Правило клиента: игнорировать неизвестные поля. Правило сервера: не переиспользовать имена. Переименование = новое поле + deprecation старого (expand/contract, Глава 15.4), не «в том же релизе».

Автоматические проверки. OpenAPI/Protobuf diff в CI: breaking → красный, кроме bump мажора. Контрактные тесты провайдера против замороженных клиентов (Pact / schema registry). Для GraphQL — `graphql-inspector` / equivalent: удаление типа — break. Для gRPC — buf breaking. Fitness function: «PR не может удалить поле v1 без ADR и даты sunset».

Sunset. Дата в заголовке `Sunset` / в docs, метрика usage версии, письма за 180/90/30 дней. Выключение без метрики «кто ещё на v1» — инцидент. Песочница выключается раньше прода — чтобы сломать интегратора в sandbox, не в Black Friday.

Когда версия вредна: внутренний API трёх сервисов одной команды с совместным деплоем — хватит схемы и CI, без `/v3/`. Чем платите за ранний `/v1/` публично: поддержкой v1, пока жив последний интегратор. Сигнал ошибки: две мажорные без changelog; breaking в patch; «совместимы, просто поправьте клиент».

Для 1–3: одна версия, additive-only, changelog. Для 10–30: buf/openapi-diff в CI, 180 дней на beta. Для 100+: каналы alpha/beta/stable, sunset-метрики, compatibility SLA в договоре.

## 14.4. Контракты между командами: schema-first, генерация клиентов, contract tests

Контракт — артефакт, который ломает CI продюсера, не Slack потребителя. Data contracts (GoCardless, Jones, 2020–2021: за ~6 месяцев ~30 контрактов) — тот же принцип на событиях; здесь — RPC/HTTP.

Schema-first. Сначала OpenAPI / Protobuf / GraphQL SDL, потом код. Code-first допустим, если схема **генерируется и проверяется** в CI как канон; иначе канон — «как получилось в runtime». На 2026 год: protobuf для gRPC, OpenAPI 3.1 для REST, SDL для GraphQL. JSON Schema на события. Не держать три канона на один API.

Генерация клиентов. Официальный SDK = генератор + тонкий слой (аутентификация, ключ идемпотентности, ретраи с jitter, пагинация). Ручной клиент расходится за спринт. Языки SDK — по доле интеграторов, не «все на свете»: обычно Python, TypeScript, Go, Java; остальные — сгенерированный spec. Версия SDK следует политике API: breaking SDK только с мажором API или с явной major SDK при том же API.

Contract tests. Потребитель пишет ожидание (запрос → ответ). Провайдер прогоняет против своего сервера в CI. Pact — один инструмент; принцип: ожидание версионировано, ломается продюсер. На событиях — schema registry (Avro/Protobuf) + запрет incompatible evolution. Overlay: typed SDK ловит форму на компиляции; contract test ловит семантику «этот статус ещё существует»; e2e ловит сборку. Три тула на один `unique` хуже дыры на ingest.

Когда schema-first тормозит: спайк на один день, один потребитель, схема ещё неизвестна. Тогда черновик, но публичный URL не отдавать. Чем платите за schema-first: часом на spec до кода. Сигнал ошибки: клиент написан руками по памяти полей; breaking всплывает на проде потребителя.

Для 1–3: OpenAPI в репо, сгенерированный TS-клиент для своего фронта. Для 10–30: buf/openapi в CI, Pact на 3–5 критических интеграций. Для 100+: registry, ownership на каждый контракт, SLO совместимости.

## 14.5. Публичный API как продукт: ключи, лимиты, тарификация, документация, DX

Публичный API имеет North Star не «число эндпоинтов», а successful integration time и долю вызовов 2xx без ретраев по вашей вине. DX — продукт: ключ за минуту, первый 200, понятная ошибка, тест в sandbox.

Ключи. Секрет хранится у клиента, у вас — хэш + префикс для отображения (`sk_live_…abcd`). Ротация без даунтайма: два ключа живы, старый expire. OAuth2/OIDC для действий от имени пользователя; ключ — для server-to-server. Не один «мастер-ключ аккаунта» на все scopes. Утечка ключа: revoke, audit, ротация; не «поменяйте в письме».

Лимиты. Token bucket как дефолт (13.5). Документировать: capacity, refill, заголовки остатка, что считать (запрос, сложность GraphQL, байты). Отдельные лимиты на sandbox, на webhook retries, на list-эндпоинты. Fair use: взрывной клиент изолируется, не кладёт соседей (bulkhead, Глава 12.2).

Тарификация. Usage-based: метр должен совпадать с тем, что видит биллинг (Глава 6, 40). Документировать, что считается билable: 4xx по вашей вине — нет; 429 — нет; 5xx — нет. Иначе DX-война. Free tier без cap на list/search — дыра unit-экономики (Глава 7).

Документация. Diátaxis: tutorial (первый ключ), how-to, reference из OpenAPI, explanation (идемпотентность, вебхуки). Reference, который пишут руками и расходится со схемой — дефект. Changelog с датой, breaking отдельно. На 2026 год портал + OpenAPI + postman/insomnia collection из той же схемы. Принцип: одно source of truth.

DX-метрики: время до первого 200; доля ошибок 4xx с `code`, который есть в docs; tickets «как сделать X» на эндпоинт без примера; лаг SDK за релизом API. Status page и SLA публичного API — отдельно от внутреннего: партнёр не читает ваш Grafana.

Когда API «как продукт» рано: один партнёр, ручной onboarding, контракт в PDF. Тогда не строить портал — построить контракт и ключи. Чем платите за ранний портал: поверхностью, которую стыдно выключить. Сигнал ошибки: ключ в логах; лимит только в nginx; docs с полями, которых нет в OpenAPI.

## 14.6. Экосистема разработчиков: SDK, песочница, партнёрская программа, ревью приложений

Экосистема появляется, когда чужой код создаёт ценность на вашем API. До этого «DevRel» — рассылка changelog.

SDK. См. 14.4. Дополнительно: семантическое версионирование, changelog, support window (N мажорных). Beta SDK не для прод-ключей без явного opt-in.

Песочница. Отдельные ключи (`sk_test_`), отдельные данные, отдельные вебхуки. Сброс sandbox — документированная операция. Нельзя: sandbox, который пишет в прод-очередь «почти никогда». Тестовые карты/события — фиксированный набор. Clock sandbox для подписок: ускорение времени, иначе партнёр не проверит renewal.

Партнёрская программа. Scopes, лимиты выше, поддержка, listing. Договор: кто виноват при 5xx, куда идут ПДн, право отозвать приложение. Метрика: доля GMV/MAU через партнёров vs стоимость ревью.

Ревью приложений. Для маркетплейса приложений: минимальный набор — OAuth scopes не шире нужного, политика данных, отсутствие скрытых запросов, версия API не sunset. Ревью — очередь со SLA, иначе экосистема душит сама себя. Отзыв приложения — runbook, как инцидент.

Когда программа вредна: PMF не доказан, а вы строите App Store. Чем платите: модерацией чужого UX. Сигнал ошибки: приложения в листинге на deprecated API; sandbox = прод с флагом.

Для 1–3: сгенерированный клиент, test-ключи. Для 10–30: sandbox, 2–3 SDK, changelog. Для 100+: партнёрский листинг, ревью, DevRel как канал (Глава 43).

## 14.7. Интеграции с внешними системами: надёжность, повторы, сверки, деньги

Исходящая интеграция — чужой API как зависимость с чужим SLO. Каркас: адаптер, таймаут, идемпотентность, журнал, сверка. Не вызов Stripe «прямо из хендлера заказа» без outbox.

Надёжность. Таймаут на каждый вызов (Глава 12.3). Ретраи только на одном уровне, capped exponential + jitter; не ретраить 4xx кроме 409/429 по правилу. Circuit breaker не первый инструмент: AWS Builders' Library предупреждает о модальном поведении; начинать с token bucket на ретраи. Идемпотентность на вашей стороне: свой ключ к ним (Stripe-ключ, PayPal-Request-Id).

Деньги. Outbox: состояние заказа и «намерение списать» в одной транзакции БД; реле публикует; вебхук провайдера — второй вход, должен сходиться с тем же `payment_id`. Двойная запись «сначала они, потом мы» без журнала — потеря денег при краше. Сверка: ежедневный файл/API провайдера vs ваша книга, до цента, с владельцем расхождения. Без сверки «идемпотентность» — вера. Подробности биллинга — Глава 40; здесь архитектурный минимум.

Вебхуки входящие. Проверять подпись, timestamp, идемпотентность `event_id`, отвечать 2xx до тяжёлой работы (очередь). Повтор вебхука — норма. Порядок событий не гарантирован — проектировать от факта, не от «сначала authorized, потом captured».

Чужой лимит. Их 429 — ваш backpressure. Не усиливать штормом. Очередь исходящих с rate limit под их bucket.

Когда не интегрировать напрямую: нет идемпотентности у них и нет сверки — не класть деньги на этот канал без ручного контура. Чем платите за адаптер: задержкой фичи. Сигнал ошибки: ретраи из cron и из хендлера одновременно; нет сверки; секрет провайдера в git.

## 14.8. Чек-лист публикации внешнего API

Гейт. Пока пункты красные — URL внутренний.

**Контракт**

- [ ] OpenAPI 3.1 / protobuf / SDL — канон в репозитории; docs собраны из него.
- [ ] Ресурсы и действия согласованы; нет двух способов создать одну сущность.
- [ ] Ошибки: RFC 9457 или эквивалент; стабильный `code`; `request_id`.
- [ ] Курсорная пагинация; offset нет на публичных списках; `limit` с потолком.
- [ ] POST денег/отправки требует Idempotency-Key; retention и повтор (включая 500) задокументированы.
- [ ] LRO длиннее ~10 с — стандартный Operation / job + вебхук, не открытый HTTP на минуты.

**Совместимость и версии**

- [ ] Политика версий записана (AIP-185 или эквивалент); breaking определён списком.
- [ ] CI ломается на breaking без bump мажора (buf / openapi-diff / inspector).
- [ ] Клиенты обязаны игнорировать неизвестные поля; это в tutorial.
- [ ] Sunset: метрика usage версии, окно ≥180 дней для beta/stable-ломания.

**Платформа**

- [ ] Ключи хэшируются; префикс для UI; ротация без даунтайма; scopes.
- [ ] Token bucket; заголовки остатка; fail open; отдельные лимиты sandbox.
- [ ] Вебхуки: HMAC+timestamp, `event_id`, jitter-ретраи, DLQ, портал replay, сверка.
- [ ] Sandbox изолирован данными и ключами от prod.
- [ ] Usage-метр совпадает с биллингом; 429/5xx не билable.

**DX и безопасность**

- [ ] Tutorial до первого 200 < 15 минут на чистой машине.
- [ ] Официальный клиент сгенерирован + ретраи/идемпотентность; версия следует политике.
- [ ] Модель угроз: утечка ключа, replay вебхука, перечисление id, IDOR (Глава 32).
- [ ] SLA/status page публичного API названы; on-call знает, что это внешний контракт.
- [ ] Пункт 13.5 выполнен: тенант-роутинг, квота, не «nginx на IP».

## Антипаттерны

«RPC под видом REST — POST /doStuff на всё — проще серверу — либо честный gRPC, либо ресурсы и :customVerb по AIP»

«Offset на миллионах — page=50000 — SQL знакомый — непрозрачный курсор с версией сортировки»

«Идемпотентность хранит запрос — повтор 500 даёт 201 — „повторить значит попробовать ещё“ — хранить результат, как Stripe»

«Свой LRO — {jobId, status} уникальной формы в каждом сервисе — казалось быстрее — AIP-151 Operation»

«GraphQL без лимита сложности — как Airbnb до отката — один граф на все экраны — persisted queries, DataLoader, BFF только там, где экран»

«Версия в URL без политики — /v1/ вечно ломают в patch — цифра успокаивает — AIP-185 + diff в CI»

«Вебхук без подписи и сверки — партнёр доверяет IP — быстрее запустились — HMAC, event_id, ежедневный cursor»

«Лимитер fail closed — Redis лег, API 503 — строгость квот — fail open + локальный бакет»

«Docs руками — поле в гайде, которого нет в OpenAPI — портал красивый — docs из схемы»

«Прямой вызов платежа из хендлера — краш после списания, до записи заказа — меньше таблиц — outbox + вебхук + сверка (Глава 40)»

«Sandbox = прод с флагом — тестовый ключ пишет боевые вебхуки — экономия инфраструктуры — изоляция данных»

«Code-first без канона — схема = вчерашний дамп — быстрее фича — генерация spec в CI как артефакт»
