# Глава 26. SRE: SLO, инциденты, постмортемы

*Коротко. SRE здесь — процесс: какие показатели отражают боль пользователя, как тратить error budget, как дежурить без выгорания, кто что делает в инциденте, как разбирать без обвинений, как убивать toil, как готовить ёмкость, какие шаблоны заполнить до первого SEV.*

*Технические классы отказов, bulkhead, retry, деградация, бэкапы и chaos — Глава 12. Эта глава не повторяет механизмы. Она задаёт политику: когда механизмы считаются достаточными, кого будить, что останавливать, что писать после.*

*Google SRE Workbook: изменения — источник порядка 70% аварий (оценка, аргумент для политики, не ваша цифра). Октябрь 2025, AWS us-east-1: автоматика DNS сама источник каскада; recovery каскада планируйте отдельно от recovery первопричины (Глава 12.1). Процесс инцидента обязан это переживать.*

*Читать, когда SLO есть в слайде и нет в алертах, on-call из троих, постмортем — PDF без тикетов, или релизы идут при нулевом бюджете ошибок.*

Надёжность без политики — набор дашбордов. Политика отвечает: какой SLI, какой SLO, что происходит при исчерпании бюджета, кто incident commander, какие экшены обязательны после, сколько toil допустимо, хватит ли ёмкости на inorganic-пик.

DORA 2025: failed deployment recovery time <1 часа — 21,3% команд; <1 дня — ещё 35,3%. Медианный MTTR критического инцидента в опросе февраля 2026 (1039 SRE/DevOps) — 1–2 часа. 61% оценивают час простоя ≥$50 000, 34% — ≥$100 000. ~40% организаций сообщают о симптомах выгорания более чем у четверти on-call. Большинство команд тратят ≥40% времени на incident management вместо разработки. Это не «культура стойкости». Это сломанные алерты, короткая ротация и отсутствие бюджета ошибок.

Для 1–3: один пользовательский SLI, SLO записан, page на него, кто дежурит в календаре, один шаблон постмортема. Для 10–30: error budget policy с последствиями, ротация ≥6, роли IC/OL/CL на SEV1, toil в квартальном опросе. Для 100+: escalation 7/30/90, ёмкость как процесс, шаблоны в репозитории, SRE и продукт подписывают SLO вместе.

## 26.1. SLI/SLO/SLA: как выбрать показатели, отражающие пользовательскую боль

SLI (service level indicator) — измерение. SLO (objective) — цель по SLI за окно. SLA (agreement) — юридический/коммерческий контракт, обычно слабее SLO: буфер, чтобы не платить неустойку при каждом выжженном внутреннем бюджете. Путать SLA и SLO — либо врать клиенту, либо задушить релизы.

SLI выбирают от пользовательского сценария, не от CPU. Сценарий «оплатить заказ»: доля успешных charge за 30 дней, latency p99 checkout. Не: CPU API, диск БД. Несколько SLI на сервис нормально; один «availability 99,9% всего» скрывает мёртвый checkout при живом маркетинге.

Типы SLI. Availability: good/valid events (успешный HTTP 2xx/3xx/4xx клиента vs 5xx и timeout; 4xx авторизации — обычно valid). Latency: доля запросов быстрее порога, не среднее. Quality: доля корректных результатов (поиск вернул не пусто на известном корпусе; инференс не fallback). Freshness: лаг пайплайна. Правило: SLI = ratio, числитель и знаменатель названы, исключены боты и health-check, если они не пользователи.

Окно. Четыре недели скользящие — дефолт Google. Календарный месяц удобен финансам и врёт на границе. Считайте оба, алертите по скользящему.

Арифметика 30 дней. SLO 99% — 7 ч 12 мин даунтайма; 99,5% — 3 ч 36 мин; 99,9% — 43 мин 12 с; 99,95% — 21 мин 36 с; 99,99% — 4 мин 19 с; 99,999% — 26 с. Выше 99,95% для сервиса с несколькими внешними hard-зависимостями обычно недостижим: теоретический потолок = произведение доступностей зависимостей. Stripe 99,99% × ваша БД 99,9% × DNS 99,99% уже не 99,99% продукта. Записывайте потолок до выбора SLO (Глава 12.1, 2.2).

Как выбрать число. Не «как AWS». Возьмите историю 90 дней, посчитайте фактический SLI, поставьте SLO чуть хуже факта, если пользователи не жалуются; чуть лучше факта, если жалуются и есть бюджет чинить. Матрица Workbook (SLO × toil × удовлетворённость): SLO выполняется, toil низкий, удовлетворённость низкая → ужесточить SLO; SLO не выполняется, toil низкий, удовлетворённость высокая → ослабить SLO. Политика без этой матрицы спорит мнениями.

Письменно. SLO в репозитории рядом с алертами, подписан разработкой и эксплуатацией (или «you build it, you run it» — одной командой). Продукт знает SLO: иначе error budget не остановит фиче-завод.

Request-based vs window-based. Request-based (доля хороших событий) честнее отражает пользователя на неравномерном трафике: ночной простой не «лечит» дневной аутдж. Window-based (доля хороших минут) удобна, когда rps низкий и один 500 из трёх запросов врёт как 33% ошибок. На публичном API с тысячами rps — request-based. На админке с 40 запросами/час — window или синтетика.

Слабый SLI выглядит так: availability по всем URL включая `/health` и статику; latency p99 без исключения long-poll; «успех» = HTTP 200 при 200 с телом `{"charged":false}`. Калибровка: возьмите 10 тикетов поддержки за квартал и проверьте, краснел ли SLI. Если тикеты есть, а SLI зелёный — индикатор не про боль.

Пример. Поиск SLO 99,5% по HTTP 200. Пользователи жалуются на пустую выдачу. 200 с нулём хитов при известном корпусе — quality SLI, не availability. Availability живой, бюджет цел, продукт «ломается». Добавляют quality: доля запросов с `hits>0` на контрольном наборе + latency. Availability не ужесточают. Матрица Workbook здесь: SLO availability выполняется, удовлетворённость низкая → не «ещё девяток», а другой SLI.

Для 1–3: availability + latency на главной ручке. Для 10–30: SLI по сценариям (логин, оплата, запись). Для 100+: разные SLO на клетки/тиры; внутренние платформенные SLO отдельно (Глава 24.8).

## 26.2. Error budget и политика его расходования

Error budget = 1 − SLO. Сервис с SLO 99,9% при 1 000 000 запросов за четыре недели имеет 1000 допустимых ошибок. Бюджет — валюта между скоростью изменений и надёжностью. Без политики это число на дашборде.

Шаблон Google (SRE Workbook, error budget policy):

- Исчерпан бюджет за предыдущее четырёхнедельное окно — останавливаются изменения и релизы, кроме P0 и security-фиксов, пока SLI не вернулся в SLO.
- Один инцидент сжёг >20% бюджета за четыре недели — обязательный постмортем с минимум одним P0-экшеном на причину.
- Класс аварий сжёг >20% бюджета за квартал — P0 в квартальном планировании.
- Споры о расчёте — эскалация до CTO (или аналога).

Escalation Google Cloud CRE: порог 1 — 7-дневный бюджет исчерпан → эксплуатация тушит, эскалация к разработке не позже недели. Порог 2 — порог 1 держится неделю, 30-дневный бюджет исчерпан → в прод только cherry-pick причин; SRE вправе требовать приоритизации. Порог 3 — 90-дневный бюджет исчерпан или разработка отказывается остановить фичи → исполнительное руководство.

Maintenance window, не входящий в бюджет, — бесплатный удар по пользователям без последствий для планирования. Окна либо считаются, либо их нет. «Серебряные пули» Google — крайне узкий набор исключений заморозки для критичных запусков; не копируйте как «нам можно всегда».

Алерт на бюджет: multiwindow multi-burn-rate (Workbook). Page: 1 час + 5 минут при 14,4× (к срабатыванию сожжено ~2% бюджета); 6 часов + 30 минут при 6× (~5%). Ticket: 3 дня + 6 часов при 1× (~10%). Срабатывание, когда оба окна выше порога. Короткое окно = 1/12 длинного. При SLO 99,9% burn 14,4× = error rate 1,44%, 30-дневный бюджет кончится примерно за 2 дня. Частая ошибка — пропуск ticket-уровня: медленная утечка не похожа на инцидент и съедает квартал.

Расход бюджета — не только авария. Canary, который 40 минут отдавал 5% ошибок на 10% трафика, тоже жжёт. Плановый эксперимент с известным риском (Глава 28) должен оценить «стоимость в минутах бюджета» до запуска. Если эксперимент сжигает 30% квартального бюджета ради гипотезы — это продуктовое решение, записанное, не сюрприз on-call.

Когда политику не применять буквально: команда из трёх, SLO ещё калибруется — тогда бюджет как диагностика, не как заморозка. Когда обязаны: есть on-call и регулярные выкаты. Чем платите за политику без последствий («бюджет 0, релизим дальше»): выгоранием и CFR. Сигнал ошибки: бюджет красный три недели, в changelog — фичи.

## 26.3. Дежурства без выгорания: ротации, нагрузка, компенсация, эскалации

On-call — ограниченный ресурс внимания, не «все всегда на телефоне». Нижняя граница toil от размера ротации (Google): 6 человек → 33% времени в ротации как пол, 8 человек → 25%. Ротация из 3 — путь к выгоранию и к пропущенному алерту. Цель Google: toil <50% времени каждого SRE, факт средних опросов ~33%. Если один человек стабильно выше — это сигнал менеджеру перераспределить, не «личная стойкость».

Гигиена (данные NeuBird / разборы 2026 выше). Ротация ≥6. Каждый page — runbook и действие; page без действия удаляется. Правило 30 дней: алерт, ни разу не приведший к действию, удаляется. Эскалация 3–4 уровня, не 12. Компенсация дежурства явная (деньги и/или отгул). Право на восстановление после ночного SEV: следующий рабочий блок не «как обычно с 10:00». Инциденты смены попадают в бэклог, не растворяются в Slack.

Нагрузка. Считать pages/week, % actionable, ночные будки, MTTA. Цель actionable >70%; факт у 57% команд <30% — значит, режьте алерты до найма. ≥10 алертов/день при actionable <30% — не «бдительность», а шум. 83% игнорируют алерты иногда; 44% поймали аварию из-за этого.

Follow-the-sun имеет смысл при ≥2 регионах присутствия инженеров и передаче IC письменно. Иначе ночь всё равно падает на одну TZ. Не путайте с «все в Slack 24/7».

Вторичный on-call (backup) имеет смысл, когда primary не отвечает N минут, не как «двое смотрят Slack всю ночь». Эскалация: primary → backup → IC-пул / engineering manager. Без лимита уровней алерт в 03:00 будит директора минуя runbook.

Компенсация, которая работает: фиксированная ставка за неделю дежурства + отгул после ночного SEV1 до полудня следующего дня минимум. «Пицца за инцидент» не компенсирует. Запрет дежурить две недели подряд. Запрет дежурить в свой отпуск. После серии SEV — вывести человека из следующей ротации, не «он уже в контексте».

Хендовер смены: 15 минут, письменно в канале ротации. Что горит, какие выкаты идут, какие алерты приглушены и почему (silence без тикета = следующий дежурный слеп). Приглушение >4 часов без тикета на починку причины — нарушение гигиены.

Для 1–3: основатель и ещё один в календаре, алертов мало (Глава 25.6), компенсация честная хотя бы отгулом. Не притворяйтесь, что ротации шесть. Для 10–30: набор до 6, включая тех, кто умеет откат (Глава 23.8). Для 100+: отдельные ротации по доменам, лимит параллельных page, запрет dual-primary без оплаты.

## 26.4. Управление инцидентом: роли, уровни серьёзности, коммуникация, статус-страница

Инцидент — отклонение, требующее координации сверх обычного on-call фикса. Роли Incident Command System, которые чаще всего нарушают:

- Incident Commander (IC) — картина, приоритеты, решения. Не чинит руками. Не самый сильный инженер в комнате обязан быть IC: он должен быть свободен.
- Operations Lead (OL) — единственный, кто вносит изменения в систему (или явно делегирует одну команду). Без OL пять человек пушат конфликтующие hotfix.
- Communications Lead (CL) — статусы наружу и внутрь с каденцией (например, каждые 15–30 минут на SEV1).
- Scribe / Planning — таймлайн, хендовер, список гипотез.

Явная передача: «I am handing IC to X, X confirm» в канале и голосом. Смена ролей при >4–6 часов: выгоревший IC принимает худшие решения. Один канал, одна страница состояния, одна временная шкала. Канал вне скомпрометированной инфры, если инцидент — security (Глава 32.10).

Severity существует, чтобы выбрать режим, не для KPI. Калибруйте под SLO и деньги; отраслевого стандарта нет.

- SEV0/1: пользовательский сценарий денег/данных недоступен для значительной доли; IC обязателен; внешняя статус-страница; page вторичных; постмортем обязателен.
- SEV2: существенная деградация или меньшая доля; IC по необходимости; внутренний статус; постмортем по порогу бюджета.
- SEV3: ограниченный импакт; ticket; разбор по желанию.
- SEV4: косметика.

Не завышайте SEV «чтобы прибежали» — следующий раз не прибегут. Не занижайте, чтобы «не портить метрики».

Коммуникация наружу. Первое сообщение — в часы, даже если фактов мало: знаем, расследуем, следующее обновление в T. Не преуменьшать охват (урок Salesloft: ошибка оценки → вторая волна репутации). Статус-страница — не маркетинг «все системы operational» при горящем checkout. Шаблон: симптом глазами пользователя, обход, следующая отсечка. Юридические сроки уведомления при breach (GDPR 72 ч, РФ 24/72, NIS2 24/72/месяц) — Глава 32/33; IC зовёт DPO с первой минуты, не после «починили».

Урок us-east-1: каскад переживает первопричину. Коммуникация «DNS починили» при мёртвом launch EC2 — ложь. Пишите, какой пользовательский сценарий жив, не какой внутренний компонент.

Каденция CL. SEV1: внешний статус не реже чем раз в 30 минут, даже «без изменений, следующая отсечка в T». Внутренний канал — гипотезы и факты, не шутки; отдельный thread для логов. Запрет править прод всем, кто не OL: «я просто посмотрю в psql» на инциденте данных — второй инцидент.

Калибровка SEV на цифрах продукта. Пример: потребительское приложение, 200k DAU. SEV1 — >5% сессий не могут пройти оплату или вход, или утечка данных любого размера. SEV2 — >1% или отдельный регион/тенант-enterprise. SEV3 — деградация поиска, обход есть. Запишите пороги в процентах и в деньгах, не в «ощущается серьёзно». Пересмотр порогов — после двух ложных SEV1 или одного заниженного.

Для 1–3: IC = кто не чинит; CL = то же лицо с таймером; статус хотя бы в Twitter/статус-URL. Для 10–30: роли на SEV1, шаблон сообщений. Для 100+: incident tooling, хендовер по сменам, comms с PR.

## 26.5. Разбор без обвинений: постмортем, контрибуторы, действия и их доведение

Blameless: графа «причина» не содержит имён. Люди работали в системе стимулов и инструментов, которая допустила событие. Цель — contributing factors и изменения системы. Amazon COE (Correction of Errors): 5 Whys, воздействие, таймлайн, экшены в бэклоге, не в PDF.

Обязательные разделы: воздействие (пользователи, деньги, длительность, SLO-burn); таймлайн; что сработало; что не сработало; где повезло (там прячутся следующие аварии); contributing factors; action items с владельцем, датой, приоритетом; ответ «почему мониторинг не поймал раньше».

Порог обязательности: SEV1 всегда; любой инцидент >20% error budget; security — всегда. Срок черновика: 48–72 часа, пока память свежая; ревью с командами, которые не участвовали — иначе слепые пятна.

Доведение. Экшен без тикета = не было. P0 из правила 20% бюджета не вытесняется «срочной фичей» без эскалации 26.2. Раз в квартал — аудит открытых экшенов постмортемов: burndown, не архив.

Не путать contributing factor с root cause единственным. us-east-1: гонка Enactor + отсутствие предохранителя устаревшего плана + каскад NLB health checks. Один «root cause: DNS» учит не тому.

Для 1–3: одна страница в Notion/git после каждого SEV1, три экшена максимум, все с датой. Для 10–30: шаблон, обязательное чтение соседней командой. Для 100+: COE-процесс, библиотека инцидентов, тренды классов.

## 26.6. Toil: измерение и систематическое уничтожение

Toil — операционная работа, которая масштабируется с сервисом, ручная, повторяемая, не даёт долгосрочной ценности, реактивная (Google SRE book). Патч в 3:00, который станет скриптом — кандидат. Проектирование нового SLI — не toil.

Измерение: квартальный опрос % времени на toil; тикеты ручных операций; pages, которые лечатся одной командой. Цель <50%, пол от ротации 25–33%. Список toil — бэклог автоматизации с ROI: часы × ставка − стоимость скрипта.

Уничтожение по порядку: убрать источник (алерт-шум, ручной сертификат → ACME); автоматизировать оставшееся; принять остаток явно. Автоматизация без kill switch — новый класс отказа 12.1 (автоматика). Toil платформы (тикет на namespace) лечится golden path (Глава 24.8), не наймом ещё одного оператора.

Для 1–3: основатель делает toil руками и записывает, что повторилось трижды — в скрипт. Для 10–30: 20% времени платформы/SRE на убийство toil, иначе ротация не сойдётся к 6. Для 100+: toil budget в OKR команды эксплуатации как ограничение, не как vanity «автоматизировали».

## 26.7. Планирование мощности и подготовка к пикам

Ёмкость планируют от headroom к пиковому трафику, не от среднего. Organic growth — тренд рядов 25.4. Inorganic — маркетинг, запуск, сезон, вирус: требуют явной заявки «ожидаем ×N в дату D» за время, достаточное на закупку и нагрузку.

Нагрузочный тест даёт точку перегиба и характер деградации, не «выдержали X rps» (Глава 22.5). Проверять отказ зависимости, не только свой сервис: checkout при мёртвом поиске (Глава 12.4). Известна утилизация, с которой начинаете shed.

Пики. Заранее: прогрев кэша, прескейл (не ждать CPU), лимиты тенантов, очередь с backpressure, статус «ограниченная регистрация». После: не оставлять прескейл навсегда — это 8% CPU как норма (Глава 24.3).

Chaos в 2026 нишевый: Chaos Mesh 3% production use, 11% evaluating (CNCF 2025). Практика для тех, у кого уже есть SLO, on-call и инцидент-процесс. Начинать — Глава 12.7, не отсюда.

Мультирегион как ёмкость — только со drill (Глава 12.5). Иначе это строка в бюджете, не headroom.

Inorganic playbook за 14 дней до кампании: прогноз ×N от маркетинга с датой (если N нет — не запускаем кампанию вслепую); load test до 1,5× прогноза; прескейл дата D−1; лимиты регистрации/инвайтов как shed; on-call расширен на окно; статус-страница готова; откат флага кампании. После окна — downscale в тикете, не «оставим, вдруг ещё». Связь с Главой 22.5: точка перегиба известна до рекламы, не во время.

Голова ёмкости часто не compute. Пул соединений Postgres, квоты облака (IP, NAT, GPU), rate limit вендора платежей, лимит TLS handshake на edge. Смотрите USE этих ресурсов, не только CPU подов. Заявка «нужно ещё 20 подов» при исчерпанном `max_connections` — вред.

Для 1–3: знать max rps на текущем тарифе БД и что будет при ×3. Для 10–30: load test до точки перегиба раз в квартал или перед inorganic. Для 100+: capacity review в цикле планирования, заявки маркетинга как вход.

## 26.8. Готовые шаблоны: SLO-документ, incident runbook, постмортем

Копируйте в репозиторий сервиса. Пустые поля = сервис не готов (связка с Главой 12.8: там техника, здесь процесс).

**SLO-документ (одна-две страницы)**

- Сервис, владелец, on-call ротация.
- Пользовательские сценарии (3–7) и SLI на каждый: формула good/valid, источник метрики, исключённый трафик.
- SLO: число, окно (4 недели), потолок от зависимостей.
- SLA если есть: число, компенсация, почему слабее SLO.
- Error budget policy: заморозка, порог 20%, эскалация, исключения (security/P0).
- Алерты: burn-rate page/ticket, ссылка на дашборд 25.6.
- Подписи: разработка, эксплуатация/продукт, дата пересмотра (не реже года или после смены архитектуры).

**Incident runbook (на каждый page и на SEV1-сценарий)**

- Алерт: что значит, какая боль пользователя, какой SLI.
- Первые 5 минут: дашборд, деплой-аннотации, откат? (Глава 23.8), зависимость жива?
- Команды: откат артефакта, выключить флаг, scale, shed, kill switch автоматики.
- Роли: кто IC по умолчанию, как эскалировать, CL-каденция.
- Коммы: шаблон внутреннего и внешнего статуса.
- Когда эскалировать security/legal/DPO.
- Как закрыть: критерии mitigation vs resolved; кто пишет постмортем.

Проверка: человек, не писавший сервис, следует runbook на stage. Если не может — runbook для автора, не для дежурного.

**Постмортем**

- Заголовок, SEV, время start/mitigate/resolve, владелец документа.
- Воздействие: N пользователей/тенантов, $ если известно, % error budget.
- Таймлайн (UTC).
- Что сработало / не сработало / повезло.
- Contributing factors (без имён).
- Детект: почему алерт сработал поздно или не сработал (Глава 25.6).
- Action items: ID тикета, владелец, дата, P0/P1/P2. Минимум один P0 при >20% бюджета.
- Рассылка: команда + одна соседняя.

Для 1–3 три файла в одном каталоге `ops/`. Для 10–30 — PR-шаблон «новый сервис» подтягивает заготовки (golden path, Глава 24.8). Для 100+ — автоматическое создание канала инцидента из алерта с подстановкой runbook.

Сквозной пример. B2B SaaS, SLO оплаты 99,9%, окно 4 недели, бюджет 43 минуты. Canary нового биллинга сжёг 15 минут (35% бюджета) за час: burn-rate page, IC не чинит, OL откатывает артефакт за 4 минуты (репетировали, Глава 23.8). Статус: «задержки списания, повторите; платежи идут старым путём». Постмортем: contributing — canary без бизнес-SLI charge_success, только HTTP 200; флаг не отделял charge path. P0: SLI charge в canary analysis; P1: удалить двойную запись после expand. Бюджет не исчерпан — релизы не заморожены, но класс «выкат без бизнес-SLI» идёт в квартальный P0, если повторится. Технический каскад ретраев — чинили по Главе 12.3; здесь решили, кто жмёт rollback и что попадает в бэклог.

## Чек-лист главы

**Договорённость**

- [ ] SLI от сценария пользователя; SLO ≤ теоретического потолка зависимостей.
- [ ] SLA слабее SLO или его нет; продукт подписал.
- [ ] Error budget policy с последствиями, не только с дашбордом; окна считаются в бюджет.

**Люди**

- [ ] Ротация ≥6 или честно меньше с компенсацией и крошечным числом page.
- [ ] IC не чинит; OL один на изменения; передача ролей вслух.
- [ ] Page actionable; правило 30 дней на удаление шума.

**После**

- [ ] Постмортем без имён; экшены в тикетах; P0 при >20% бюджета.
- [ ] Toil измерен; ёмкость от пика, load test с точкой перегиба.
- [ ] Три шаблона 26.8 заполнены до публичного URL (вместе с 12.8).
