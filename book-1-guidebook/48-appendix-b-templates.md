## B.1. PRD

```
# PRD: <название фичи>
Статус: draft | review | accepted | shipped | killed
Автор / дата / владельцы: PM, TL, Design
Связь: ставка Type 1/2 (Глава 4), гипотеза (Глава 5), OKR если есть

## Проблема
Кто страдает. Частота. Цитата или метрика. Что делают сейчас вместо нас.

## Пользователь и job
Сегмент. JTBD. Не-пользователь (вычеркнут).

## Ценность
Что изменится в их работе. Отсекающая фраза value prop.

## Ограничения
Срок, регулятор, совместимость, себестоимость, что нельзя ломать (SLO, threat model).

## Метрика успеха
Primary. Guardrails (error rate, latency, crash, жалобы, cost). Kill metric и дата.

## Не делаем
Явный список. Кастом, платформа, AI — только если проходит 29.1/30.1.

## Решение (набросок)
Поток. Состояния пусто/ошибка/loading. Флаг. Деградация.

## Скоуп v1 / позже
Нарезка. Appetite или диапазон дат (P85), не одно число.

## Риски и этика
T&S, privacy, тёмные паттерны (37.7).

## Запуск
Кому, волна, доки, поддержка, эксперимент (B.8) или почему не A/B.
```

## B.2. RFC / технический дизайн

```
# RFC-NNNN: <заголовок>
Статус: open | accepted | rejected | withdrawn

## Варианты

## Безопасность / privacy / деньги
```

## B.3. ADR

```

Статус: proposed | accepted | superseded by ADR-XXXX | deprecated

## Context
Силы: нагрузка, команда, $, регулятор, лицензия.
```

## B.4. Модель угроз

```
# Threat model: <поверхность>
Дата. Автор. Scope: логин | оплата | загрузка | агент | UGC | другое
Диаграмма (текстом): акторы → границы доверия → активы

## Активы
Данные, ключи, деньги, репутация, ёмкость GPU.

## Акторы
Пользователь, инсайдер, бот, соседний тенант, модель/агент, supply chain.

## Угрозы (STRIDE или список)
ID | угроза | путь | влияние | митигация сейчас | остаточный риск | владелец

## Явно не закрываем
С датой пересмотра.

## Тесты / детект
Что в CI. Что в проде. План утечки (A.9).
```

Минимум до публичного запуска: логин, оплата, загрузка файлов; плюс инструменты агента если есть.

## B.5. SLO-документ

```
# SLO: <сервис / сценарий>
Владелец. Ревизия.

## Пользовательский исход
Например: «открыл отчёт», «сообщение доставлено», «матч начался».

## SLI
Формула. Источник (RUM / сервер / синтетика). Не CPU.

## SLO
Цель (например 99,9% за 30 дней). Потолок по hard-зависимостям посчитан (2.2).

## Error budget
Объём. Политика при 50% / 0%: стоп фич, только reliability.

## Алерты
Multi-window burn если умеете; иначе симптом + порог. Проверены на стейдже.

## Исключения
Плановые окна. Зависимости вне скоупа.

## Связь с SLA
Публичный SLA ≤ внутренний SLO. Credits ≠ damages.
```

## B.6. Runbook

```
# Runbook: <алерт / симптом>
Сервис. Severity. Автор. Дата ревизии (≤ квартал).
Тест качества: новый дежурный закрыл инцидент только по этому тексту — да/нет.

## Симптом
Что видит пользователь. Какой алерт. Дашборд (ссылка).

## Первые 5 минут
1. Объявить инцидент / IC.
2. Проверить статус-страницу зависимостей.
3. Митигация: флаг / откат / shed / failover.
Не искать корневую причину до митигации.

## Диагностика
Команды, запросы, «если X — смотри Y».

## Эскалация
Кого, когда, контакты. Вендор L4.

## Откат / компенсация
Точные команды. Деньги: не чинить леджер руками в проде без тикета.

## После
Постмортем если Sev ≥ порога. Правка этого runbook в том же PR.
```

## B.7. Постмортем

```
# Postmortem: <инцидент ID>
Blameless. Статус: draft | published internal | published external
IC. Scribe. Дата инцидента. Дата разбора (≤24 ч).

## Кратко (язык неинженера)
Что. Длительность. Кого затронуло. Потеря денег/данных — факт или «не подтверждено».

## Таймлайн
UTC штампы. Обнаружение → митигация → resolve.

## Impact
SLI, error budget, тикеты, ARR at risk.

## Контрибьюторы (не «виноват X»)
Дыры процесса, слепые зоны мониторинга, сложный diff, отсутствующий флаг.

## Что сработало
## Действия
ID | действие | владелец | срок | статус
(без владельца и срока — не действие)

## Внешняя версия
Ссылка. Что убрано (секреты, имена).
```

## B.8. План эксперимента

```
# Experiment: <название>
Гипотеза (если X, то Y на метрике Z).
Владелец. Флаг. Даты.

## Единица рандомизации
Пользователь / аккаунт / регион / время (switchback). Интерференция: да/нет.

## Primary / guardrails
Guardrail нарушен → стоп независимо от primary (28).

## Размер выборки и длительность
Расчёт или «трафика мало → качественный метод (28.7)».
Не подглядывать ежедневно без sequential design.

## SRM
Проверка соотношения групп.

## Сегменты
Не усреднять enterprise и self-serve.

## Решение заранее
Ship / iterate / kill критерии.

## После
Результат. Доверительный интервал. Что вошло в roadmap.
```

```
Активация, ошибки, тикеты, cost. Решение: держать / откатить / сузить.
```

## B.10. Реестр рисков

Таблица (квартальная ревизия + после SEV). Шаблон строки:

```
ID: PAY-04
Риск: двойное списание при ретрае без идемпотентности
Класс: технический
Вероятность: M | Влияние: C (доверие + деньги + диспуты)
Сигнал: count(charges) > count(orders) за сутки
Митигация сейчас: уникальный ключ, тест повторного POST, сверка
План при срабатывании: стоп ретраев, refund, постмортем, фикс
Владелец: Staff backend + finops
Корреляции: PAY-01 вебхуки; FIN-02 сверка; KEY-01 bus factor биллинга
Дата ревью:
```

Правила: один живой человек; митигация = действие сейчас; без измеримого сигнала — тревога, не риск; корреляции помечать (44.3). Pre-mortem (44.4) обязан распарситься сюда.
