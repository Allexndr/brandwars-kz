# Глава 43. Поддержка, документация и сообщество

*Коротко. Поддержка — продукт с SLA и петлёй в roadmap, не очередь тикетов. Документация — четыре типа по Diátaxis, не «вики после релиза». Сообщество — канал с метриками DX, не чат для звёзд GitHub.*

*Глава: тиры и эскалации, самообслуживание и AI-агенты, петля support→product, docs-as-code, внутренние артефакты, сообщество, DevRel/OSS, кризисные коммуникации.*

*Фаундеру — что закрыть до публичного запуска, чтобы первый инцидент не убил доверие. Техлиду — как не стать L3 на каждый пароль. Staff — как не мерить deflection вместо resolution.*

*Возвращайтесь при запуске биллинга, UGC, публичного API, при первом P1 и при внедрении AI в поддержку.*

Тестирование и релизная готовность — Главы 31 и 23. Здесь — после того как пользователь уже в продукте: как он получает помощь, как знания не гниют, как вы говорите, когда горит.

Две ловушки 2026. Первая — deflection rate как северная звезда. Клиент, бросивший чат в раздражении, засчитывается как «не дошёл до человека». Klarna: февраль 2024 — ассистент на 2,3 млн диалогов/мес, нарратив «700 FTE»; май 2025 — CEO в Bloomberg/Fortune: стоимость была слишком доминирующим фактором оценки, качество просело, людей наняли обратно. Интерпретация: коррекция скоупа, не отказ от AI. Гибрид: модель на массовом tier-1, человек на споры, фрод, эмпатию. Цифры падения CSAT ~22% по вторичным источникам не подтверждены первично — не цитировать как факт.

Вторая — база знаний, которую не трогали полгода. Команды с Help Center, обновлённым за 30 дней, показывают порядка 45% deflection; без аудита 6 месяцев — порядка 18% (сводки true deflection 2026). Разброс по свежести больше, чем разброс между AI-вендорами.

Документация измеримо связана с поставкой. DORA 2023: качественная внутренняя документация → +25% team performance. Модельные лифты практик при docs выше среднего vs ниже (осторожно, не RCT): trunk-based 1525% vs 36%, CI 750% vs 34% — направление устойчиво, абсолютные множители не копировать в OKR.

## 43.1. Архитектура поддержки: уровни, каналы, SLA, эскалации

Лестница L0 (self-service) → L1 (фронтлайн) → L2 (техспециалисты) → L3 (инженеры) → L4 (вендоры) работает на одном продукте и одной кодовой базе. На масштабе тикеты должны идти **вбок** — к командам, владеющим системой, — а не вверх к дженералистам-роутерам. Признаки сломанных тиров: три одних и тех же имени в каждой war room; в L3 «горячие картошки» по 90 дней; инциденты гниют в швах между командами.

**Swarming:** один владелец тикета на всю жизнь, эксперты подтягиваются, хендоффов нет. Для сложных кросс-системных низкообъёмных проблем. Не сваривайте всей командой сброс пароля. Высокообъёмный повторяющийся поток — тиры. Смешение без правила = и дорого, и медленно.

SLA/SLO по **severity**, не по тиру. Рабочая матрица (ориентир SaaS-практик, публичный SLA слабее внутреннего):

- S1 (сервис недоступен, потеря данных): первый ответ 15 мин, цель решения 4 ч, эскалация немедленно.
- S2 (ключевой сценарий сломан, обхода нет): 30 мин / 8 ч / через 1 ч без движения.
- S3 (баг с обходом): 2 ч / 24 ч / через 4 ч.
- S4 (как сделать, фидбек): 8 ч / 48 ч / через 1 рабочий день.

Каналы. Chat: медианный FRT 1,5–2 мин, топ-дециль <30 с (бенчмарки 2026). Email: медианный FRT 4–7 ч, среднее ~12 ч из-за хвоста. First contact resolution среднее ~72%. Медианное решение email-тикета ~24 ч. CSAT кросс-индустрия 2026: среднее 78/100, топ-квартиль 86+; SaaS ~80 / топ 88+. Связь FRT–CSAT в вендорских сводках (~1,7 пункта за час задержки) — ориентир, не закон. CSAT ниже 70% в B2B SaaS — конкурентный недостаток; целиться в высокие 70-е.

Для 1–3: основатель на S1/S2, макросы на S4, статус-страница хотя бы ручная. Нет L3-отдела — есть on-call и runbook (Глава 26). Для 10–30: L1 (часто совмещённый CS) + эскалация в stream-aligned команду по таксономии. Для 100+: вбок по владению; swarming на SEV; отдельный comms lead на P1.

Enterprise-очередь не смешивать с self-serve: разные SLA, разные люди, иначе крупный клиент тонет в S4.

## 43.2. Самообслуживание: база знаний, поиск, автоответы, AI-агенты в поддержке

L0 — самый дешёвый контур, если измерять resolution, не deflection. True deflection = (self-service решения − повторные контакты за 48 ч) / все попытки помощи. Разрыв deflection vs resolution до 20–30 п.п.

Gartner (5 728 клиентов): только 14% обращений полностью решаются в self-service; среди «очень простых» — 36%. Традиционная база знаний: медиана deflection ~18% (P10–P90: 5–35%). AI self-service: медиана ~22% (8–45%). Независимые агрегаты tier-1 автоматизации: медиана ~41%, верхний квартиль ~59% (определения смешаны, спорно). Intercom Fin заявляет среднюю resolution rate 76% (топ 80–93%) по своей инсталлбазе и своему определению («полностью без человека, без возврата, без недовольства») — вендор, отобранный intent-микс. Распределение бимодально: ~55–60% входящего — структурированный tier-1, часто >60% автоматизации; ~35–40% неструктурированный tier-2, редко >30%.

AI-агент в поддержке. Классификационный слой **до** LLM: фрод, споры, платежи, account security не идут в модель. Handoff с полным контекстом — иначе клиент пересказывает и CSAT падает. Человеческий выход явный, не спрятанный. Аудит выборки диалогов человеком с первой недели. Re-contact 48–72 ч с первой недели, не постфактум (слепое пятно Klarna). Ориентир re-contact AI vs человек 11,3% vs 8,7% — спорный агрегат, использовать как гипотезу.

Свежесть базы бьёт выбор вендора. Каденция: аудит Help Center каждые 30 дней на топ-20 интентов по объёму × severity. Статья без владельца и даты ревизии — кандидат на удаление, не на «пока оставим».

Поиск по докам: то же, что продуктовый поиск (Глава 29) в миниатюре — лексика + синонимы ошибок, не только embedding. Код ошибки и SKU плохо живут в чистом vector-only.

Для 1–3: 15–30 статей how-to на реальные вопросы, не «о нас»; шаблон ответа в почте. AI-чат поверх пустой базы тиражирует галлюцинации. Для AI-продукта: лимиты и биллинг в L0 до того, как LLM начнёт «объяснять счёт».

## 43.3. Связь поддержки с продуктом: классификация, приоритизация, обратная петля

Незамкнутая петля — сбор тикетов в никуда. Четыре компонента:

1. Автоклассификация по продуктовой таксономии (30–50 позиций, иерархия). Пересмотр раз в месяц человеком, не автотегом в одиночку.
2. Детекция паттернов до кризиса (всплеск темы, не абсолют объёма).
3. Маршрутизация к команде, владеющей поверхностью.
4. Измерение: снизил ли фикс контактный паттерн. Этот шаг пропускают чаще всего.

Приоритет темы: объём × severity (риск оттока) × сегмент (ARR/тариф), не голое число тикетов. У темы владелец: продукт, документация, онбординг или процесс — не всегда PM. Inner loop: вернуться к конкретному клиенту. Outer loop: убрать причину. Закрытие наружу: «вы просили — зарелизили». Пять минут, непропорциональный эффект на готовность давать фидбек.

NPS/CSAT. Медианный NPS B2B SaaS ~30–40; enterprise/infra 40–50; SMB-focused 25–30; горизонтальная продуктивность 20–30 (2026). In-app завышает на 5–10 пунктов vs email (выборка активных). Response rate 10–30% — нерепрезентативность; по CustomerGauge нереспонденты оттекают почти вдвое чаще (вендор, осторожно). Enterprise в том же продукте часто на 10–20 пунктов ниже self-serve. Рецепт: relational NPS раз в квартал по сегментам + транзакционный CSAT на события (онбординг, тикет, релиз) + обязательный открытый вопрос.

Каналы фидбека и response rate (порядки 2026): SMS 40–50%; in-app 20–35% (PLG до 30–40%); email с кнопкой 15–25%; email со ссылкой 10–18%; веб-опрос 8–15%. Переход email→in-app даёт 2–10× в вендорских данных Pendo — как гипотеза.

Сторы. Hassan et al. (2018): после ответа разработчика 4,4% повышают оценку vs 0,7% без ответа. Google Play Console (2024): ответ на негатив в среднем +0,7 звезды. AppFollow: ответ ≥50% отзывов → +0,3…0,7 звезды за 90 дней; сильная категорийная дисперсия (Entertainment до +2,1, Social ≈0) — вендор. Скорость: 24 часа лучше идеального ответа на день 4. Play собирает больше отзывов и показывает ответ быстрее; App Store модерирует ответ до недели.

## 43.4. Документация как продукт: Diátaxis, docs-as-code, актуальность

Четыре типа (Diátaxis, Pronovost; принят Django, Cloudflare Developer Docs, Canonical, Gatsby):

- **Tutorial** — «научи меня», линейный путь. Ошибка: ветвления «можно также».
- **How-to** — «помоги сделать X», один результат. Ошибка: превращение в туториал.
- **Reference** — факт, полнота. Ошибка: советы и объяснения внутри.
- **Explanation** — почему. Ошибка: пошаговые инструкции.

Практика: четыре директории верхнего уровня. Канон (параметры, коды ошибок, форматы) **только** в Reference, остальное ссылается. Композитные runbook/troubleshooting помечают секции по квадрантам.

Docs-as-code: markdown/MDX в том же монорепо или в репо с PR-связью на код; ревью рядом с фичей; reference генерируется из OpenAPI/типов — единственный способ не разъехаться; линтер стиля в CI; версия доков = версия продукта. Changelog: human-readable (что изменилось пользователю) отдельно от machine-readable (semver, breaking + миграция).

Актуальность: статья без кода ошибки, который уже в API, — дефект релиза, не «docs потом». Definition of Done фичи включает how-to или reference-дифф. Для публичного API — Глава 14; здесь правило: без Diátaxis DX-метрика TTFV не сдвинется.

Для 1–3: один tutorial (quickstart до ценности), 10 how-to, generated reference. Explanation можно не писать, пока «почему» не спрашивают дважды. Для 100+: docs platform, поиск, версии, локализация (Глава 36).

## 43.5. Внутренние документы: runbooks, onboarding, архитектурные обзоры

Типология:

- RFC — мутабельное предложение до решения (Глава 42.5).
- ADR — иммутабелен.
- Design doc — эволюционирует.
- Runbook — живой; тест: новый дежурный в 3 ночи закрывает инцидент только по тексту.
- Postmortem — заморожен после публикации.

Каденция ревизии: runbooks ежеквартально; архитектурные обзоры 6–12 месяцев; ADR и постмортемы — never, статус frozen. Онбординг-доки — после каждого новичка (петля 41.6): если first PR медленный, чинят docs и тулинг.

Не плодить пятый тип «wiki dump». Если документ не RFC/ADR/runbook/design/onboarding/postmortem — либо how-to внутренний, либо удалить.

## 43.6. Сообщество: каналы, модерация, амбассадоры, программы

Сообщество — канал привлечения и удержания разработчиков/пользователей, не «тепло». Метрики, которые переживают разговор с CFO:

Ведущие: Time to first success / TTFV (минуты от quickstart до hello-world, на новых людях); конверсия доков (визит → quickstart → API-ключ); Monthly Active Developers (хотя бы один аутентифицированный вызов/коммит за 30 дней); доля ответов в сообществе от **не-сотрудников**; время ответа на issue; активные контрибьюторы.

Отстающие: атрибутированные регистрации и PQL (конверсия PQL→платящий у dev-tools часто 15–30% vs 2–5% MQL — вендорские агрегаты); retention из dev-каналов; видимость в AI-ответах как канал дискавери 2026.

Выбросить: GitHub-звёзды как адопшн, просмотры страниц, число участников чата, посещаемость митапа как самоцель. Тёмное соцмедиа (приватные Slack/Discord) ломает атрибуцию — компенсировать опросом «как узнали» после покупки.

Модерация сообщества — T&S в миниатюре (Глава 34): правила, эскалация, выгорание модераторов-волонтёров. Амбассадоры: письменный мандат, что можно обещать от имени продукта. Без мандата получите теневой саппорт с обещаниями, которых нет в ToS.

Для 1–3: один канал (GitHub Discussions или Discord), ответ в 48 ч, основатель модерирует. Не открывать пять площадок. Для 10–30: форум + чат, ротация дежурства, макросы. Для 100+: программа амбассадоров, отдельные треки enterprise/community, чтобы SLA не смешались.

## 43.7. Developer relations и открытый код как канал

DevRel — воронка engaged developer, не маркетинг с футболками. Engaged Developer Funnel (Neo4j и последователи): awareness без first success бесполезен. TTFV — главный рычаг. Changelog и breaking policy — часть продукта API (Глава 14).

OSS как канал работает при трёх условиях: реальная польза без покупки; честная граница OSS/commercial; отвечаемые issue. Иначе — дорогой маркетинг с репутационным риском (лицензии — Глава 44.6: AGPL/BSL не «как MIT»). CLA, если принимаете внешний код. Security policy и SLA на уязвимости — до первого CVE в зависимостях, не после.

Не мерить DevRel звёздами. Мерить: TTFV, MAD, долю не-сотрудников в ответах, атрибутированный пайплайн, retention.

## 43.8. Коммуникация в кризисе: инциденты, утечки, изменения цен

Роли инцидента (Глава 26 детализирует операционку): Incident Commander (решения), Communications Lead (внешние апдейты), Scribe (таймлайн), Ops. IC ≠ Comms: нельзя одновременно чинить и писать статус.

Четыре пункта каждого апдейта:

1. Подтверждение: знаем, работаем.
2. Влияние: кого и что, максимально точно.
3. Действие: что делаем сейчас, простым языком.
4. **Когда следующий апдейт.**

Пункт 4 снимает пинги стейкхолдеров. Каденция P1: каждые 15–30 мин, даже «всё ещё расследуем». Тишина читается как скрываем. Статусы: Investigating → Identified → Monitoring → Resolved.

Честность: только проверяемое. Не обещать сохранность данных до проверки. Не называть ETA, который не держите. Переобещавший апдейт стоит дороже простоя.

Статус-страница: отдельные компоненты (API, checkout, auth, БД); автоинцидент по синтетике; аптайм 90 дней с методикой; постмортем из закрытого инцидента. Поддержка получает макрос в момент объявления, не через час. Шаблоны с legal на утечку, чарджбэк-волну, смену цены — до кризиса.

Утечка. GDPR: уведомление регулятора 72 часа (Глава 33). Если CHD не хранили — сказать и доказать архитектурой/SAQ. Если хранили SAD — отдельный класс (PCI + сети). Не «обойдём другим Stripe-аккаунтом».

Смена цены: дедлайн коммуникации, grandfathering vs force-migrate, версия Price object (Глава 40). Кризис цен — если узнали из инвойса. ToS: право менять цену с уведомлением за N дней, заранее.

Постмортем: внутренний разбор ≤24 ч, внешний 24–72 ч; action items с владельцем и сроком; иначе ритуал. Blameless — механизм (факты, контрибьюторы), не запрет называть дыру в процессе.

Масштаб. 1–3: один канал правды (статус-страница или баннер), шаблон на P1, основатель = IC и Comms по очереди — вдвоём, не в одном лице на час. 10–30: раздельные IC/Comms. 100+: comms playbook, пресс, регулятор, enterprise TAM в одном дереве сообщений.

## 43.9. Чек-лист операционной готовности к запуску

**Поддержка**

- [ ] Матрица S1–S4: FRT, цель решения, автоэскалация; публичный SLA слабее внутреннего.
- [ ] Каналы названы; enterprise не смешан с self-serve, если есть оба.
- [ ] L0: Help Center по топ-интентам, ревизия ≤30 дней, владелец статьи.
- [ ] AI-агент (если есть): классификация до LLM, handoff с контекстом, явный человек, re-contact с недели 1.
- [ ] Метрика — resolution и re-contact, не deflection в одиночку.
- [ ] Таксономия 30–50 тем общая с продуктом; у топ-тем владелец; outer loop измеряется.
- [ ] Макросы на ожидаемые вопросы запуска и на инцидент.

**Документация**

- [ ] Tutorial quickstart с измеренным TTFV на новом человеке.
- [ ] How-to на денежный и основной сценарий.
- [ ] Reference генерируется из спецификации, не копипастится.
- [ ] Changelog человеческий + breaking.
- [ ] Runbook на 5 отказов; тест «новый дежурный».
- [ ] Онбординг-док обновлён после последнего новичка.

**Сообщество и кризис**

- [ ] Одна площадка сообщества с SLA ответа, не пять мёртвых.
- [ ] Статус-страница; шаблон апдейта из 4 пунктов; Next update by.
- [ ] Разделение IC и Comms на P1 (хотя бы два человека).
- [ ] Шаблон на утечку и на смену цены согласован с legal.
- [ ] Постмортем: окно 24–72 ч наружу, action items с владельцами.

Сигнал лжи: запуск «в Twitter», база знаний из пяти заглушек, основатель — единственный, кто умеет написать статус.

## Чек-лист главы

- [ ] Deflection не является северной звездой поддержки.
- [ ] Klarna-урок учтён: cost-метрика без CSAT/re-contact запрещена как единственная.
- [ ] Diátaxis: четыре типа не смешаны в одном документе без пометки.
- [ ] Docs в PR фичи, не в «потом».
- [ ] NPS сегментирован по тарифу и каналу опроса.
- [ ] Ответы на стор-отзывы идут ≤24 ч хотя бы на 1★/2★.
- [ ] TTFV измерен, звёзды GitHub не в отчёте совету.
