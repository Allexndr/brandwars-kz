# Глава 24. Инфраструктура, cloud и внутренняя платформа

*Коротко. Инфраструктура — слои, на которых бежит продукт, и команда, которая продаёт эти слои внутренним клиентам. Глава: что поднимать на каждой стадии, IaC без дрейфа, когда Kubernetes — выстрел в ногу, экономика serverless, сеть и край, идентичности вместо ключей, окружения, golden path, DevEx как метрика.*

*DORA 2025: 90% организаций имеют минимум одну внутреннюю платформу, 76% — выделенную платформенную команду. Качество платформы — один из семи усилителей эффекта AI. Это не индульгенция строить Backstage на десятерых.*

*Выбор облака vs bare metal vs гибрид как ставка стека — Глава 16.4–16.5. Cost per request и FinOps-рычаги (Savings Plans, Spot, rightsizing) — Глава 22.6–22.8. Секреты приложения, KMS, ротация ключей данных — Глава 32.5. Здесь — инфраструктурный контур: слои, платформа, доступ раннеров и кластеров.*

*Читать, когда счёт облака растёт быстрее MAU, новый инженер неделю добывает доступы, или «мы на K8s, утилизация 8%».*

Инфраструктура не равна Kubernetes. Это ответ на вопросы: где исполняется код, кто выдаёт идентичность, как воспроизводится окружение, сколько минут до первого деплоя нового человека, что происходит, когда облако врёт.

CNCF 2025 (628 респондентов, сентябрь 2025): 98% организаций применяют cloud native, 82% пользователей контейнеров запускают Kubernetes в проде (66% в 2023), 66% хостят на нём генеративный AI. Главный барьер — не технология: 47% называют культурные изменения в командах разработки. GitOps — маркер зрелости: 0% у explorers, 58% у innovators. Карго-культ читается так: скопировать 82%, не скопировать культуру и праваizing.

Cast AI 2025 по десяткам тысяч production-кластеров: средняя утилизация CPU 8% (было 10%), memory 20%, GPU 5%; переподготовка CPU (аллоцировано vs запрошено) 69% (было 40%). Kubernetes сам не даёт эффективности. Gartner: к концу 2026 80% крупных инженерных организаций будут иметь платформенные команды (45% в 2022). DORA 2024: 89% используют IDP; эффект +8% индивидуальной продуктивности, +10% результативности команды, +6% SDO организации — и −8% throughput, −14% стабильности изменений. Платформа не бесплатна: централизует решения и добавляет точку отказа. Выигрыш — на масштабе и во времени.

Для 1–3: managed Postgres, managed контейнеры или serverless, Terraform/OpenTofu на один каталог, без своей платформенной команды. Для 10–30: гибрид, thinnest viable platform (2 человека на 3–5 продуктовых команд). Для 100+: 4–8 инженеров платформы + продакт-менеджер; golden path как продукт.

## 24.1. Слои инфраструктуры и что действительно нужно на каждой стадии

Слои снизу вверх: железо/облако → сеть и идентичность → runtime (VM, контейнер, функция) → данные и очереди → delivery (CI, registry, GitOps) → наблюдаемость → продукт. Пропуск нижнего слоя не заменяется верхним: отличный портал не лечит отсутствие backup.

Стадия «идея / 1–3 человека». Нужны: один регион, один аккаунт облака с MFA, managed БД с автобэкапом, object storage, CI. Не нужны: мультиаккаунт, service mesh, свой Kubernetes, внутренний портал. Чем платите за ранние слои «как у Netflix»: toil, который съедает discovery (Глава 5).

Стадия «есть пользователи / 10–30». Добавляются: отдельные AWS-аккаунты/проекты prod и non-prod, IaC на модулях, staging, секрет-менеджер, базовые SLI, CDN на статику, WAF на публичный край. Runtime — managed контейнеры или маленький кластер с человеком, который умеет CNI. Мультирегион — только если есть сценарий и drill (Глава 12.5).

Стадия «масштаб / 100+». Платформа: golden path создания сервиса, policy as code, workload identity, GitOps, FinOps-атрибуция по сервису, клетки/поды если blast radius «все клиенты» неприемлем. Здесь же — отдельный слой AI-инференса со своим SLO и счётом (Глава 13.8), не «ещё один Deployment».

Правило откладывания: слой вводится, когда есть владелец и метрика. «Потом пригодится mesh» без NetworkPolicy — пропускаете ступень. Порядок наращивания сети: Security Group / NetworkPolicy → видимость (Hubble/flow logs) → mTLS → L7-меш, и только когда L7 реально нужен.

Vendor lock-in терпим на managed БД и auth, смертелен на уникальном control plane без плана выхода (Глава 16.5). Репатриация 37signals: с $3,2 млн/год облака до существенно меньше $1 млн, проекция >$10 млн за 5 лет (DHH, 2024–2025). Имеет смысл при предсказуемой нагрузке, своей Linux-экспертизе, больших объёмах хранения. Не имеет: резкие пики, малая команда, зависимость от managed-сервисов, где TCO своей эксплуатации выше.

## 24.2. Инфраструктура как код: модули, окружения, дрейф, ревью

IaC — git как источник желаемого состояния. Ручное изменение в консоли без записи — инцидент дрейфа, не «временно».

На 2026 год. OpenTofu — MPL 2.0, Linux Foundation, CNCF Sandbox с апреля 2025, нативное шифрование state с 1.7. Terraform — BSL 1.1, HashiCorp/IBM; сделка закрыта февраль 2025 (часть источников указывает декабрь 2024). HCP Terraform закрыл бесплатный тариф в марте 2026. Доли рынка разъезжаются в оценках агрегаторов (OpenTofu ~12% практиков, Terraform 33–62%) — не норматив. Дефолт для greenfield и OSS-first: OpenTofu. Оставаться на Terraform, если HCP Stacks в проде, IBM Cloud Pak, Sentinel как основа governance, закупки требуют HashiCorp.

Crossplane — control plane для мультиоблака в зрелых организациях, не замена модулей «по умолчанию». Pulumi — когда инфраструктура генерируется программно и команда не хочет второго языка.

Модули. Граница модуля — единица владения и blast radius: сеть, кластер, datastore, сервис. Модуль «вся компания» неотревьюваем. Версии модулей пинятся; `latest` модуля = `latest` образа.

Окружения. Один код, разные tfvars/workspaces/stacks: не копипаста каталога `prod2`. State — раздельный на prod; доступ на apply prod — отдельно от apply preview. Шифрование state (нативное у OpenTofu или encrypted backend) обязательно: в state попадают секреты, даже если вы «не хотели».

Дрейф. GitOps (Argo CD / Flux, оба CNCF graduated, конец 2022) реконсилирует runtime. IaC-дрейф облачных ресурсов — periodic plan / drift detect, не «когда сломается». Self-heal без policy — автоматика, которая возвращает ручной hotfix. Kill switch на реконсиляцию нужен так же, как на DNS-planner (урок us-east-1, октябрь 2025, Глава 12).

Ревью. Plan в PR, apply от CI по merge в protected branch, не с ноутбука. Policy: запрет публичных SG 0.0.0.0/0 на SSH, запрет нешифрованных бакетов, обязательные теги `service`/`owner`/`env`. OPA/Sentinel/Checkov — порог, не отчёт в PDF.

Для 1–3: один каталог, remote state, plan в PR. Для 10–30: модули, разный state, policy на публичные поверхности. Для 100+: платформенные модули как продукт, версионирование, внутренний registry модулей.

## 24.3. Kubernetes: когда он нужен и когда это выстрел в ногу

Kubernetes нужен, когда есть много сервисов с разными масштабами, потребность в унифицированном runtime, платформенная команда или человек, способный отладить CNI и планировщик, и нагрузка, на которой serverless-экономика уже проиграла.

Не нужен, если нет такого человека; сервисов меньше пяти; нагрузка спайковая и низкая; нет требования портируемости между облаками; команда <10 без выделенного DevOps. Ориентир: <10 инженеров — serverless или managed-контейнеры (Cloud Run, Fargate, App Service); 10–30 — гибрид; 30+ с платформенной командой — полноценный кластер.

Выстрел в ногу выглядит так. Кластер «для резюме». Утилизация CPU 8% при 69% overprovision (Cast AI, 2025). Sidecar-меш на 12 сервисах. Операторы, которых никто не умеет апгрейдить. `:latest` и Privileged. Мультикластер «для HA» без понимания control plane.

Service mesh. Sidecar-эра закончилась как дефолт. Istio Ambient GA в 1.24 (ноябрь 2024): per-node ztunnel для L4 + mTLS, waypoint на namespace для L7. Cilium — mesh в ядре через eBPF. <50 сервисов — почти всегда overkill; NetworkPolicy + observability закрывают потребность. Если CNI уже Cilium — не поднимайте второй стек. AWS App Mesh: end of support 30 сентября 2026, миграция обязательна.

Порядок: Pod Security `restricted` по умолчанию; ResourceQuota/LimitRange; NetworkPolicy default-deny; autoscaling по правильной метрике (не CPU на IO-bound); Karpenter/cluster autoscaler + праваizing. Цель утилизации после rightsizing — порядок 40–60% CPU, не 8%. GPU: 5% средняя утилизация при растущих ценах (H200 Capacity Block +15% в январе 2026) — отдельный пул и очередь, не «ещё node group».

Когда K8s применять рано: регулятор требует изоляцию на уровне namespace+policy; нужны identical preview-окружения пачками; GPU-пул с шарингом. Чем платите: 1–2 FTE на кластер минимум. Сигнал ошибки: инцидент «DNS в кластере», и в комнате нет человека, который читает CoreDNS логи.

## 24.4. Serverless и управляемые сервисы: экономика и границы

Serverless (Lambda, Cloud Functions, Cloud Run scale-to-zero) покупает отсутствие toil на нодах ценой: холодных стартов, лимитов длительности, vendor API, мультидименсионального биллинга (запрос × GB-s × egress × API Gateway × NAT).

Экономический перелом serverless → постоянный runtime (K8s/VM) для одного API-сервиса — порядок 1–3 млн запросов в день (~30–40 млн/мес) в модельных таблицах 2025–2026. Сдвигается радикально от длительности, памяти, стоимости API Gateway/NAT и утилизации нод. Все опубликованные таблицы — модельные расчёты, не измерения: считайте на своём профиле (салфетка Главы 9.6 × cost per request Главы 22.6).

Когда serverless уместен: спайки, низкий steady state, event-driven (загрузка файла → обработка), команда без платформы, cron/jobs. Когда нет: постоянные 200+ rps с тяжёлым теплым кэшем в процессе; длинные соединения (WebSocket) без отдельного сервиса; нужен предсказуемый p99 без cold start; GPU. Гибрид нормален: API и воркеры на Cloud Run/Fargate, стейтфул и realtime — на сервисе с процессом.

Управляемые БД, очереди, object storage — дефолт до масштаба, где стоимость или лимиты жмут. Граница: когда idle-стоимость кластера меньше, чем managed + когда нужны расширения/суперпользователь, которых нет у вендора. Не путайте «RDS дороже EC2 Postgres на бумаге» с TCO, где 0,3 FTE DBA.

Prime Video опубликовал разбор (2023): перевод audio/video monitoring с распределённых Step Functions на процесс на VM снизил стоимость на 90% на этом контуре. Урок — не «serverless плох», а «оркестрация на горячем пути с высокой скважностью — другой паттерн» (см. Главу 13.7). Копировать вывод на CRUD-API нельзя.

Для 1–3: serverless + managed DB, пока счёт и холодный старт не болят. Для 10–30: гибрид по профилю. Для 100+: serverless для края и jobs, ядро — на платформенном runtime.

## 24.5. Сеть, DNS, сертификаты, edge и CDN

DNS — control plane, который кладёт всё. AWS us-east-1 19–20 октября 2025: пустая запись `dynamodb.us-east-1.amazonaws.com` из гонки DNS Planner/Enactor; каскад пережил первопричину. У себя: несколько резолверов, мониторинг NXDOMAIN на критичных именах, TTL осознанный (низкий TTL — быстрый failover и выше QPS на DNS; высокий — кэш переживает ваш инцидент), не одна зона в одном аккаунте без бэкапа.

Сертификаты. На 2026 де-факто: ACME (Let’s Encrypt, облачные ACM) + cert-manager в кластере (58% production use, CNCF 2025). Срок жизни публичных сертификатов индустрия укорачивает; автоматизация выпуска — не опция. За 30 дней до expiry — алерт. Wildcard на `*.prod` удобен и расширяет blast radius компрометации ключа.

Edge и CDN. Статика и медиа — CDN (Глава 13.7). API — CDN/кэш только если кэш-ключи и Authorization согласованы (Airbnb ушла с GraphQL POST, который CDN не кэшировал). TLS 1.3, HTTP/3/QUIC там, где клиенты выигрывают на потере пакетов (Глава 9.4). WAF — на известные классы, не как замена доступа (Глава 32).

Сеть в облаке. Private subnets для данных; egress-allowlist важнее бесконечного ingress-фильтра: ломает exfiltration, SSRF, червей. NAT — статья счёта ($0.045/GB плюс часы NAT Gateway на AWS, порядок 2026). Cross-AZ $0.01/GB в сторону: болтливый mesh без zone affinity — скрытый налог (Глава 9.1, 13.2). Prefersamezone / topology spread — конфигурация, не «оптимизация потом».

Для 1–3: DNS у облака, managed certs, CDN на статику. Для 10–30: раздельные зоны prod, мониторинг DNS, egress из данных. Для 100+: Anycast/edge PoP по гео, DNS load shedding, runbook на «вендор DNS деградировал».

## 24.6. Секреты, идентичности и доступы в инфраструктуре

Целевое состояние 2026: в CI не хранится ни одного долгоживущего облачного ключа. Workload identity: job получает OIDC JWT (репозиторий, ветка, workflow, environment) → облако проверяет JWKS и trust policy → временные креды на 15–60 минут. Украденный на раннере токен бесполезен через минуты. В инциденте `tj-actions/changed-files` у репозиториев на чистом OIDC эксфильтрованные токены протухали быстрее, чем атакующие их обрабатывали.

Trust policy без ограничения по `sub` (репозиторий, ref, environment) выдаёт роль любому workflow организации. Production-секреты скоупятся на environment с protection rules, не на репозиторий. Аудит имён `AWS_ACCESS_KEY_ID`, `GCP_SA_KEY` в org — тикет миграции с дедлайном.

Секреты, которые нельзя убрать (ключи подписи, webhook, API без OIDC): secret manager, ротация по расписанию, не чтение 90 дней — кандидат на удаление. GitGuardian 2026: 28,65 млн новых захардкоженных секретов в публичном GitHub за 2025 (+34% г/г); 64% валидных секретов 2022 года всё ещё не отозваны. Хранение, envelope encryption, KMS, ротация DEK/KEK — Глава 32.5. Не дублируем.

Kubernetes: `automountServiceAccountToken: false` по умолчанию; bound tokens с audience; External Secrets / SOPS, не секрет в etcd plaintext и не секрет в Git. GitOps принуждает к нормальной стратегии секретов: закоммитить Vault-путь нельзя прилично — и это польза.

Человек: SSO + MFA на облако; JIT-эскалация на 1–4 часа вместо постоянных админов; запрет долгоживущих access keys людей. Break-glass — отдельный контур с алертом на каждое использование.

Режим отказа OIDC: недоступность эндпоинта блокирует деплой. Это сознательный размен — недоступность видна, компрометация статического ключа может жить месяцами.

Для 1–3: OIDC в CI, секрет-менеджер облака, MFA. Для 10–30: environment isolation, JIT, ESO. Для 100+: федерация всех workload, SIEM на secret manager, периодический access review.

## 24.7. Окружения: prod, stage, preview, локальная разработка, тестовые данные

Паритет. Совпадает обязательно: версия рантайма и ОС, схема БД, топология зависимостей, admission policies, способ доставки конфига, тип лимитов (не величина). Не обязательно: масштаб, объём данных, стоимость, число реплик. Тихо расходится: версии сайдкаров, TLS, таймауты ingress, дефолты флагов, TZ/locale.

Prod — единственное место с реальными пользователями и реальными деньгами. Stage — интеграция полного графа на уменьшенном масштабе, не «кто последний задеплоил». Общий stage без изоляции даёт флейки и очередь.

Preview / ephemeral: окружение на PR, URL `pr-N.preview.example.com`, teardown на close/merge. Лечит очередь за stage и «у меня локально работает». Стоимость, по убыванию эффекта: агрессивный teardown; idle timeout / scale-to-zero; hard TTL (типично 7 дней); не поднимать кластер БД на каждый PR — database branching или схема на PR; заниженные requests + ResourceQuota; spot-ноды; лимит конкурентных окружений. Wildcard DNS, без тикета на каждую запись.

Данные — узкое место, не деплой. Никогда не направлять preview на production-данные. Лестница: сид-датасет → read-only снапшот → branching с маскированием → анонимизированный клон. Маскирование — хук клонирования, не ручной шаг (право на забвение — Глава 33.4). «Анонимизировали: убрали email» — ложная анонимизация.

Локальная разработка. Цель — <30 минут до полезного изменения. Tilt/Skaffold/compose для зависимостей; seed; секреты — фиктивные. Не требование «мини-prod на ноутбуке»: паритет типов, не паритет масштаба. Remote-dev (cloud workstation) — когда сборка не влезает в ноутбук, не как статус.

Для 1–3: prod + локаль + CI. Stage — когда появился второй человек, ломающий первого. Для 10–30: stage + preview с TTL. Для 100+: self-service preview в платформе, квоты, маскирование как default.

## 24.8. Внутренняя платформа и golden paths: платформа как продукт

IDP (Internal Developer Platform) — движок: провижининг, пайплайны, observability, политики за self-service интерфейсом. Internal Developer Portal — руль: Backstage, Port, Cortex. Golden path — предопределённый поддерживаемый маршрут для типовой задачи (новый сервис, новый джоб, новый крон). Путают портал с платформой: каталог без провижининга — вики с UI.

Три принципа работающей платформы: внутренние клиенты, не «пользователи тикетов»; golden path — стандартный маршрут, не клетка (команда может уйти, приняв последствия); метрика — DevEx, uptime — необходимое условие.

DORA 2025: 90% имеют платформенную практику, 76% — выделенную команду; качественная платформа усиливает орг-эффект AI и при этом связана с небольшим достоверным ростом нестабильности поставки (CFR, rework). Как читать противоречие DORA 2024 (−8% throughput, −14% стабильности): типичная кривая трансформации — ранние выигрыши, спад, восстановление по мере созревания. Мандат на сырую платформу фиксирует спад.

Puppet/Perforce Platform Engineering 2026 (820 респондентов): 73% зрелых по платформе считают зрелость критичной для успеха AI против 44% незрелых; доверие к AI 81% vs 48%; до 92% при стандартизированном IDP. Только 21,6% платформенных команд имеют выделенного PM (оценка консультантов — порядок, не перепись). Около 30% не трекают метрик платформы.

Штат. 2 человека тянут thinnest viable platform на 3–5 продуктовых команд. На 100+ разработчиков: 4–8 инженеров + PM + бюджет на инструменты. Ребрендинг ops в «платформу» без смены модели (тикет-очередь осталась) — бутылочное горлышко.

Golden path должен совпадать с рабочим процессом: `create-service` → репозиторий с CI, SLO-заготовка, дашборд, сеть, идентичность, on-call заглушка. Если путь требует новый DSL и смену мышления — adoption низкий независимо от качества движка.

Backstage: #5 по velocity в CNCF 2025, production use — единичные проценты. Базовый инстанс — недели; production-grade — 6–12 месяцев и 2–3 инженера постоянно. Оценки трёхлетнего TCO самохостинга (1,2–2,5 млн евро vs 150–450 тыс. managed) — консультантские, не аудит. Для <100–150 разработчиков своя сборка Backstage редко окупается: каталог в существующем портале или managed.

Антипаттерн мандата: malicious compliance, обходные пути, −14% стабильности без +10% результативности. Платформа продаётся adoption: время до первого деплоя, NPS/DXI, доля сервисов на path добровольно.

Для 1–3: golden path = README + cookiecutter + CI template. Для 10–30: два человека, 3–5 путей (сервис, джоб, фронт). Для 100+: платформа как продукт с роадмапом, PM, отказом от тикетов на типовое.

## 24.9. Developer experience как метрика: время до первого коммита, длительность цикла

DevEx — трение на пути от намерения до изменения в проде. Не «счастье в опросе» отдельно от системы: DX Core 4 (декабрь 2024, DX; Forsgren и Storey в составе) сводит Speed (diffs + perceived delivery), Effectiveness (DXI, 14 Likert), Quality (CFR), Impact (доля времени на новые возможности). Заявленные +3–12% эффективности и +14% времени R&D на фичи — вендорские данные, направление полезно, абсолют не копировать. SPACE (2021): не сводить продуктивность к одной цифре.

Что мерить у себя, привязав к сервису, не к человеку:

- Time to first commit / first deploy: новый инженер, новый сервис. Цель порядка: первый полезный коммит в день 1, первый деплой в preview <1 дня. Онбординг — Глава 41.6.
- Change lead time: коммит → прод (DORA). Топ-24,4% команд быстрее дня (DORA 2025).
- CI wait: очередь и длительность pre-merge. Порог TBD — 10 минут.
- Self-service rate: доля типовых workflow без тикета в платформу.
- Adoption golden path: доля новых сервисов на пути, добровольно.
- Perceived friction: квартальный DXI или 5 вопросов. Без опроса системные метрики врут.

DORA на людей и стек-ранкинг команд запрещены (Глава 42.9). Сравнение — одна команда во времени. AI увеличил throughput генерации и время ревью: мерить review wait отдельно, иначе «ускорились», а lead time вырос.

Когда метрика вредна: цель OKR «снизить lead time на 40%» без CFR. Чем платите: мелкими бессмысленными деплоями и обходом ворот. Сигнал ошибки: DXI падает, деплои растут.

Пример. Компания 80 инженеров, платформа год, Backstage есть, time to first deploy — 4 дня (тикеты на IAM, namespace, DNS). Self-service rate 20%. Лечение: один path «сервис», OIDC и wildcard DNS, квота namespace. Через квартал first deploy <4 часов, adoption 60%, тикеты — только исключения. Не начинали с портала плагинов: убрали тикет как единственный API.

## 24.10. Чек-лист инфраструктурной зрелости

**Стадия и слои**

- [ ] Слои 24.1 соответствуют размеру команды; K8s и mesh не введены «на вырост».
- [ ] Владелец каждого слоя назван; слой без метрики не расширяется.

**Код и дрейф**

- [ ] IaC: plan в PR, apply из CI, раздельный state prod.
- [ ] Дрейф детектится; self-heal имеет kill switch.
- [ ] Теги owner/service/env обязательны политикой.

**Runtime**

- [ ] K8s: есть человек на CNI; PSS restricted; requests≠limits без причины; утилизация не 8% «норма».
- [ ] Serverless/K8s выбраны по профилю и салфетке стоимости, не по моде.
- [ ] Mesh нет либо есть причина L7; App Mesh не остаётся после 30.09.2026.

**Идентичность и край**

- [ ] CI ходит в облако по OIDC; статических ключей в secrets org нет.
- [ ] Trust policy сужена до репо/ветки/environment.
- [ ] DNS мониторится; сертификаты автовыпускаются; алерт за 30 дней.
- [ ] Egress из data-слоя не «весь интернет».

**Окружения и платформа**

- [ ] Preview с teardown и TTL; prod-данные не в preview.
- [ ] Golden path покрывает «новый сервис»; тикет не единственный API.
- [ ] Time to first deploy и self-service rate пишутся; платформа имеет внутренний роадмап.

**Деньги**

- [ ] Cost per service виден (Глава 22); неатрибутированное < порога.
- [ ] Rightsizing сделан до Savings Plans; Spot не сжигает RI.

## Чек-лист главы

**Соответствие масштабу**

- [ ] Для 1–3 нет кластера «как у взрослых»; для 100+ есть платформенная команда, не переименованный ops.
- [ ] 90%/76% DORA 2025 не использованы как аргумент строить портал раньше path.

**Эксплуатация**

- [ ] Workload identity вместо ключей в CI.
- [ ] Паритет типов окружений соблюдён; данные для тестов выбраны до автоматизации preview.

**Продукт платформы**

- [ ] Golden path можно пройти без тикета.
- [ ] DevEx-метрики есть хотя бы две: системная и опросная.
