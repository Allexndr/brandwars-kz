# Глава 29. ML в продукте

*Коротко. ML — когда паттерн в данных стабильно бьёт правила на holdout и вы платите за serving и мониторинг. Иначе — 10–20 ветвлений. Поиск 2026 — гибрид BM25+dense, RRF, rerank. Рекомендации — воронка кандидатов и ranker, не «нейросеть ленты». Фрод — каскад правил и модели в authorization path. Skew на запуске убивает чаще, чем слабая архитектура.*

*Глава: когда не ML; поиск и оценка; рекомендации; персонализация в реальном времени; антифрод; утечки и training/serving skew; MLOps; экономика инференса классических моделей (LLM — Глава 30).*

*События и фичи из склада — Глава 27. Онлайн-оценка — Глава 28. Операционные векторы как хранилище — Глава 18.4, здесь retrieval как продукт. Каркас очередей AI — Глава 13.8. Безопасность модели — пересечение с 32; T&S — 34. Цена токенов и агентов — 30.8 и 6.4.*

«У нас есть данные» ≠ нужна модель. Правила выигрывают, пока задачу кодируют 10–20 ветвлениями, labels мало или грязные, регулятор требует объяснимость, распределение прыгает быстрее цикла ретрейна. ML оправдан, когда holdout стабильно лучше эвристики **и** есть бюджет на parity online/offline, drift, rollback.

Вторая ошибка — начать с модели, а не с воронки. Поиск без BM25 на SKU; лента без candidate generation; фрод без velocity-правил. Индустрия уже собрала двухстадийные каноны (YouTube RecSys 2016; поисковый hybrid 2026). Третья — утечка будущего в фичу и две реализации трансформа: в ноутбуке pandas, в проде «почти то же». Google Rules of ML, rule 37: зазор next-day→live ловит serving skew.

Для 1–3: правила + управляемый поиск (Postgres FTS / Typesense), без feature store. Для 10–30: гибридный поиск или одна модель с shadow, метрики качества в CI. Для 100+: feature store, несколько источников кандидатов, каскад фрода, FinOps на предикт.

## 29.1. Когда задача действительно требует ML, а когда достаточно правил

Правила — код с порогами: velocity, allow/deny lists, «если запрос содержит SKU — BM25 first». Их можно объяснить, откатить, покрыть тестом. Они проигрывают, когда комбинаций больше, чем ветвлений, и паттерн устойчив в данных.

Тест на ML. (1) Есть labels приемлемой задержки и шума. (2) Эвристика уже сняла сливки, остаток систематический. (3) Holdout бьёт правило по метрике, связанной с деньгами или retention, не по accuracy в вакууме. (4) p99 serving вписывается в бюджет ручки. (5) Есть владелец на ретрейн и drift. Если нет (1) или (5) — сначала разметка и операции, не архитектура.

Когда ML вреден: юридический запрет без человека (часть AI Act — Глава 33.7); холодный старт без контентных фич; «персонализация» при 200 DAU. Чем платите: latency, skew, молчаливая деградация. Сигнал ошибки: модель вместо KYC; или классификатор там, где regex по коду ошибки закрывает 95%.

Сквозной пример. Поддержка. Правила: FAQ keyword + точный код ошибки → статья. ML/LLM — перефраз и многоязычность, когда Recall@10 правил вышел на плато и есть golden queries. Не наоборот.

Для 1–3: таблица «правило / порог / метрика». Для 10–30: A/B правила vs модели на одной primary (Глава 28). Для 100+: каскад (29.5).

## 29.2. Поиск: лексический, семантический, гибридный, ранжирование, оценка качества

Три семейства retriever'ов.

| Семейство | Сигнал | Сильные | Слепые |
|---|---|---|---|
| Лексический (BM25 / sparse) | термы, IDF | SKU, имена, коды, редкие токены, юридические формулировки | синонимы, intent «как сделать X» |
| Dense embeddings | близость векторов | перефраз, многоязычность | точные id, новые термины вне энкодера |
| Гибрид | оба + fusion | закрывают дыры друг друга | два индекса, два отказа |

Production-дефолт 2026: оба retriever'а параллельно → Reciprocal Rank Fusion → cross-encoder rerank → top-k в UI или в RAG (Глава 30.3). Notion, Perplexity, Vespa, Azure AI Search — публично на гибриде. Vector-only приемлем для «похожие документы», опасен для support/SKU.

RRF (Cormack, Clarke, Buettcher, SIGIR 2009): \(\mathrm{RRF}(d)=\sum_r 1/(k+\mathrm{rank}_r(d))\), типично \(k=60\). Не нормализует несравнимые BM25 и cosine — работает рангами; k в диапазоне 30–100 слабо влияет. Взвешенная сумма после min-max требует калибровки на корпус; RRF выиграл как default из-за «не калибровать».

Двухстадийный бюджет: stage-1 recall — top 50–100 с каждого retriever'а; RRF; stage-2 — cross-encoder на 50–100 → top 5–10. Cross-encoder видит пару (query, doc), точнее bi-encoder, O(n) forward-pass — только короткий список. Латентность rerank 100–300 мс типична для API-rerankers — закладывать в SLO. Индекс не источник правды: документ живёт в OLTP, в поиск уходит проекция (Глава 18.4).

Офлайн на qrels: Recall@k для stage-1 (цель высокий Recall@100: нет золота в сотне — reranker не воскресит); nDCG@k — дефолт, когда порядок в UI важен, умеет graded 0/1/2; MRR/MAP — «один правильный ответ» (FAQ); Precision@k токсичен как единственная метрика — легко показать 3 очевидных хита. Онлайн: CTR позиции врёт из-за position bias; канон — position-normalized или interleaving (Team Draft / Balanced). Офлайн nDCG врёт, когда асессоры ≠ пользователи.

Золотой набор гниёт: новые документы и запросы. Режим: еженедельный семпл live-запросов + разметка; CI гоняет nDCG/recall на frozen set + свежий canary. Падение Recall@100 на canary — блокер релиза индекса.

Postgres FTS / Typesense / Meilisearch — до продукта «поиск» и среднего корпуса. Elasticsearch/OpenSearch — полнотекст + фасеты + объём. Векторный движок — операционный выбор 18.4 (pgvector до ~10–50 млн чанков), не замена BM25.

Для 1–3: FTS или hosted search, разметка 50 запросов. Для 10–30: гибрид + rerank, eval в CI. Для 100+: свои энкодеры, интерливинг, SLO свежести индекса (документ в поиске ≤ T минут).

Когда dense-only вреден: каталог с артикулами. Сигнал ошибки: «семантический поиск» без BM25 и без Recall@100.

## 29.3. Рекомендации: генерация кандидатов, ранжирование, разнообразие, холодный старт

Канон — двухстадийная воронка YouTube (Covington, Adams, Sargin, RecSys 2016): candidate generation (сотни из миллионов, десятки мс) → ranking (тяжёлая модель на сотнях фич). Позже multi-task (клик + watch time + негатив) и MMoE как типичный ranker с несколькими головами. Публичные внутренности 2024–2026 ограничены; кости те же.

Кандидаты — не одна модель, а **5–20 источников**, union, дедуп, per-source квоты: two-tower (user × item, dot product, ANN: HNSW / ScaNN / IVF-PQ) — workhorse, item-эмбеддинги прекомпутятся, user — на запросе; entangled cross-attention в башне ломает ANN. Плюс co-watch / item2vec; подписки; freshness/trending (иначе новое не наберёт статистику); content-based для cold item; popularity/geo fallback. Метрика stage-1: Recall@K на held-out (K=100–1000). Latency: единицы–десятки мс. Two-tower не выразит «любит длинные этого автора, но не шортсы» так богато, как ranker — цена скорости.

Ranking на 100–1000 кандидатах: cross-features user×item, контекст (время, устройство, позиция в сессии). MLP / Wide&Deep / DCN / DLRM / трансформер на истории. Оптимизация не «клик»: клик ловит clickbait. YouTube взвешивал позитивы watch duration. Сейчас типично multi-objective: engagement, satisfaction, dislike/skip/hide, diversity proxy, integrity. Офлайн: nDCG@k / AUC / logloss на следующем взаимодействии. Онлайн: session value, не CTR карточки. Расхождение офлайн/онлайн — норма; шип по офлайн без A/B — антипаттерн (Глава 28).

Разнообразие. Filter bubble — продукт ranker'а на мгновенный engagement. Post-processing: MMR (relevance vs несхожесть с уже выбранными); квоты (не более N из одного creator/category); DPP теоретически чище, на практике тяжелее MMR.

Холодный item: content encoder (текст + картинка) до первого клика; exploration quota в mix; creator prior. Холодный user: контекст/демография (осторожно с fairness), popularity, явный выбор в онбординге. Холодная система: только content-based, пока нет матрицы. Exploration vs exploitation — отдельный эксперимент (ε-greedy, Thompson на уровне источника), не «случайные 10% и забыли». На маркетплейсе новое не в топ-1, а в слот 8–12 — guardrail UX.

Для 1–3: популярное + content similarity + явные предпочтения. Для 10–30: two-tower или co-visitation + простой ranker. Для 100+: много источников, multi-objective, integrity scores (Глава 34).

Когда коллаборатив вреден: каталог обновляется быстрее, чем матрица; или регуляторный запрет на профилирование (Глава 33). Сигнал ошибки: одна модель end-to-end на миллионах item в p99 50 мс.

## 29.4. Персонализация и сегментация в реальном времени

Персонализация — подстановка опыта под контекст сейчас: тариф, этап онбординга, риск, последний intent, эксперимент. Это не обязательно deep ranker. Часто это сегмент + правила + 3–5 online-фич.

Сегментация. Статическая (план, гео, когорта регистрации) живёт в OLTP/warehouse и обновляется батчем. Динамическая (активен ли путь к активации, «только что искал биллинг», velocity) требует online store: ключ `user_id`, TTL, то же определение, что в обучении, если сегмент кормит модель. Микросегмент из 12 человек в A/B — путь к 28.6 (множественные сравнения) и к пустому UX. Правило покрытия: сегмент как рычаг продукта должен иметь достаточно юнитов, чтобы его можно было двигать и измерять; иначе это one-off ручной список, не персонализация.

Реальное время. Если решение автоматическое и ценность падает за секунды — стрим (Глава 27.3) пишет фичу в Redis/Valkey/Dynamo, p99 lookup единицы–десятки мс. Если «персонализация» = другая сортировка раз в час — micro-batch. Не строить Flink, чтобы поменять баннер. Смешивать батч-сегмент «план Pro» и стрим-фичу «открыл поиск 30 с назад» можно: разные TTL, один API `GetExperience(user_id, surface)`.

Контур. Identify и value-events (27.2) → silver → (а) батч-сегменты в gold, (б) stream → online features → API «какой опыт показать». Feature store (29.6) оправдан, когда сегменты делят несколько моделей и SLA <100 мс. Иначе одна таблица `user_state` с версией схемы.

Сквозной пример. Онбординг SaaS. Статический сегмент: `plan`, `role`. Динамика: `notes_created_7d`, `activated` (бинарный, T=24 ч), `last_search_intent`. Экран home: если не activated — чеклист к `NoteCreated`; если activated и `last_search_intent=billing` — блок тарифа, не лента шаблонов; если Pro и пустой поиск — подсказка по командам. Ranker ленты подключается, когда кандидатов >20 и CTR без персонализации вышел на плато. До этого правила дешевле и объяснимее.

Этика и право. Профилирование, согласия, ограничение спецкатегорий — Глава 33.6. Персонализация цены и тёмные паттерны — 37.7. Integrity: персонализация не обходит бан (Глава 34). Guardrail эксперимента: персонализация не режет доступность и не взрывает cost per user. Не персонализировать отказ в праве (доступ к данным, апелляция) — это не UX, это compliance.

Для 1–3: 3–5 сегментов вручную (план × activated). Для 10–30: батч-сегменты ежедневно + 1–2 realtime флага. Для 100+: online store, те же фичи в ранжировании и в месседжинге.

Когда realtime вреден: письмо с рекомендациями раз в неделю. Сигнал ошибки: «персонализация» = 40 копий лендинга без eval; или user_id в метке Prometheus (Глава 25.4).

## 29.5. Антифрод и риск-скоринг: признаки, пороги, обратная связь, атаки на модель

Фрод — ML на критическом пути с асимметричной ценой: false negative = деньги, false positive = живой клиент. Архитектура ближе к поисковой воронке, чем к ноутбуку.

Каскад (публичный референс Stripe Radar): (1) детерминированные правила / lists (украденные карты, velocity, geo-mismatch) — микросекунды; (2) GBDT/DNN на сотнях–тысяче фич — миллисекунды; Stripe: >1000 характеристик, решение <100 мс, «incorrectly blocks just 0.1%» легитимных — формулировка вендора; (3) 3DS / ручной review — серый хвост. Модель синхронно в authorization path, не ночным батчем. Shield NeXt (DNN) сократил training time >85%, до <2 часов; наивный отказ от XGBoost стоил ~1.5 п.п. recall — замена архитектурой, не «выключили деревья». Переобучение на свежих данных: до +0.5 п.п. recall в месяц — drift как операция. 10× больше training transactions всё ещё давали прирост (Stripe).

Фичи, которые нельзя считать «как удобно» батчем: частые IP карты, velocity 1h/24h, граф карта–девайс–аккаунт. Они живут в online store с тем же определением, что в training. Labels опаздывают: chargeback — дни–недели. Proxies: TC40/SAFE, метки аналитиков, ранние dispute. Тренироваться только на chargeback = учиться на прошлом поколении атаки.

Пороги не глобальные: per-merchant / per-geo / per-method. Один порог убивает малый бизнес со «странным» профилем. Метрики: recall на фроде, FPR на легитимных, authorization rate, $ prevented vs $ lost to FP. F1 в вакууме бесполезен.

Атаки: probing порога мелкими транзакциями; ATO vs stolen card — разные паттерны; эмуляция device fingerprint. Правила закрывают известный эксплойт быстрее ретрейна; модель ловит неизвестное. Feedback: analyst labels + chargebacks → weekly retrain, shadow до cutover (29.7). Никогда «нейросеть вместо KYC». Платежный фрод смежен с Главой 40.6 и 34.5; здесь — скоринг на пути авторизации.

Для 1–3: velocity, country/BIN mismatch, лимиты, ручной review. Для 10–30: GBDT на своих labels, порог по сегменту. Для 100+: каскад, граф, shadow, ретрейн по свежести важнее новой архитектуры на коротком горизонте (Stripe).

Когда ML фрода рано: нет labels и нет правил. Сигнал ошибки: ночной батч «риск на вчерашние платежи»; один global score.

## 29.6. Данные для ML: разметка, утечки признаков, training/serving skew, feature store

Разметка. Инструкция асессору короче, чем кажется: примеры границы, не «релевантно/нет». Двойная разметка + κ на golden. Для фрода — delayed label и правило, что делать с неизвестным. Гниль разметки = гниль модели; бюджет разметки — строка, не «стажёры вечером».

Утечка. Фича из будущего (статус чарджбэка в момент авторизации; «пользователь отменил на D30» в модели D1; агрегат, посчитанный по всей сессии, когда предикт был на первом событии). Типичные дыры: `user_ltv` из gold, куда уже вошла будущая выручка; `avg_rating` айтема, посчитанный включая клик, который предсказываете; join по `updated_at` склада вместо `event_time`. Point-in-time join: для метки в t фичи ≤ t. Иначе офлайн блестит, прод падает. Тест утечки: сдвинуть все фичи на +1 день относительно метки — если качество почти не падает, вы, возможно, не смотрите в будущее; если падает сильно — либо фичи очень свежие (законно), либо утечка. Второй тест: обучить только на фичах, доступных в serve-логе; расхождение с ноутбуком = skew или утечка.

Training/serving skew — баг дня запуска. Две реализации трансформа (pandas vs serving); NULL offline drop / online fill 0; окно «7 дней» UTC vs локаль; late events в stream, которых не было в batch. Rule 37: зазоры training→holdout, holdout→next-day, **next-day→live**. Третий ловит skew. Nubank-практика в разборах: смотреть percentiles скора, не только mean.

Feature store (Feast / Tecton / Hopsworks) убивает skew **только если определение трансформа одно**. Feast: `get_historical_features` (PIT join) vs `get_online_features`; ядро трансформаций всё ещё можно раздвоить. Tecton претендует на batch/stream/on-demand из одной дефиниции (вендор). Онлайн-стор — Redis/Valkey/Dynamo, p99 lookup единицы–десятки мс. Когда store не нужен: 1 модель, 5 фич, batch inference раз в сутки. Когда нужен: 2+ моделей делят фичи, online <100 мс, цена ошибки высока (фрод, кредит).

События из Главы 27 — сырьё. Не кормить модель gold-метрикой, которая сама содержит будущее (LTV с look-ahead). Срезы обучения версионируют вместе с кодом фич.

Для 1–3: один SQL/код трансформа для train и serve, даже без бренда store. Для 10–30: PIT join, сверка next-day vs live. Для 100+: store, parity-тесты в CI.

Сигнал ошибки: AUC 0.95 в ноутбуке, в проде как random; или `fillna(0)` только в serve.

## 29.7. MLOps: версии, офлайн- и онлайн-оценка, теневой запуск, откат, дрейф

Версия = код фич + данные среза + гиперпараметры + веса + eval-отчёт. Registry (MLflow / аналог) с тегом `production`. Rollback — переключить указатель, не «передеплоить кластер за час».

Офлайн: frozen set на каждый PR фич/модели. Онлайн: A/B или interleaving (Глава 28); для фрода — delayed labels, не CTR. Без онлайн-оценки «MLOps» — YAML вокруг pickle.

Shadow / dark launch: новая модель видит живой трафик, ответ логируется, юзеру не отдаётся. Сравнивают распределение скора, latency, и — где есть delayed label — качество. Canary доли трафика после shadow. Теневой трафик как метод качества — также Глава 31.7.

Drift. Data/covariate — вход уехал (новый SDK, новый рынок). Concept — связь x→y уехала (паттерн фрода, смена UX). Prediction — выход как симптом. Детекторы: PSI (эвристика: <0.1 спокойно, 0.1–0.25 смотреть, >0.25 существенно — правило большого пальца, не теорема), KS, null-rate, cardinality, freshness age. Алертить фичу, не ждать «accuracy упал»: метка часто опаздывает на недели. Stripe: свежие данные важнее новой архитектуры в коротком горизонте.

Eval в CI: frozen + canary live-семпл. Алерты freshness фич — пейджер владельца модели.

Для 1–3: файл модели + чеклист отката на предыдущий артефакт. Для 10–30: registry, shadow, PSI на топ-фичах. Для 100+: платформенный path, как CI сервиса (Глава 23).

Когда MLOps-платформа рано: одна модель в неделю. Сигнал ошибки: нет кнопки отката; ретрейн «когда вспомним».

## 29.8. Экономика инференса: латентность, батчинг, квантизация, стоимость на запрос

Единица — cost per successful prediction / per successful task, не GPU-час в вакууме и не HTTP 200. Юнит-экономика продукта — Глава 7; AI-GM и прайс — Глава 6.4 (ICONIQ проекция GM AI-native ~52% в 2026 vs 75–85% классического SaaS). Здесь рычаги себестоимости **классического** инференса; токены LLM — 30.8. Топология очередей — 13.8.

Latency. Бюджет ручки (Глава 22.1) режет архитектуру: фрод <100 мс → CPU GBDT или маленький DNN, не кросс-энкодер на 1000 кандидатов. Поиск: stage-1 десятки мс, rerank 100–300 мс — либо асинхронно за пределами первого экрана, либо меньший k. Персонализация lookup — единицы–десятки мс из online store, не JOIN по складу.

Батчинг. Для классики: micro-batch на GPU-ранкере ленты (собрать 8–32 запроса) vs интерактивный одиночный. Смешать онлайн-ленту и ночной пересчёт эмбеддингов в одном пуле — шумный сосед (Глава 12). Continuous batching и PagedAttention — про LLM (30.8 / 13.8).

Квантизация и дистилляция. INT8/INT4 на ранкере — если eval (nDCG, recall фрода) держится на своём сете, не «4-bit = 99% из README». Дистилляция cross-encoder → bi-encoder для stage-1. Для API-провайдера квантизация уже в цене; для self-host — VRAM vs качество.

Стоимость. Считать: (вызовы модели / день) × (себестоимость) / (успешные задачи). Кэш предсказаний по ключу `(model_version, feature_hash)` с TTL, если вход повторяется (рекомендации «похожие» для одного item). Не кэшировать фрод навечно. ANN-индекс: rebuild vs incremental — в RTO и в счёте.

Когда GPU вреден: GBDT на CPU укладывается в p99 и в деньги. Сигнал ошибки: нет cost в дашборде рядом с AUC; или hedging предикта без лимита (удвоение счёта).

Для 1–3: CPU, batch job, без GPU. Для 10–30: бюджет p99 и $/1k предиктов. Для 100+: отдельные пулы, chargeback команде-владельцу модели.

## 29.9. Чек-лист вывода модели в прод

**Нужна ли модель**

- [ ] Правила/поиск/эвристика измерены; ML бьёт их на holdout по метрике, связанной с деревом (Глава 28.1).
- [ ] Labels, владелец ретрейна, бюджет p99 и $ на 1k предиктов названы.

**Данные и parity**

- [ ] Point-in-time join; нет фич из будущего.
- [ ] Одна дефиниция трансформа train/serve; зазор next-day→live измерен (rule 37).
- [ ] PII/спецкатегории помечены; политика как у склада (Главы 27.6, 33).

**Качество и выкат**

- [ ] Frozen eval в CI; для поиска — Recall@100 / nDCG, блокер на падение.
- [ ] Shadow пройден (скор, latency, где возможно — delayed label).
- [ ] Онлайн-оценка: A/B или interleaving; primary + guardrails (Глава 28.9).
- [ ] Rollback = смена указателя в registry.

**Эксплуатация**

- [ ] PSI/null/freshness на фичах; пейджер владельца.
- [ ] Каскад фрода: правила до модели; пороги не глобальные.
- [ ] Diversity/exploration — явный слот, не случайные 10% «навсегда».
- [ ] Cost per 1k предиктов на дашборде; пулы interactive vs batch разведены.
