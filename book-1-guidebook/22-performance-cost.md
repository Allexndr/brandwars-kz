# Глава 22. Производительность и стоимость

*Коротко. Производительность без бюджета — вкусовщина. Стоимость без единицы работы — чужой счёт в конце месяца. Глава ведёт от продуктового требования к лимиту, через измерение и доказанный фикс, continuous profiling, хвост p99, нагрузку до точки перегиба, unit-cost и FinOps, и закрывается расчётом, где счёт падает без потери качества.*

*Читать после 9.1 (порядки латентностей и $ за GB), 11 (профиль нагрузки), 12 (ёмкость как плата за надёжность), 7.7 (юнит-экономика ↔ запрос). Наблюдаемость как счёт — 25.7; ёмкость пиков процессом — 26.7. Здесь — инженерная дисциплина: измерил, нашёл, доказал, атрибутировал доллар.*

*Dean & Barroso (2013): fan-out 100 при p99 листа 1 с даёт пользовательский p50 ≈ 1 с (вероятность ≥1 медленного ≈63%). AWS 2026: cross-AZ $0.01/GB в каждую сторону = $0.02/GB round trip; NAT +$0.045/GB. Flexera 2026: 29% cloud-бюджета — waste, впервые рост за 5 лет. Prime Video VQA: −90%+ инфра после схлопывания Step Functions+Lambda в один процесс.*

*Возвращайтесь, когда средний latency зелёный, а жалобы на «тормозит»; когда Kubernetes на 8% CPU (Cast AI 2025); когда оптимизировали p50; когда счёт вырос при том же MAU.*

Среднее врёт дважды. Пользователь живёт в хвосте: один медленный лист в fan-out, GC, сосед по диску, холодный код. Финансы живут в байтах и часах, которые архитектура не называла: cross-AZ болтовня, NAT, логи как 50%+ observability (ориентир 15–30% инфра-бюджета на телеметрию, Глава 25). Оптимизация без профиля — перекраска.

Вторая ошибка — чинить без доказательства. Ускорили бенчмарк на ноутбуке, в проде p99 тот же: узкое место было очередью, не CPU. Методика: измерить пользовательский сценарий → найти стек в профиле/трейсе → изменить одно → доказать тем же измерением. Без третьего шага это хобби.

Третья — считать облако «операционкой». Flexera 2026 (N=753+): 85% называют стоимость главным вызовом; 63% имеют FinOps-команду; unit economics ведут 49% (было 40%). Waste 29% (+2 п.п.). Средняя утилизация CPU в Kubernetes — 8%, memory 20%, GPU 5% (Cast AI, 2025). Горизонталь воздуха — не масштаб (Глава 11).

Для 1–3: бюджет на один сценарий, RUM или хотя бы синтетика, cost per request на салфетке 9.6, без FinOps-комитета. Для 10–30: p99 в дашборде, load test до перегиба, теги cost на сервисы. Для 100+: continuous profiling, eBPF точечно, error budget связан с perf SLO, Savings Plans на пол после rightsizing.

## 22.1. Бюджеты производительности: от продуктового требования к техническому лимиту

Бюджет начинается с пользовательского события, не с «сервис отвечает за 50 мс». Формулировка: «p75/p99 сценария X на устройстве Y в сети Z ≤ T». X — открыть ленту, оплатить, начать матч. Y — mid-range, не флагман. Z — 4G / cross-region, не офисный Wi-Fi.

Расклад сверху вниз. Пример: пользовательский p99 200 мс = 20 мс TLS+сеть до edge + 30 мс edge + 100 мс backend + 50 мс запас (Глава 9.1). Последовательные вызовы складывают латентности. Параллельные складывают хвосты: p99 листа при fan-out ≥10 становится пользовательским p50. Кросс-регион синхронно — минимум 40–70 мс US East↔West, 80–150 мс океан. Это пол, не баг.

Веб: Core Web Vitals на 2026 не сдвигались (Google): LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на 75-м перцентиле поля, 28 дней. Все три сразу. Lab (Lighthouse) — регрессия в CI, не истина поля. Мобильный клиент: TTID, crash-free (Глава 20.4) — отдельные бюджеты, не CWV.

Связь с продуктом. Deloitte × Google, 2020 (37 брендов, 30+ млн сессий): −0,1 с мобильной скорости → retail конверсия +8,4%, AOV +9,2%; travel +10,1%; lead-gen формы +21,6%. Akamai (~10 млрд визитов): 100 мс ≈ −7% конверсии. Vodafone: LCP −31% → +8% продаж (web.dev). «Amazon 100 мс = 1%» ~2006 — возраст оговаривать. Бюджет без метрики продукта — инженерный театр.

Процедура на час. Берёте один сценарий (оплата). Пишете цепочку spans: DNS, TLS, gateway, auth, inventory, payments, commit. Каждому — жёсткий cap, сумма ≤ T. Где cap меньше RTT физики — меняете топологию (регион, кэш, async), не фреймворк. Где cap съеден JSON — Глава 9.2. Где съеден lock — 17.2. Бюджет клиента (INP 200 мс, TTID 2 с) не делят с бюджетом API: это разные T на одном journey.

Когда не ужесточать: SLO 99,99% и p99 50 мс на сервисе с тремя внешними API — потолок есть произведение зависимостей (Глава 12, 26). Чем платите за бюджет «как у Google»: железом и отказом от фич. Сигнал: в RFC есть «быстро», нет T и перцентиля.

Для 1–3: один сценарий, одно T, одно устройство. Для 10–30: бюджет в CI (бандл, TTID, p99 API). Для 100+: бюджет на каждый user journey в SLO.

## 22.2. Методика оптимизации: измерь, найди узкое место, докажи улучшение

Три шага, иначе откат в понедельник.

**Измерь.** Тот же сценарий, что в бюджете. Поле (RUM, мобильный vitals) + лабораторный профиль на фикс. Без поля вы оптимизируете Chrome на кабеле. Без лаба не увидите стек. Сэмпл: не среднее одной сессии — распределение и хвост.

**Найди.** Трейс (OpenTelemetry, Глава 25) показывает где время: сеть, БД, очередь, JSON. Профиль показывает почему CPU: аллокации, замок, regex. Если трейс говорит «Postgres 80 мс», не ускоряйте сериализацию. Если профиль говорит «JSON 80% CPU», не покупайте Aurora. Discord: быстрая БД и меньше работы для БД — разные рычаги (ScyllaDB + Rust data services с coalescing).

**Докажи.** A/B или canary с теми же SLI. Одна переменная. Если p99 не сдвинулся — фикс не тот, даже если p50 −30%. Зафиксировать в ADR: было → стало → метод измерения. Иначе через квартал «оптимизация» откатится как непонятный хак.

Порядок рычагов (дешевле сверху): убрать лишнюю работу (N+1, stampede, лишний кросс-AZ) → правильный индекс/кэш с jitter (11.6) → параллелизм без fan-out хвоста → железо. Микрооптимизация цикла до удаления N+1 — антипаттерн.

Когда не оптимизировать: error budget и так зелёный, узкое место — конверсия онбординга. Чем платите за ранний perf-спринт: потерянными фичами. Сигнал: нет «было/стало» в тикете.

Для 1–3: один профайлер локально + slow query. Для 10–30: трейсы на 1–5% + правило «одно изменение». Для 100+: continuous profiling всегда включён.

## 22.3. Профилирование в проде: continuous profiling, флеймграфы, eBPF

Прод ≠ staging нагрузкой и данными. Профиль с ноутбука врёт по GC, диску, соседям.

**Continuous profiling.** Сэмплирование стеков (CPU, alloc) всегда, низкий overhead порядка единиц процентов при разумном rate — сверять на своём рантайме, не обещать «бесплатно». Флеймграф: ширина — время/сэмплы, искать плоские плато и неожиданные символы (codec, regex, serde). OpenTelemetry: traces/metrics/logs — GA; **profiles — четвёртый сигнал**, alpha/near-stable beta на момент graduation CNCF (май 2026). Инструментировать против OTel — дефолт; бэкенд — коммерческий выбор.

**eBPF.** Наблюдение ядра без инструментирования каждого процесса: сеть, syscall, планировщик. Cilium/Hubble — сеть и DNS. Профили CPU через eBPF — когда нет символов в управляемом рантайме или нужен системный взгляд. Цена: экспертиза, безопасность (привилегии), шум. Когда не: команда из трёх без человека, который отличит probe от инцидента. Когда да: 100+, latency в ядре, noisy neighbor, «в приложении чисто — в сети нет».

Что смотреть на флеймграфе в первую очередь. Плоское «плато» широкой рамки — вы в чужом коде (SDK аналитики, serde, regex на hot path). Пила одинаковых узких стеков — аллокации/GC. Время в `epoll`/`futex` — вы не CPU-bound, профиль CPU врёт, нужен off-CPU/trace очереди. Правило: не оптимизировать кадр, который не входит в p99-трейс того же сценария.

Связка с трейсами: профиль без request_id — археология. Трейс без профиля — «медленно в span X» без причины. Кардинальность меток в метриках взрывает счёт (25.4): не кладите user_id на CPU-профиль как лейбл Prometheus.

Когда не continuous: превью-окружения, локальная отладка одного запроса — достаточно pprof/Instruments один раз. Чем платите за eBPF рано: toil и поверхностью атаки. Сигнал: купили profiler SaaS, никто не открывает флеймграф в ревью инцидента.

Для 1–3: pprof/Instruments по инциденту. Для 10–30: continuous на самых дорогих сервисах. Для 100+: флот, eBPF на node, профиль в постмортеме обязателен.

## 22.4. Хвостовые задержки: почему p99 важнее среднего и как его чинить

Пользователь не усредняется. Один запрос из 100 — это «приложение тормозит» в отзыве. Математика fan-out (Dean & Barroso, CACM 2013): 100 листьев, p99=1 с → P(хотя бы один ≥1 с) ≈ 1−0,99^100 ≈ 63%. Серверный p99 = пользовательский p50.

Источники хвоста: GC, очереди, соседи, планировщик, компакции, энергосбережение CPU, холодный код, hot key. Лечение — три семьи:

1. Уменьшить вариативность: меньше co-tenancy на критичном пути, короче GC, фоновые джобы не в том же пуле (bulkhead, 12.2).
2. Маскировать внутри запроса: hedged requests. Канон: BigTable, hedge через 10 мс, p99.9 получения 1000 ключей с 1800 мс до 74 мс при +2% запросов. Порог чуть выше p50, дубли <5%. В 2026 hedge в gRPC, Envoy, AWS SDK; адаптивный порог (DDSketch) + token bucket, иначе в инциденте удваиваете нагрузку. Tied requests: в две очереди, cancel двойника. Hedging LLM/транскода кадра — удваивает деньги; не копировать.
3. Переобеспечить ёмкость — дорого; Netflix tier-0 ~30% утилизации (re:Invent 2025) как плата за эвакуацию, не как дефолт стартапа.

Jitter на TTL и на ретраях (12.3). Stampede (11.6): XFetch + single-flight. Не лечите хвост средним: алерт на avg зелёный при p99 в аду.

Когда p99 не цель: внутренний batch, где важен throughput за час. Чем платите за охоту на p99.99: железом. Сигнал: дашборд без перцентилей; бенчмарк NVMe по среднему при p99.9 в 100× (контроллер GC).

Для 1–3: смотреть p95/p99 одного API. Для 10–30: SLO на p99 сценария, не на avg. Для 100+: hedge с bucket, клетки, запрет синхронного fan-out без бюджета хвоста.

## 22.5. Нагрузочное тестирование: профиль, генерация, интерпретация

Нагрузка без профиля — DDoS самих себя. Профиль: соотношение read/write, размер payload, уникальные ключи, inorganic всплеск, доля тяжёлых тенантов. Генерация с одним `user_id` проверяет hot key, не систему. Генерация с бесконечными уникальными ключами не прогревает кэш.

Цель теста — **точка перегиба**: rps, после которого p99 ломает бюджет или ошибки растут, плюс что ломается первым (12.1). «Выдержали 10k rps» без p99 и без отказа зависимости — не результат. Гонять 2–3× ожидаемого пика и отдельно деградацию зависимости (БД 200 мс, 50% errors).

Интерпретация. Если ломается CPU линейно — scale out/вертикаль. Если ломается p99 при живом среднем — очередь/лок/GC. Если ломается на 5% ключей — шардирование и coalescing, не реплики. Если ломается сеть — смотреть cross-AZ байты и NAT.

Инструменты на 2026: k6, Gatling, свой генератор с тем же протоколом (WS/QUIC отдельно от HTTP). Синтетика из одной AZ врёт по RTT. Chaos (Глава 12.7) — не замена нагрузки; Chaos Mesh в CNCF 2025 — 3% production: ниша после SLO.

Профиль генерации, без которого тест врут. Доля уникальных ключей ≈ прод (иначе 100% cache hit или 100% miss). Размер тела — перцентиль прода, не «типичный JSON». Think time пользователя: 10k rps без пауз — это не 10k людей. Для сокетов: не только handshake, а устойчивые N соединений с fan-out сообщений (иначе проверили только accept). Для мобильного API — смесь 3G/RTT 150 мс в генераторе или честный вердикт «тест без RTT клиента». Останавливать тест при error budget сценария, не при «CPU 80%»: иногда p99 умирает на 40% CPU из-за лока.

Когда не гонять 100×: нет staging с прод-подобными данными — получите ложную уверенность. Чем платите: счётом стейджа и ложным «готовы». Сигнал: нагрузили login, а упала лента.

Для 1–3: один сценарий до перегиба раз в релиз. Для 10–30: пик маркетинга в календаре, тест 2×. Для 100+: постоянные тесты, capacity как 26.7.

## 22.6. Стоимость как метрика инженерии: cost per request, per user, per feature

Единица работы называется в RFC: запрос, GB egress, тик, participant-minute, токен, минута транскода (13.9). Без единицы FinOps не к чему привязать.

Считать: cost per request (compute + DB + сеть + наблюдаемость на этот путь); cost per active user / per tenant; cost per feature (флаг включён → маржа). Наблюдаемость 15–30% инфра, >50% из этого — логи: cost per service на телеметрию — отдельная строка. CI монорепо у >50 инженеров часто топ-3 статья, иногда выше prod compute (research 02).

Салфетка (9.6) до кода: rps × CPU × цена инстанса + GB × тариф. Cross-AZ $0.02/GB RT. Репликация 10 TB/сутки us-east-1 → eu-west-1 ≈ $200/сутки ≈ $6 000/мес только трафик. Публичные чтения S3 ≳5 TB/мес: CloudFront обычно дешевле origin-egress (оценки 85–90%; CloudFront origin same-region $0).

AI: cost per successful task, не per HTTP 200 (13.8). Hedge и мультиагент умножают токены.

Пример на салфетке, который должен жить в RFC. API 500 rps, p50 20 мс CPU, 2 vCPU-эквивалента на 1000 rps после замера → 1 vCPU на текущий rps. c6i.large ~$0.085/час on-demand (порядок AWS 2026, сверять регион) ≈ $60/мес за ядро → compute пути ≈ $60. Плюс 5 TB/мес ответов клиенту: если origin-egress $0.09/GB = $450; через CloudFront $0.085 и 1 TB free — меньше, и origin same-region $0. Если те же 5 TB ещё и ходят cross-AZ туда-обратно между двумя сервисами — +$100 (5 000 × $0.02). Итог: сеть на этом пути дороже compute. Оптимизация JSON на 10% CPU не бьёт счёт; zone affinity и CDN бьют. Без такой строки «ускорили сервис» не связано с деньгами.

Когда не считать per feature: команда из трёх, один продукт, счёт $500. Хватит одной строки AWS. Чем платите за игнор на росте: маржой. Сигнал: MAU плоский, счёт +40%; неатрибутированные расходы.

Для 1–3: месячный счёт / MAU. Для 10–30: теги на сервисы, cost per request топ-5 путей. Для 100+: showback командам, бюджет фичи в RFC.

## 22.7. FinOps: видимость, атрибуция, оптимизация, автоскейл, спот, резервирование

FinOps — инженерная практика с финансовым артефактом, не отдел скидок.

**Видимость.** Теги: service, env, team, cost-center. Нет тега — нет атрибуции. 49% организаций на unit economics (Flexera 2026). AI-расходы в периметре у 98% (FinOps Foundation 2026, было 63%) — burst GPU и токены, которые governance не успевает.

**Атрибуция.** Showback до chargeback. Сначала видят, потом спорят, потом лимиты. Неатрибутированное — отдельный KPI к нулю.

**Оптимизация порядок:** rightsizing → bin-packing / zone affinity → наблюдать пол 60–90 дней → коммит 60–70% пола (40–50% при сезонности) Compute Savings Plans (до 66%) → верхушка Spot (до 90%, прерываемое). Karpenter ротирует типы — instance-locked RI сгорают; SP на compute, не на Spot. Cast AI: частичный Spot ~59% экономии compute, полный ~77% — вендорский бенчмарк, направление верное. Не коммитить до rightsizing: 8% CPU при 69% over-request (Cast AI 2025) — вы резервируете воздух.

Автоскейл по правильной метрике: не CPU, если узкое место — очередь или p99. Scale-to-zero на превью (TTL 7 дней). Kubernetes без `PreferSameZone` (1.35) — скрытый cross-AZ.

Репатриация (37signals): $3,2 млн/год → существенно <$1 млн; 18 ПБ Pure ~$1,5 млн CAPEX, OPEX <$200k/год; проекция >$10 млн за 5 лет. Когда: ровная нагрузка, своя экспертиза, нет нужды в глобальной эластичности. Когда не: пики, малая команда, управляемые сервисы дешевле своего toil.

Когда не FinOps-театр: счёт меньше зарплаты одного инженера. Чем платите за RI до профиля: сгоревшим коммитом. Сигнал: Spot + большой портфель RI; GPU на on-demand при 5% утилизации.

Для 1–3: теги, budget alert, один Savings Plan после 2 месяцев ровного счёта. Для 10–30: еженедельный cost review топ-сервисов. Для 100+: выделенный FinOps, unit-cost в дашборде команд.

## 22.8. Кейс-расчёт: как снизить инфраструктурный счёт в разы без потери качества

Два канона и арифметика сети. Качество = те же пользовательские SLI, не «вроде работает».

**Кейс A. Prime Video VQA, март 2023.** Нагрузка: анализ качества видеопотока. Архитектура: Step Functions, несколько state transition на каждую **секунду** потока; кадры в S3 между микросервисами. Эффект: упёрлись в лимиты аккаунта на ~5% ожидаемой нагрузки; per-transition billing; взрыв S3 Tier-1. Действие: один процесс на инстансе, кадры в памяти, ECS/EC2, Compute Savings Plans. Результат: −90%+ инфраструктурных затрат, масштаб выше. Урок, который перевирают: не «микросервисы плохи». Урок: не распределять оркестрацию на единице «кадр/секунда» и не класть мегабайты в объектное хранилище как шину. Качество: тот же анализ, меньше движения данных. Когда копировать приём: высокочастотная мелкая единица, данные тяжелее RPC. Когда не: независимые домены с разным SLA.

**Кейс B. Cross-AZ как тихий налог, AWS 2026.** Тариф: $0.01/GB в каждую сторону → $0.02/GB round trip. NAT +$0.045/GB; вместе $0.055/GB в одну сторону. Сценарий порядка величины: болтливая сетка 50 TB/мес cross-AZ RT = 50 000 GB × $0.02 = **$1 000/мес** только за «сервис A спросил сервис B в соседней зоне». При 500 TB — $10k/мес без фичи. Плюс NAT на egress из private subnet. Действие без потери качества: `PreferSameZone` / pod affinity; кэш и connection reuse (Cloudflare Pingora: reuse 87,1% → 99,92%, новых соединений к origin ×1/160 — урок шаринга пула, не «переписать на Rust»); не реплицировать Kafka cross-AZ, если лаг 500 мс приемлем (KIP-1150, GA не раньше экстраполяции 2029+). Multi-AZ на стейтфул остаётся для отказа зоны (Глава 12.5): изоляция ≠ болтовня на каждый запрос. Качество: p99 не обязан расти, если чтение остаётся в зоне реплики.

**Кейс C (контроль). 37signals репатриация** — счёт −в разы при своей экспертизе железа; качество продукта не измерялось как CWV в публикации — не копировать как perf-кейс, копировать как TCO при ровной нагрузке.

Сквозная процедура на своём счёте за день:

1. Выгрузить cost by service и data-transfer. Найти top-3: compute, egress/cross-AZ, логи.
2. На top compute: утилизация vs request; rightsizing; не автоскейл от 8% CPU вверх репликами.
3. На transfer: какие вызовы cross-AZ обязательны для SLO, какие — случайный kube-scheduler. Цель: RT трафик только на репликации стейта, не на RPC.
4. На логи: cardinality budget, tier routing (25.7) — часто −30–50% без потери инцидентного окна.
5. Повторить нагрузку 22.5 и поле 22.1: p99 сценария не хуже бюджета. Если хуже — откат экономии, это не «без потери качества».

Число, которое стоит проговорить вслух на ревью. 20 микросервисов × 2 AZ без affinity, 1 KB JSON туда-обратно на каждый пользовательский запрос, 100 rps: 100 × 20 × 2 × 0,001 MB × 86 400 ≈ 345 GB/сутки ≈ 10 TB/мес × $0.02 ≈ **$200/мес** «за архитектуру». На 10k rps это уже $20k/мес. Prime Video убрал не AZ, а **копии данных между процессами**. Оба рычага: меньше RPC и меньше зон на RPC. Качество: пользовательский p99 проверяется после, не до.

Для 1–3: шаг 1–3 вручную в консоли. Для 10–30: еженедельно top-3. Для 100+: политика zone affinity в платформе, cost anomaly alerts.
